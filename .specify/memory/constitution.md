# pecot 憲法

## 基本原則

### I. ドメイン駆動設計（DDD）

コードベースはドメイン（業務領域）を中心に構造化しなければならない（MUST）。
技術的関心事ではなくドメインの境界でモジュールを分割し、
各層の責務を明確に分離する。

- **レイヤー分離**: プレゼンテーション層（CLI/API）、ドメイン層（ビジネスロジック）、
  インフラ層（外部I/O）を分離しなければならない（MUST）。
  依存方向は外側 → 内側（プレゼンテーション → ドメイン ← インフラ）とする。
- **ドメインモジュール**: 各ドメインは独立したモジュールとし、
  ドメイン固有の型・ロジック・ルールをそのモジュール内に閉じ込める。
- **循環依存禁止**: モジュール間の循環インポートは禁止。
  ドメイン間の連携が必要な場合はインターフェース（抽象）を介する。
- **境界づけられたコンテキスト**: ドメインが十分に大きい場合、
  コンテキスト境界を明示的に定義し、コンテキスト間の変換層を設ける。
- **リンターによる構造強制**: DDDの層構造・依存方向はリンタールール
  （インポート制約等）で自動強制しなければならない（MUST）。
  ドキュメントだけの規約は守られないため、違反をCIで検出可能にする。

**根拠**: ドメイン中心の構造はビジネス要件の変化に強く、
各機能を独立してテスト・置換可能にする。リンターとセットで運用することで、
アーキテクチャの劣化を防ぎ、プロジェクト規模の拡大に耐える構造を維持する。

### II. テスト駆動開発（TDD）（交渉不可）

対応するテストなしにコード変更を完了とみなしてはならない。
テストカバレッジは設定された閾値以上を維持しなければならない（MUST）。

- **Red-Green-Refactor**: 新機能は失敗するテストを先に書き、
  テストを通す最小の実装を行い、その後リファクタリングする。
  テストと実装の同時作成も許容するが、テストなしの実装は禁止。
- テストはソース構造を反映して配置する。
- すべてのテストはマージ前に通過しなければならない（MUST）。
- **テスト分類**: 単体テスト（ドメインロジック）、
  統合テスト（層間連携・外部I/O）、E2Eテスト（エンドツーエンド）を
  目的に応じて使い分ける。DDDのレイヤー境界ごとにテスト戦略を定める。

#### テストの実質性

単体テストの通過は正しさの検証にはならない。
単体テストはリグレッション検知の蓄積であり、新しく書いたコードが
意図通りに動作することを証明するものではない。

- テストコードが通ることと機能が動くことは別である。
  「テストが通った」は正しさの十分な証拠にはならない。
- モックはI/O境界（HTTP、ファイルシステム、外部プロセス）に
  限定しなければならない（MUST）。ビジネスロジック、データ変換、
  パース処理は実入力と実出力でテストすること——モック禁止。
- アサーションは具体的な期待値と比較しなければならない（MUST）。
  `assert result is not None`、`assert isinstance(...)`、
  `assert len(...) > 0` は主要アサーションとして不可。
- テスト入力は実際のユースケースを反映しなければならない（MUST）。
  ハッピーパスのみを通る作為的な最小限の例は不可。
- 単体テスト通過後、実際のコマンド／関数を現実的な入力で実行し、
  出力が期待通りであることを確認して動作を検証しなければならない（MUST）。
  これはテストランナー実行とは別のステップである。

**根拠**: TDDはテストを設計ツールとして活用し、実装前に仕様を明確化する。
AIエージェントが書く単体テストは「グリーンパス」の足場になりがちで、
通るようにモックされており、実際の欠陥を検出するようには設計されていない。
テストの実質性を義務付けることで、テストがカバレッジの水増しではなく、
真の品質証拠として機能することを保証する。

### III. コード品質ゲート

コード品質は自動化されたゲートで担保しなければならない（MUST）。
具体的なツール構成はプロジェクトに応じて選定するが、
以下の領域をカバーするゲートが存在しなければならない。

- **リンター/フォーマッター**: コードスタイルの統一を自動で強制する。
- **静的型検査**: すべてのプロダクションコードは言語に応じた
  型チェッカーをstrictモードで通過しなければならない（MUST）。
  すべての関数は完全な型アノテーションを持つこと。
  テストコードはstrictモードを緩和してよい。
- **テストカバレッジ計測**: カバレッジ閾値を設定し、閾値未満でCIを失敗させる。
- **コミットメッセージ検証**: 規約に沿ったメッセージ形式を強制する。
- ゲートが未導入のプロジェクトでは、機能開発の前にゲート整備を
  行わなければならない（MUST）。ゲートなしでの開発着手は禁止。
- 通常のワークフローで `--no-verify` バイパスは許可されない。
  ツールが内部で付けるもの（`nx release` の push）は除く。
  その場合も、push する中身は PR の検証を通っていなければならない（MUST）。

**根拠**: 自動化されたゲートは主観的なスタイル議論を排除し、
すべてのコントリビューター間で一貫したレビュー可能なコードベースを保証する。
型チェックを含む品質ゲートを一体運用することで、統合エラーの早期検出と
コードベースの一貫性を同時に実現する。
ゲートなしで開発を進めると品質負債が蓄積し、後からの導入コストが増大する。

### IV. シンプルさとYAGNI

すべての変更は現在の要件を満たすために必要最小限でなければならない（MUST）。
投機的な抽象化、早期の汎用化、仮定のシナリオに対する
フィーチャーフラグは禁止する。

- 明示的に要求された範囲を超えて機能追加、リファクタリング、
  改善を行ってはならない（MUST NOT）。
- 3行の類似コードは早期抽象化より望ましい。
- エラーハンドリングとバリデーションはシステム境界
  （ユーザー入力、外部API）でのみ必要。
- 直接的なコード変更で足りる場合、後方互換性シムを
  導入してはならない（MUST NOT）。
- 未使用コードはコメントアウトやアンダースコアプレフィックスでのリネームではなく、
  削除しなければならない（MUST）。

**根拠**: 複雑さはソフトウェアの主要な長期コストである。
コードベースをリーンに保つことで保守性と迅速なオンボーディングを確保する。

### V. 本体実装優先（speckit 成果物の編集の最小化）

speckit 成果物（`specs/` の spec・plan・tasks など）への編集は、必要最小限に留めなければならない（MUST）。
AIエージェントは成果物の体裁整理や小さな改善よりも、
本体（`plugins/`・`libs/`・`.githooks/`・`.github/` など、配布物と開発基盤）の
実装作業を優先しなければならない（MUST）。

- speckit 成果物への編集が許容されるのは以下の場合に限る（MUST）:
  - 新規機能の spec/plan/tasks 一式の作成・追加
  - 仕様変更や実装結果との差分に伴う既存 speckit 成果物の整合性修正
  - 憲法・テンプレート・ガバナンス関連ファイルの変更（明示的指示があるとき）
- 本体の実装が未完・未着手の状態で、speckit 成果物の
  文書整形・体裁改善・リファクタのみを目的とした編集を行ってはならない
  （MUST NOT）。「ついでに直す」も禁止。
- 本体に不具合や未実装を発見した場合、speckit 成果物を
  先に直すのではなく、本体での修正を優先提案しなければならない（MUST）。
- ユーザーから speckit 成果物の編集の明示的指示があった場合のみ本原則の
  制約は解除される。指示の範囲を超えた追加編集はしてはならない（MUST NOT）。

**根拠**: speckit 成果物は計画・仕様の集約所であり、その価値は指し示す
本体の実装が完成して初めて実現される。文書の整形は機械的に
着手しやすいためAIエージェントが安易に手を出しがちだが、それ単体では
本来的価値を生まず、本体実装の停滞を覆い隠す。本体優先を明示することで、
計画と実装の乖離および「動いた風」のごまかしを防ぐ。

## ガバナンス

この憲法はプロジェクト原則の権威ある情報源であり、
アドホックな慣習に優先する。すべてのspeckitアーティファクト
（仕様書、計画、タスク、チェックリスト）はこれらの原則と
整合しなければならない（MUST）。

- **改正**: この憲法への変更は明確な根拠とともにPRで提案し、
  レビューと承認を経てマージしなければならない（MUST）。
- **バージョニング**: 憲法はセマンティックバージョニング（MAJOR.MINOR.PATCH）に
  従う。MAJORは原則の削除・再定義、MINORは追加・拡張、
  PATCHは明確化・誤字修正。
- **準拠**: PRレビューはこれらの原則への準拠を検証すべきである（SHOULD）。
  `/speckit.plan` のConstitution Checkゲートはこれらの原則を
  参照しなければならない（MUST）。
- **スコープ**: この憲法は、このリポジトリ（`pecotcraft/pecot`）の speckit 成果物
  （`specs/`・`.specify/`）と実装に適用する。
