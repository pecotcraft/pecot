# 仕様駆動開発フロー

仕様を先に確定させてから実装に入るワークフロー。
Issue乱立を防ぎ、Phase単位で作業を管理する。

## 背景・問題意識

### 現状の課題

| 課題 | 説明 |
|------|------|
| Epic粒度の曖昧さ | 「大きな目標」の基準がなく、ばらつきが発生 |
| Issue肥大化 | Ready/Backlogに古いIssueが溜まる |
| コンフリクト | 同一ファイルを複数タスクで編集するとマージに時間がかかる |
| 形式主義 | テンプレート準拠が目的化するリスク |

### 解決アプローチ

- 仕様と実装を分離し、仕様検討はボード外で行う
- Phase 単位で管理し、Epic を実装フェーズとして扱う
- 順序を明示し、並列可能/直列必須を明確にする

## フロー全体像

```text
┌──────────────────────────────────────────────────────────┐
│  仕様フェーズ（ボード外）                                │
│  ──────────────────────────────────────────────────────  │
│  Speckit/仕様書 → 開発ブランチにマージ                   │
│  （開発ブランチは config の develop_branch）             │
│  （GitHub Projectsには載せない）                         │
└──────────────────────────────────────────────────────────┘
                        ↓ 仕様確定
┌──────────────────────────────────────────────────────────┐
│  実装フェーズ（ボード管理）                              │
│  ──────────────────────────────────────────────────────  │
│  [Epic] Phase 1  ← Backlog                               │
│  [Epic] Phase 2  ← Backlog                               │
│  [Epic] Phase 3  ← Backlog                               │
│                                                          │
│  Phase 1 開始時:                                         │
│    → Phase 1 のサブIssue を Ready に一括投入             │
│    → 1個ずつ Active にして作業                           │
│                                                          │
│  Phase 1 完了 → Phase 2 開始:                            │
│    → Phase 2 のサブIssue を Ready に一括投入             │
└──────────────────────────────────────────────────────────┘
```

## 詳細フロー

### 1. 仕様作成（ボード外）

仕様書をリポジトリ内で管理する。

```text
specs/
├── feature-x/
│   ├── overview.md      # 概要・目的
│   ├── requirements.md  # 要件定義
│   └── design.md        # 設計
```

ポイントは次のとおり。

- PRでレビュー・承認を経て開発ブランチにマージ（base は config の develop_branch で、`project_info` で確認する）
- ボードには載せない（ノイズ防止）
- 仕様確定後に実装フェーズへ

### 2. Epic作成（Phase単位）

仕様確定後、実装をPhase単位に分割してEpicを作成。

```markdown
## [Epic] Feature X - Phase 1: 基盤実装

### 関連仕様
- [specs/feature-x/overview.md](../specs/feature-x/overview.md)
- [specs/feature-x/design.md](../specs/feature-x/design.md)

### 概要
Feature Xの基盤部分を実装する。

### 完了条件
- [ ] データモデル定義
- [ ] APIエンドポイント実装
- [ ] 基本テスト作成

### 前提Phase
（Phase 1の場合は「なし」）
```

### 3. サブIssue投入（Phase開始時）

Phase開始時に、そのPhaseのサブIssueをReadyに一括投入。

次のPhaseのサブIssueは投入しない（Ready肥大化防止）。

### 4. 作業実行

1. Readyから1つ選択 → Active
2. 実装・テスト
3. PR作成・マージ
4. 次のサブIssue

### 5. Phase完了 → 次Phase

Phase内の全サブIssue完了後：

1. Epic本文の完了条件をチェック
2. 次PhaseのサブIssueをReadyに投入
3. 繰り返し

## ステータス運用

現状のステータス構成を維持する。

| ステータス | 用途 |
|-----------|------|
| **Backlog** | Epic（Phase単位）・Tracker置き場 |
| **Pending** | 人が後回しにしたEpicまたはタスク。Ready／Backlog から手動で移動。人だけが出し入れする |
| **Blocked** | 前提を待っているサブIssue。pecot が置き、pecot が出す。ボードに無ければ `project_init` で足す |
| **Ready** | 今、着手できるサブIssue |
| **Active** | 作業中（同時1-2個まで） |
| **Archived** | 完了後退避 |

## 並列作業の制約と対策

### コンフリクト発生パターン

```text
✗ コンフリクト発生:
  [Task] A: src/feature.ts を変更
  [Task] B: src/feature.ts を変更
```

同一ファイルを複数タスクで編集すると、後からマージする方でコンフリクト解決が必要。

### 対策1: ファイル境界を意識したタスク分割

```text
✗ 悪い分割:
  [Task] 機能Aの実装（feature.ts, utils.ts）
  [Task] 機能Bの実装（feature.ts, helper.ts）  ← feature.ts が重複

✓ 良い分割:
  [Task] feature.ts の変更
  [Task] utils.ts の変更
  [Task] helper.ts の変更
```

### 対策2: 直列実行の順序明示

同一ファイルを触るタスクが避けられない場合、Epic本文で順序を明示：

```markdown
## サブタスク（順序あり）

以下の順序で実行すること:

1. [ ] #100 - feature.ts 基盤実装
2. [ ] #101 - feature.ts 機能A追加 ← #100完了後
3. [ ] #102 - feature.ts 機能B追加 ← #101完了後
```

### 対策3: 並列可能タスクの明示

Epic本文で並列実行可能なタスクを明示：

```markdown
## サブタスク

### 並列実行可能
- [ ] #103 - utils.ts ユーティリティ追加
- [ ] #104 - helper.ts ヘルパー追加

### 直列実行必須（順序あり）
1. [ ] #100 - feature.ts 基盤
2. [ ] #101 - feature.ts 機能A
```

## 運用ルール

### Epic本文の必須事項

| 項目 | 説明 |
|------|------|
| 関連仕様リンク | 仕様書へのリンク必須 |
| 完了条件 | チェックリスト形式 |
| 前提Phase | 依存するPhaseがあれば明示 |
| サブタスク順序 | 並列/直列を明示 |

### 仕様変更時の対応

| パターン | 対応 |
|---------|------|
| 軽微な変更 | 仕様書更新 + 既存Issueに追記 |
| 中規模変更 | 仕様書更新 + 追加タスクIssue作成 |
| 大規模変更 | 新規Phaseとして別Epic作成 |

### Phase投入タイミング

- 投入するのは、前Phaseの全サブIssue完了後
- 並列可能と判断した場合は、例外として同時投入してよい
