# 計画の前の clarify

計画を書く前に、Issue と依頼の曖昧な点を洗い出し、利用者に聞いて決める。進め方は Spec Kit の clarify と同じにする。
違うのは、読む対象が spec ではなく Issue と依頼であることと、答えを書き込む先が計画であることだけだ。

- [Spec Kit の clarify](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)

## 1. 洗い出す

Issue の本文・依頼の文・調査で読んだコードを、次の観点で見る。観点ごとに「明確」「一部だけ」「欠けている」のどれかに分ける。

- 範囲と振る舞い（達成したい状態、対象外、使う人）
- データ（扱う対象、状態の移り変わり、量）
- 操作の流れ（利用者の手順、エラーや空のときの見え方）
- 品質（性能、信頼性、セキュリティ、観測）
- 外とのつなぎ（外部のサービスや API と、その失敗のとき。データの形式）
- 端のケースと失敗の扱い
- 制約とトレードオフ（技術の制約、採らない案）
- 用語（同じものを指す語のゆれ）
- 完了の条件（Acceptance を確かめられるか）
- 未決の印（TODO、「適切に」「使いやすく」のような量の無い語）

## 2. 質問を選ぶ

「一部だけ」「欠けている」の観点から、質問の候補を作る。

- 答えで実装か検証のやり方が変わる点だけを、質問にする
- 実装の手段・技術の比較・作業の分け方は、質問にしない。正しさを左右するときだけ聞く
- もう答えの出ている点と、書き方の好みは、質問にしない
- 質問は 5 問までにする。超えるときは、影響と不確かさの大きい順に選ぶ
- 候補が無ければ、聞かずに計画へ進む。曖昧な点が無かった旨を 1 行で伝える

## 3. 聞く

AskUserQuestion で、1 問ずつ聞く。後の質問を先に見せない。

- 質問は、それだけで意味の通る疑問文にする。見出しや項目名を質問にしない
- 答えで何が変わるかを、質問に 1 文で添える
- 選択肢は 2〜4 個で、互いに重ならないものにする。推奨の案を先頭に置き、推す理由を書く
- 答えが曖昧なら、同じ質問のまま聞き直す。問数には数えない
- 重要な点が決まったとき、利用者が切り上げたとき、5 問を聞いたときに終える

## 4. 計画に書く

答えを 1 つ受けるたびに、計画のファイルに書く。

- Notes の折りたたみに `- Q: <質問> → A: <答え>` を 1 行足す
- 答えの当たる見出し（Approach・Files・E2E）を直す。答えで外れた案の記述は、消して置き換える
- 5 問で聞ききれなかった重要な点は、計画を投稿する前に利用者へ伝える
