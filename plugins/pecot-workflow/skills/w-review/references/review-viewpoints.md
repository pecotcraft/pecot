# レビューの視点

PR の diff を 2 つの視点で見て、指摘を出す。コードの編集・テストの実行・CUJ の実行はしない。

## 返し方

指摘ごとに、視点の印を 1 つ付ける。印は `[tech]`・`[cuj]` の 2 つで、下の節の見出しに対応する。

- 指摘ごとにファイルと行を添える。行を指せない指摘は、その旨を書く
- 視点に当たる指摘が無ければ、その視点は「指摘なし」とする
- 指摘は、直した形まで書く。推奨と不適合を混ぜない

## 調べ方

指摘には根拠の出典（公式文書・ソース・型定義）を示す。学習データだけで判断しない。
既存の実装と同じ形であることと、テストが通ることは、正しい使い方の根拠にしない。

根拠は、リポの中のコード・型定義・設定・同梱の文書と、外の公式の文書を読んで確かめる。外の文書は、次の順で引く。

1. ライブラリ・フレームワークの文書は、Context7 の `resolve-library-id` と `query-docs` で引く
2. 仕様・公式の文書のページは、`WebFetch` で読む
3. ページの場所が分からないときは、`WebSearch` で探してから `WebFetch` で読む

`WebFetch` は、許されたドメインのページしか読めない。拒まれたら、別のドメインで同じ文書を探さない。
外の文書を引けなかった根拠は、学習データに頼った旨を指摘に書く。

許可の無いツールは試さず、確かめられなかった点を指摘に書く。

## [tech] 標準との適合と技術的正確性

次の 3 つを見る。API の使い方・設定・型が正しいか、非推奨・廃止の API を使っていないかもあわせて確かめる。

1. 標準との適合: 対象の仕組みの仕様と公式の参照実装を読み、diff の形を項目ごとに比べる
   - 違う点は「不適合」として 1 つずつ挙げ、標準に合わせた形を示す。推奨として返さない
   - 標準の無い技術では、公式に推奨される方式と比べる
2. 全消費環境: 変更するデータ（ファイル・設定・出力）を読むすべての環境・ツールを挙げ、各環境での互換性を文書・仕様で確かめる
3. コードパス: 入力の読み込みから最終出力までを、ソースの関数単位で追い、途中で変換・除外される箇所を示す

### 計画と照らす

w-review の Step 1 で、PR が閉じる Issue の計画のコメントを読めたときに行う。読めなかったときは、この節を飛ばす。

次の 3 つを見る。

1. 計画の Files にあって、diff で直していない項目
   - Files の `<details>` の中の、ファイルごとの項目まで照らす
   - ディレクトリの項目は、その下に新しいファイルがあれば、直したとみなす
   - Files に無いファイルを直しただけでは、指摘にしない
2. diff の形が、計画の Files の詳細・Approach と違う点
3. PR の本文の主張（Summary・Changes）と、diff の外に残った記述（spec・README・参照）の食い違い
   - 主張の語でリポを Grep して、diff の外の記述を探す
   - 食い違いは、行を指せないので General の指摘にする

指摘には `[tech]` を付け、計画の該当の箇所（見出しと項目）を引く。
計画と diff のどちらが正しいかは決めない。計画を直すか diff を直すかを、書き手に選ばせる形で書く。

## [cuj] CUJ とテストの品質

- 変更が既存の CUJ に与える影響を見る
- テストの妥当性・網羅性を見る。テストが期待値と比べているか、モックが I/O 境界だけにあるかを確かめる
- 標準や公式の仕様がある公開面（MCP ツールの結果など）のテストは、仕様の項目で確かめているかを見る
