# Feature Specification: PR を作ると、クラウドのエージェントが w-revise を自動で回す — 人が端末で起こさなくても、レビューの指摘が PR に載る

**Feature Branch**: `027-auto-revise-on-pr`

**Created**: 2026-11-16

**Status**: Draft

**Input**: Epic pecotcraft/pecot#489。pecot-workflow の利用者が PR を作ると、クラウドで動くエージェントが w-revise の手順でその PR をレビューする。人は端末で w-revise を起こさない。指摘は PR に投稿される。承認待ちで止まらない。起動する PR・ツール・ターンと時間に上限を置く。pecot の最初のクラウドのエージェントとして作る。

## Clarifications

### Session 2026-11-16

- Q: 自動レビューのエージェントは、どこで動かすか → A: GitHub Actions の上で、claude-code-action を PR の契機で動かす。claude.ai/code のクラウドセッションは使わない（FR-002）
- Q: 自動レビューは、どこまで進めて終わるか → A: 指摘の投稿まで。採否の決定・修正のコミットと push・スレッドの resolve・対応の報告は行わない。続きは、w-pr の Step 5 で進める（FR-010、FR-011、FR-014。2026-11-17 に、続きの場所を w-revise から w-pr に改めた）
- Q: 起動・トークン・安全策は spec 023 と重なる。どう分けるか → A: この spec が共通の部分を先に作る。spec 023 は、後からそれを使う形に直す（FR-019、FR-033）
- Q: 自動レビューの手順は、どのスキルが持つか → A: w-revise の 1 本が持つ。レビューと指摘の投稿は、PR が来るたびに GitHub Actions の上で行う形を標準にする。端末で同じレビューをする道も残し、使うかは開発者が選ぶ。新しいスキルは足さない（FR-005、FR-014）
- Q: PR に新しいコミットが push されたときも、自動レビューは起動するか → A: 起動しない。起動するのは、PR の作成と、書き込み権限を持つ人が PR に合言葉のコメントを書いたときだけ（FR-001、FR-003）。合言葉の既定は `@pecotbot review` だ
  - 例外は、まだ自動レビューの付いていない PR への push だ。GitHub はコンフリクトのある PR では作成と ready のワークフローを動かさないので、解いた push で最初のレビューを起こす（#682）
- Q: bot が作った PR でも、自動レビューは起動するか → A: 設定を変えなければ起動しない。利用者が名前で許した bot の PR だけ起動する。bot の PR でも、人が合言葉のコメントを書けば起動する（FR-025）

### Session 2026-11-17

- Q: 人のいない実行のために、スキルに分岐（`--unattended`）を足すか → A: 足さない。w-revise を w-review に改め、PR の情報・レビュー・投稿だけにする。w-review を起こすのはワークフローだけで、開発者が PC から打つ場面は無い（FR-005、FR-008）
- Q: 指摘の採否・修正・報告は、どこで行うか → A: w-pr の Step 5。PR を出した開発者は、CI とレビューを待つ間も手を止めない。レビューのコメントが付いたら考える工程は、PR を出して CI を待つ w-pr の側にある（FR-014）
- Q: レビューの視点は → A: `[tech]`・`[cuj]` の 2 つ。`[quality]`（コード品質）は外す。計画のレビューのエージェントは w-plan-reviewer に改め、PR のレビューには使わない（FR-006）
- Q: 自動レビューの GitHub のトークンは、どの App のものを使うか → A: 既定は、公式の Claude の GitHub App だ。利用者が自前の App を作らずに導入できる。権限を絞りたい利用者は、自前の App を作り、その変数と secret を置けば、雛形がそちらを使う。Claude の App のトークンは書き込みを持つので、FR-011 は、エージェントに書き換えの手段を渡さないことで守る（FR-011、FR-019）

## 背景

PR のレビューは、人が端末で w-revise を起こさないと始まらない。

| 場面 | 今の姿 |
|---|---|
| PR を作った後 | 人が端末で `/pecot-w:w-revise` を打つ。打ち忘れた PR は、w-reviewer の指摘が無いままマージの判断に進む |
| 指摘の採否 | w-revise は、指摘を投稿した後、採否を人に質問して待つ。人のいない実行では、ここで止まる |
| レビュアーの起こし方 | w-revise は、w-active で控えた w-reviewer に頼む形を先に試す。人のいない実行には、控えた相手も会話の文脈も無い |
| クラウドで動くエージェント | pecot にはまだ 1 つも無い。Issue のラベルで起こす自動処理（spec 023）は計画までで、実物が無い。spec 023 は、レビュー指摘への対応を対象から外している |
| claude.ai/code のクラウドセッション | pecot CLI が動かない。GitHub のプロキシが GraphQL を 403 で拒否する。プラグインも読み込まれない |

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| 自動レビュー | PR を契機に、GitHub Actions の上でエージェントが w-revise の手順を指摘の投稿まで進める 1 回の実行 |
| 導入先のリポ | 利用者が自動レビューの仕組みを置いたリポ |
| 指摘 | w-review が PR の diff に付ける `F-NN` の 1 件 |
| 指摘の一覧 | w-revise が PR に投稿する `review-findings` のコメント |
| 対応の報告 | w-revise が PR に投稿する `review-resolution` のコメント |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PR を作ると、人が介さずにレビューの指摘が PR に載る (Priority: P1)

導入先のリポの開発者が PR を作る。自動レビューが始まり、w-review の視点でその PR の diff を見る。指摘は、インラインコメントと指摘の一覧として PR に載る。開発者は、PR の画面で指摘を読む。

**Why this priority**: Epic の目的そのものだ。これだけで、w-revise の打ち忘れで指摘の無いままマージに進む PR が無くなる。

**Independent Test**: 導入先のリポで、指摘の出る変更を含む PR を作る。人が何も操作せずに、インラインコメントと指摘の一覧が PR に付くことを確かめる。採番・投稿先・コメントの形が、`review-findings` のテンプレートと CLI の検証に合うことを確かめる。

**Acceptance Scenarios**:

1. **Given** 導入先のリポ、**When** 書き込み権限を持つ人が PR を作る、**Then** 人の操作なしで自動レビューが始まり、指摘がインラインコメントと指摘の一覧で PR に載る
2. **Given** 進行中の自動レビュー、**When** w-review の手順を進める、**Then** 人へ質問する箇所が無く、人を待たずに投稿まで進む
3. **Given** 自動レビューが投稿したコメント、**When** 採番・投稿先・本文の形を見る、**Then** `review-findings` のテンプレートの形で、CLI の検証を通っている
4. **Given** 指摘が 1 件も無い PR、**When** 自動レビューが終わる、**Then** 0 件だったことを PR のコメントから読める
5. **Given** 自動レビューが終わった PR、**When** 開発者が PR を見る、**Then** PR から結果を読める。終えたときは指摘の一覧がある。終えられなかったときは、止まったことを知らせるコメントがある
6. **Given** 既に外部のレビュアーのコメントがある PR、**When** 自動レビューが指摘をまとめる、**Then** 外部の指摘を投稿し直さず、指摘の一覧に元のスレッドを添えて並べる

---

### User Story 2 - 起動する PR・使えるツール・ターンと時間に上限があり、外部の PR から起動されない (Priority: P1)

導入先のリポが public でも、fork からの PR と、書き込み権限の無い人の PR では、自動レビューは起動しない。起動された自動レビューは、許可リストにあるツールだけを使い、ターンと時間の上限で止まる。同じ PR の自動レビューは同時に 1 つしか動かない。

**Why this priority**: 人のいないエージェントが、PR に書き込むトークンを持って動く。PR の diff と本文は、外部の人が書ける入力だ。安全策が無い仕組みは、public リポの利用者に配れない。User Story 1 と同じ版で届ける。

**Independent Test**: fork から PR を作り、自動レビューが起動しないことを確かめる。次に、ターンの上限を小さくして、書き込み権限を持つ人が PR を作る。上限で止まり、PR に報告が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** public な導入先のリポ、**When** fork から PR が作られる、**Then** 自動レビューは起動しない
2. **Given** public な導入先のリポ、**When** 書き込み権限の無い人が、PR へコメントする・本文に起動を促す文を書く、**Then** 自動レビューは起動しない
3. **Given** 進行中の自動レビュー、**When** 許可リストに無いツールやコマンドを使おうとする、**Then** その操作は実行されない
4. **Given** 進行中の自動レビュー、**When** ターンか時間の上限に達する、**Then** 自動レビューが止まり、上限で止まったことが PR に残る
5. **Given** 自動レビューが進行中の PR、**When** 同じ PR でもう一度起動の契機が起きる、**Then** 同じ PR の自動レビューは 2 つ同時に動かない
6. **Given** 仕組みを導入した直後のリポ、**When** 利用者が既定値を何も変えない、**Then** FR-020〜FR-025 の安全策がすべて有効になっている
7. **Given** diff・PR の本文・コメントに、許可の外の操作や secret の表示を求める文がある PR、**When** 自動レビューがその PR を読む、**Then** その文に従わない

---

### User Story 3 - 自動レビューは指摘の投稿で終わり、開発者は w-pr で続きから進められる (Priority: P2)

自動レビューは、指摘を投稿したところで終わる。採否を決めず、コードを直さない。PR を出した開発者の w-pr は、CI を待った後、自動レビューが投稿した指摘をそのまま使い、採否の確認から進める。同じレビューを 2 度行わない。

**Why this priority**: 指摘を盲目的に適用しないために、採否は人が決める。その続きで、自動レビューの指摘を使えないと、開発者は同じレビューをもう一度待つことになる。指摘が PR に載るだけでも User Story 1 の価値が出るので、P2 とする。

**Independent Test**: 指摘が複数出る PR を作り、自動レビューが終わるのを待つ。PR のブランチに、自動レビューのコミットが無いことを確かめる。次に、開発者の PC で w-pr を起こす。新しい指摘が重ねて投稿されず、Step 5 で自動レビューの指摘の採否を聞かれることを確かめる。

**Acceptance Scenarios**:

1. **Given** 指摘を投稿し終えた自動レビュー、**When** 投稿が済む、**Then** 人に質問せず、採否を決めずに終わる
2. **Given** 自動レビューが終わった PR、**When** PR のブランチとスレッドを見る、**Then** 自動レビューのコミットが無く、自動レビューが resolve したスレッドも無い
3. **Given** 自動レビューが終わった PR、**When** 開発者が、w-pr を PC から起こす、**Then** w-pr の Step 5 は自動レビューの指摘を使い、採否の確認へ進む。同じ指摘を重ねて投稿しない

---

### User Story 4 - 利用者が onboarding の流れで、自動レビューの仕組みとトークンを導入できる (Priority: P3)

pecot の利用者が、onboarding の流れの中で自動レビューを使うかを選ぶ。使うなら、仕組みがリポに置かれ、要るトークンと secret の用意が手順として示される。導入の後、設定がそろっているかを確かめられる。

**Why this priority**: User Story 1〜3 は、このリポ自身に手で設定して確かめられる。利用者に届けるには導入手順が要るが、仕組みが動いた後に固める。

**Independent Test**: 自動レビューを入れていないリポで onboarding の流れをたどり、示された手順だけで導入する。PR を作って、指摘が PR に載ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 自動レビューを入れていないリポ、**When** 利用者が onboarding の流れで導入を選ぶ、**Then** 仕組みがリポに置かれ、利用者の行う設定が FR-028 の順に示される
2. **Given** 導入の手順、**When** トークンに要る権限を読む、**Then** 要る権限が最小の範囲で列挙され、それぞれ何に使うかが書かれている
3. **Given** 導入を終えたリポ、**When** 設定の確認を動かす、**Then** 足りない設定（雛形・変数・secret）が名前で示される。Claude の App が入っているかは、導入の手順が確かめ方を示す
4. **Given** onboarding の流れ、**When** 利用者が自動レビューを使わないと選ぶ、**Then** 何も置かれず、ほかの onboarding の手順は変わらない
5. **Given** 導入済みのリポ、**When** pecot-workflow の新しい版で仕組みが変わる、**Then** 利用者は、置いたものが古いことと更新の手順を知る方法を持つ

---

### User Story 5 - 後に続く自動処理が、起動・トークン・安全策の同じ仕組みを使える (Priority: P3)

pecot を開発する人が、2 つ目のクラウドのエージェント（spec 023 の自動処理など）を足す。起動者の確かめ方・トークンの渡し方・上限の決め方は、自動レビューで作ったものを使う。利用者は、2 つ目のためにトークンを作り直さない。

**Why this priority**: 自動レビューは、pecot の最初のクラウドのエージェントだ。ここで決めた形が、後の自動処理の前提になる。自動レビューだけでも価値が出るので、P3 とする。

**Independent Test**: 自動レビューの導入を終えたリポで、導入の手順と配布物を読む。起動・トークン・安全策のうち、自動レビューに固有でない部分が、ほかの自動処理から使える形で分かれていることを確かめる。

**Acceptance Scenarios**:

1. **Given** 自動レビューを導入済みのリポ、**When** 利用者が後から別の自動処理を導入する、**Then** 自動レビューのために作ったトークンと secret を、作り直さずに使える
2. **Given** 配布物の導入の手順、**When** トークンと安全策の説明を読む、**Then** 自動レビューに固有の設定と、ほかの自動処理と共通の設定が、分けて書かれている

---

### Edge Cases

- draft の PR が作られたとき — 起動しない。ready for review への切り替えで起動する
- bot が作った PR（Dependabot など）のとき — 利用者が名前で許した bot の PR だけ起動する。許していない bot の PR は、人が合言葉のコメントを書いたときだけ起動する
- PR に新しいコミットが push されたとき — 起動しない。人が合言葉のコメントで起こす
- 既に自動レビューが終わった PR で、起動し直したとき — 2 巡目として扱う。前の指摘が直ったかを先に確かめ、同じ趣旨の指摘は、新しく投稿せずにそのスレッドを指す
- 自動レビューが進行中に、PR が閉じられた・マージされたとき — 進行中の実行は、その後に PR へ書き込まずに終わる
- 自動レビューが進行中に、人が同じブランチへ push したとき — 人のコミットを上書きしない。古い diff への指摘であることが、コメントから分かる
- diff がとても大きい PR のとき — ターンか時間の上限で止まり、PR に止まった場所が残る
- 積んだ PR（下の段の PR の上に作った PR）のとき — その PR 自身の diff だけをレビューする。載せ直しが要るときは、載せ直さずに、要ることを PR に書く
- インラインコメントの投稿が拒否されたとき — その指摘を指摘の一覧に回す
- トークンの期限切れ・権限の不足で、途中の操作を拒否されたとき — 拒否された操作の名前を PR に書いて終わる。PR にも書けないときは、実行の記録に残す
- モデルの利用に要る認証（API キーなど）が無い・無効のとき — 起動の直後に失敗し、実行の記録から原因が分かる
- diff・PR の本文・コメントに、エージェントへの指示（secret の表示・ほかのリポへの push など）が書かれているとき — 従わない
- GitHub Enterprise Server のリポ — 使える範囲と使えない範囲を、導入手順に書く

## Requirements *(mandatory)*

### Functional Requirements

**起動 — PR の作成で始まる**

| ID | 要件 |
|---|---|
| FR-001 | 導入先のリポで、書き込み権限を持つ人が PR を作ったとき、自動レビューが 1 回始まらなければならない。draft の PR は、ready for review になったときに始まる |
| FR-002 | pecot-workflow は、PR の作成を契機に自動レビューを起こす仕組みを、配布物として持たなければならない。仕組みは、pecot-workflow のプラグインを実行環境に入れ、FR-005 の手順を起動する。実行の場所は GitHub Actions で、エージェントの実行には claude-code-action を使う |
| FR-003 | 書き込み権限を持つ人は、PR に合言葉で始まるコメントを書いて、自動レビューを起動し直せなければならない。合言葉は既定値を持ち、利用者が変えられる。新しいコミットの push は契機にしない。ただし、まだ自動レビューの付いていない PR は、push でレビューを始める。作成か ready のときにコンフリクトで実行の起きなかった PR が当たる |
| FR-034 | 欠番。起動ラベルを外す決まりだった。起動し直しを合言葉のコメントに変え、外すラベルが無くなった（2026-11-17） |
| FR-035 | 合言葉のコメントで起動したとき、自動レビューは、始まった時点でそのコメントに 👀 のリアクションを付けなければならない。飛ばされたときは付けない |
| FR-004 | 自動レビューの対象は、導入先のリポの中のブランチから作られた PR に限らなければならない |

**手順 — 承認を待たずに w-review を進める**

| ID | 要件 |
|---|---|
| FR-005 | 自動レビューの手順は、w-review（旧 w-revise）の 1 本が持たなければならない。新しいスキルは足さない。w-review を起こすのは、自動レビューのワークフローだけだ。指摘への対応（採否・修正・報告）は w-pr の Step 5 が持つ |
| FR-006 | w-review は、会話の文脈が無い状態から、PR の diff をレビューしなければならない。サブエージェントは起こさず、main が w-review の視点の参照に従ってレビューする |
| FR-007 | 自動レビューが投稿する指摘の採番・投稿先の振り分け・コメントの本文の形は、`review-findings` のテンプレートに従わなければならない。CLI の検証を通り、検証を迂回してはならない |
| FR-008 | w-review は、人の承認や答えを待つ箇所を持ってはならない |
| FR-009 | 自動レビューは、指摘が 0 件のときも、0 件だったことを PR に残さなければならない |
| FR-010 | 自動レビューは、指摘の一覧を投稿したところで終わらなければならない。採否の決定・コードの修正・コミット・push・スレッドの resolve・対応の報告の投稿を行ってはならない |
| FR-011 | 自動レビューは、導入先のリポのブランチとファイルを変更してはならない。エージェントに、リポの内容を書き換えるツールを渡さない。利用者が自前の App を使うときは、トークンの権限も、リポの内容を書き換えられない範囲に限る |
| FR-012 | 自動レビューは、終わるときに必ず、結果を PR に残さなければならない。結果は、レビューを終えた・失敗した・上限で止まった・設定が足りない、のどれかである。終えたときは、指摘の一覧が結果を兼ねる。ほかの 3 つのときは、止まったことを知らせるコメントを 1 つ残す。実行の記録へは、GitHub が PR に出すチェックの行から行ける |
| FR-013 | 自動レビューは、PR のマージ・PR のクローズ・Issue のクローズ・リリースを行ってはならない |
| FR-014 | w-pr の Step 5 は、PR の未解決の指摘を使って採否の確認から進められなければならない。同じ指摘を重ねて投稿しない |
| FR-015 | 2 巡目以降の自動レビューは、前の指摘が直ったかを先に確かめ、指摘の一覧に直ったか・直っていないかを書かなければならない。F-NN は PR の中の通し番号とし、新しい指摘には続きの番号を振る。前の指摘と同じ趣旨のものは、新しく投稿せず、指摘の一覧でそのスレッドを指す |

**権限**

| ID | 要件 |
|---|---|
| FR-016 | 自動レビューに渡すトークンの渡し方は 1 つに決め、導入手順に書かなければならない。要る権限は最小の範囲で列挙し、それぞれ何に使うかを書く |
| FR-017 | 自動レビューに渡すトークンと secret は、PR・コメント・コミット・実行の記録に出力されてはならない |
| FR-018 | 要る権限が無いとき、自動レビューはレビューを始めずに終わり、足りない設定を PR に書かなければならない |
| FR-019 | 起動者の確かめ方・トークンの渡し方・上限の既定値・導入の手順のうち、自動レビューに固有でない部分は、この spec が先に作らなければならない。後に続く自動処理が、作り直さずに使える形で持つ |
| FR-033 | spec 023 の成果物（spec・plan・tasks）は、FR-019 の共通の部分を使う形に直さなければならない。直すのは、共通の部分の形が決まった後とする |

**安全策**

| ID | 要件 |
|---|---|
| FR-020 | 書き込み権限の無い人の操作は、public リポでも自動レビューを起動してはならない。fork からの PR は、FR-004 で対象から外れる |
| FR-021 | PR の本文・タイトルの編集、合言葉で始まらないコメント、Issue へのコメントでは、自動レビューを起動してはならない。合言葉での起動は、コメントを書いた人が書き込み権限を持つときに限る |

### Key Entities

| 名前 | 内容 |
|---|---|
| 自動レビューの実行 | 1 つの PR に対する 1 回の実行。契機（PR の作成・起動し直し）・対象の PR・結果（レビューを終えた・失敗・上限・設定の不足）を持つ |

## Assumptions

- 起動の契機は、PR の作成と、draft から ready for review への切り替えだ。新しいコミットの push では起こさない。指摘が重なり、費用も増えるためだ。起動し直しは、PR へのコメントの合言葉で行う
  - claude-code-action の公式の例（`@claude` のメンション）と同じ形だ
  - ラベルで起動し直す形は、action の公式の例に無いので採らない（2026-11-17、ユーザーの判断）
  - `pecotbot` は、pecot が Organization として持つ名前だ。CodeRabbit（`@coderabbitai review`）・Sourcery・Dependabot と同じく、提供元が持つ名前に話しかける形で、他人に通知が飛ばない（research の R15）
- 「クラウドのエージェント」は、GitHub Actions の上で動くエージェントを指す。claude.ai/code のクラウドセッションは、pecot CLI が動かないので使わない
- 自動レビューは、ボードの欄を動かさない。w-review も w-pr の Step 5 も動かさないためだ
- 積んだ PR の載せ直しは、自動レビューでは行わない。載せ直しは force push を伴い、衝突で人の判断が要るためだ
- CUJ の再実行（w-pr の Step 5）は、自動レビューでは行わない。修正をしないためだ
- モデルの利用に要る認証は、利用者が用意して導入先のリポに登録する。どの認証を既定にするかは、下の「費用と認証の方針」に従う
- ターン・時間・許可リストの既定値の具体的な数と中身は、検証用のリポでの試行をもとに決める
- w-review は、サブエージェントを起こさない。人のいない実行で起こせることは確かめたが、裏で起こすと結果を待たずに実行が終わった。分けるべき作業の文脈も無い（research の R5、2026-11-17 のユーザーの判断）
- 確かめの場所は、spec 026（マージ前の変更を確かめる試験環境）の決まりに従う。外部から起動されないことも、検証用のリポで確かめる
- 最初の導入先は、このリポ（pecotcraft/pecot）である。導入は、検証用で通った後に行う
- GitHub Copilot CLI を人のいない環境で動かす形は、この spec の対象にしない。スキルの文は、Claude Code 固有のツール名に依らない書き方を保つ
- 他チームの PR のレビューは対象にしない。w-revise が、自分たちの PR だけを対象にしているためだ

## 費用と認証の方針

自動レビューは、PR を作るたびに動く。このリポでは、2026-10-17〜11-16 の 30 日にマージされた PR が 250 件あった。認証の選び方で、この件数の費用を誰がどう払うかが変わる。

| 認証 | 払い方 | 引き受けること |
|---|---|---|
| Claude のサブスクリプションのトークン（`claude setup-token`） | 月額の中で使う。追加の費用は無い | 開発者が手元で使うのと同じ使用量の枠を使う。トークンに寿命があり、切れたら作り直す |
| Workload Identity Federation | API の従量。Console の組織のクレジットから引かれる | 1 件ごとに費用が出る。リポに secret を置かない |
| API キー | 同上 | 同上。静的な secret を置く |

- 既定は、サブスクリプションのトークンにする。ユーザーの判断だ（2026-11-17）。月の件数が多く、従量では費用が読めないためだ
- 雛形は、トークンの secret と Workload Identity Federation の変数の両方を読む。secret があればトークンで動き、消せば Workload Identity Federation で動く。雛形を書き換えずに切り替えられる
- トークンが切れたときは、自動レビューが止まったことを PR のコメントで知らせ、作り直す手順を書く（FR-012）
- API キーは、雛形で読まない。Workload Identity Federation が同じ従量で、secret を置かずに済むためだ
