# Feature Specification: バグ修正と小さなタスクを起票の時点で処理する — Issue にラベルを付けると、GitHub Actions が pecot の手順で直して PR まで作る

**Feature Branch**: `023-label-triggered-autofix`

**Created**: 2026-11-11

**Status**: Draft

**Input**: Epic pecotcraft/pecot#315。バグ修正と小さなタスクの Issue にラベルを付けると、GitHub Actions が pecot の手順でブランチ・修正・テスト・PR 作成まで進める。承認待ちで止まらず、迷えば Issue に質問を書いて終わる。起動できる人・ツール・ターンと時間に上限を置く。

## Clarifications

### Session 2026-11-11

- Q: 無人で進める手順は、新しいスキルとして足すか、既存の w-quick・w-pr に無人のモードを足すか → A: 新しいスキルを 1 つ足す。w-quick・w-active・w-pr は変えない（FR-003）
- Q: 自動処理はどこまで進めて終わるか → A: PR を作った後、その PR の CI が通るまで直す。直す回数に上限を置く。レビュー指摘への対応とマージは含めない（FR-007、FR-035〜FR-037）
- Q: 質問や上限で止まった自動処理を、人はどの操作で起動し直すか → A: 起動ラベルの付け直しだけにする。自動処理は終わるときに起動ラベルを外す。コメントでは起動しない（FR-011、FR-038）
- Q: PR が無いまま止まった Issue を、ボードの上でどう見せるか → A: 進行の欄は Active のままにする。既定の Status に待ちの値を 1 つ足し、自動処理が止まるときにその値を書く。起動し直すと Todo に戻す。着手と PR の時点では既定の Status に書かず、ボードの既定の自動化に任せる（FR-018、FR-039〜FR-043）
- Q: PR ができた後、CI を直す回数の上限で止まった Issue にも、待ちの値を書くか → A: 書く。進行の欄は In Review のままにする。起動し直すと In Progress に戻す（FR-039、FR-040）

## 背景

小さなバグ修正でも、起票から PR までは人が端末でスキルを順に回す。

| 場面 | 今の姿 |
|---|---|
| 起票から PR まで | 人が w-quick（または w-active）→ 実装 → w-pr を手で回す。1 ファイルの修正でも同じ手順と待ち時間がかかる |
| 無人での実行 | w-quick と w-pr は、プランモードの承認と質問で人を待つ。無人で動かすと途中で止まる |
| claude.ai/code のクラウドセッション | pecot CLI が動かない。GitHub のプロキシが GraphQL を 403 で拒否し、CLI の Issue・PR・リポ・ボードの操作は GraphQL を使う。プラグインも読み込まれない |
| GitHub Actions（claude-code-action） | 入力の `plugins` で pecot-workflow を入れられる。しかし pecot には、起動するワークフローの雛形も、無人で進めるスキルも無い |

無人の実行の置き場は GitHub Actions にする。pecot CLI とプラグインが動く無人の環境が、今はここだけだからだ。

ボードには状態を示す欄が 2 つある。

| 欄 | 動かしているもの |
|---|---|
| 進行の欄 | pecot CLI。着手で Active にし、PR の作成で In Review にする |
| 既定の Status | ボードの既定の自動化。追加で Todo、PR の連携で In Progress、クローズで Done にする。pecot CLI は書かない |

PR が無いうちは、既定の Status は Todo のままだ。着手済みかどうかは進行の欄の列で読む。

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| 自動処理 | ラベルを契機に、GitHub Actions の上でエージェントが Issue から PR までを進める 1 回の実行 |
| 起動ラベル | 付けると自動処理が始まるラベル |
| 導入先のリポ | 利用者が自動処理のワークフローを置いたリポ |
| 進行の欄 | pecot がボードに足す独自のフィールド。値は Backlog・Pending・Ready・Active・In Review・Archived。今のボードの列になっている |
| 既定の Status | GitHub のボードに初めからあるフィールド。値は Todo・In Progress・Done。カードの上に色付きの札で出る |
| 待ちの値 | 既定の Status に足す値。人の対応を待っていることを示す |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Issue にラベルを付けると、人が介さずに pecot の規則どおりの PR ができる (Priority: P1)

導入先のリポの保守者が、バグ修正か小さなタスクの Issue に起動ラベルを付ける。自動処理が、ブランチの作成・計画の投稿・修正・テスト・PR の作成を進め、PR の CI が通るまで直す。保守者は、できた PR をレビューしてマージする。端末は開かない。

**Why this priority**: Epic の目的そのものだ。これだけで、1 ファイルの修正に人の手順と待ち時間がかからなくなる。

**Independent Test**: 導入先のリポで、直し方が本文から決まるバグの Issue に起動ラベルを付ける。人が何も操作せずに、その Issue を閉じる PR ができることを確かめる。できた PR の本文・ブランチ名・コミットを、手で回すときの検証にかけ、通ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 直し方が本文から決まる open の Issue、**When** 起動できる人が起動ラベルを付ける、**Then** Issue に計画のコメントが付き、その Issue を閉じる PR ができる
2. **Given** 進行中の自動処理、**When** 手で回すスキルなら承認や質問で止まる箇所に来る、**Then** 人を待たずに次へ進む
3. **Given** 自動処理が作った PR、**When** 本文・タイトル・ブランチ名・コミットメッセージを見る、**Then** 手で回したときと同じテンプレートの形で、同じ検証を通っている
4. **Given** 自動処理が修正を終えた時点、**When** 変更箇所に絞ったテストが失敗する、**Then** PR を作らず、失敗の内容を Issue に書いて終わる
5. **Given** 自動処理が作った PR、**When** その PR の CI が落ちる、**Then** 自動処理が落ちた内容を読んで同じブランチで直し、CI が通るか上限に達するまで繰り返す
6. **Given** 自動処理が終わった Issue、**When** 保守者が Issue を見る、**Then** Issue のコメントから、結果（PR の作成・質問・失敗）と実行の記録への行き方を読める

### User Story 2 - 起動できる人・使えるツール・ターンと時間に上限があり、外部の Issue から起動されない (Priority: P1)

導入先のリポが public でも、書き込み権限の無い人は自動処理を起動できない。起動された自動処理は、許可リストにあるツールだけを使い、ターンと時間の上限で止まる。同じ Issue の自動処理は同時に 1 つしか動かない。

**Why this priority**: 無人のエージェントが、リポへの書き込みとトークンを持って動く。安全策が無い雛形は、public リポの利用者に配れない。User Story 1 と同じ版で届ける。

**Independent Test**: 書き込み権限の無いアカウントで、Issue の起票・コメント・本文の編集をして、自動処理が起動しないことを確かめる。次に、ターンの上限を小さくして起動する。上限で止まり、Issue に報告が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** public な導入先のリポ、**When** 書き込み権限の無い人が Issue を起票する・コメントする・本文に起動を促す文を書く、**Then** 自動処理は起動しない
2. **Given** 起動ラベルの付いた Issue、**When** ラベルを付けた人がリポへの書き込み権限を持たない、**Then** 自動処理は修正を始めずに終わる
3. **Given** 進行中の自動処理、**When** 許可リストに無いツールやコマンドを使おうとする、**Then** その操作は実行されない
4. **Given** 進行中の自動処理、**When** ターンか時間の上限に達する、**Then** 自動処理が止まり、上限で止まったことが Issue に残る
5. **Given** 自動処理が進行中の Issue、**When** 同じ Issue に起動ラベルをもう一度付ける、**Then** 同じ Issue の自動処理は 2 つ同時に動かない
6. **Given** 雛形を導入した直後のリポ、**When** 利用者が既定値を何も変えない、**Then** FR-022〜FR-026 の安全策がすべて有効になっている
7. **Given** 書き込み権限の無い人が、許可の外の操作や secret の表示を求める文を書いた Issue、**When** 保守者が起動ラベルを付ける、**Then** 自動処理はその文に従わない

### User Story 3 - 判断に迷えば Issue に質問を書いて終わり、人が答えると続きから進む (Priority: P2)

Issue の本文だけでは直し方が決まらないとき、自動処理は推測で進めない。Issue に質問を書いて終わる。保守者が答えを書いて起動し直すと、質問と答えを読んで続きを進める。

**Why this priority**: 承認待ちで止まらないことと、推測で誤った PR を作らないことを両立させる。直し方が明らかな Issue では User Story 1 だけで価値が出るので、P2 とする。

**Independent Test**: 直し方が 2 通りあり、本文からは選べない Issue に起動ラベルを付ける。PR ができず、選択肢を並べた質問が Issue に付くことを確かめる。次に、答えを書いて起動し直す。答えに沿った PR ができることを確かめる。

**Acceptance Scenarios**:

1. **Given** 直し方が本文から決まらない Issue、**When** 自動処理が計画を立てる、**Then** 修正を始めず、判断に要る質問を Issue のコメントに書いて終わる
2. **Given** 質問で終わった Issue、**When** Issue の状態を見る、**Then** 人の答えを待っていることが、ラベルかコメントで分かる
3. **Given** 質問で終わった Issue に保守者が答えを書いた状態、**When** 保守者が起動し直す、**Then** 自動処理が前回の計画・質問・答えを読み、同じ質問を繰り返さずに続きを進める
4. **Given** FR-013 の対象に合わない Issue、**When** 起動ラベルを付ける、**Then** 修正を始めず、対象外の理由と、人が手で進める手順を Issue に書いて終わる

### User Story 4 - ボードが手で回したときと同じ規則で動き、人を待つ Issue が一目で分かる (Priority: P2)

自動処理が進めた Issue は、進行の欄で、人が w-quick・w-active・w-pr を回したときと同じ値をたどる。人の対応を待って止まった Issue は、列を動かさず、カードの札が待ちの値に変わる。保守者は、列を眺めるだけで、人の対応を待つ Issue に気づける。

**Why this priority**: pecot はボードで作業の状態を管理する。自動処理だけ進行の欄が動かないと、ボードが実態とずれる。止まった Issue が作業中のものと同じ見た目だと、保守者が気づかず、Issue が放置される。ボードを動かす権限を別に渡す必要があるため、User Story 1 から分けて確かめる。

**Independent Test**: Ready の Issue に起動ラベルを付け、着手の時点と PR 作成の時点の進行の欄を、手で回したときの値と比べる。次に、質問で止まる Issue に起動ラベルを付ける。ボードを開き、Active の列でそのカードの札だけ色が違うことを確かめる。

**Acceptance Scenarios**:

1. **Given** ボードにある Ready の Issue、**When** 自動処理が着手する、**Then** 進行の欄が Active になり、既定の Status は Todo のまま変わらない
2. **Given** 進行中の自動処理、**When** PR を作る、**Then** 進行の欄が In Review になる。既定の Status は、ボードの既定の自動化が In Progress にする
3. **Given** PR が無いまま、質問・失敗・上限で終わった自動処理、**When** ボードを見る、**Then** そのカードは Active の列にあり、既定の Status が待ちの値になっている
4. **Given** 待ちの値になっている Issue、**When** 保守者が起動し直す、**Then** 既定の Status が元の値に戻る。PR が無ければ Todo、PR があれば In Progress だ
5. **Given** PR を作った後、CI を直す回数の上限で終わった自動処理、**When** ボードを見る、**Then** そのカードは In Review の列にあり、既定の Status が待ちの値になっている
6. **Given** 既定の Status に待ちの値が無いボード、**When** 自動処理が待ちの値を書こうとする、**Then** 進行の欄は変えずに、足りない設定を Issue のコメントに書く
7. **Given** ボードを動かす権限が渡されていない導入先のリポ、**When** 起動ラベルを付ける、**Then** 自動処理は修正を始めず、足りない設定と導入手順の場所を Issue に書いて終わる

---

### User Story 5 - 利用者が onboarding の流れでワークフローとトークンを導入できる (Priority: P3)

pecot の利用者が、onboarding の流れの中で自動処理を使うかを選ぶ。使うなら、ワークフローの雛形がリポに置かれ、要るトークンと secret・ラベルの用意が手順として示される。導入の後、設定がそろっているかを確かめられる。

**Why this priority**: User Story 1〜4 は、このリポ自身に手で設定して確かめられる。利用者に届けるには導入手順が要るが、仕組みが動いた後に固める。

**Independent Test**: 自動処理を入れていないリポで onboarding の流れをたどり、示された手順だけで導入する。Issue に起動ラベルを付けて、PR ができることを確かめる。

**Acceptance Scenarios**:

1. **Given** 自動処理を入れていないリポ、**When** 利用者が onboarding の流れで導入を選ぶ、**Then** 雛形がリポに置かれ、利用者の行う設定が FR-031 の順に示される
2. **Given** 導入の手順、**When** トークンに要る権限を読む、**Then** 要る権限が最小の範囲で列挙され、それぞれ何に使うかが書かれている
3. **Given** 導入を終えたリポ、**When** 設定の確認を動かす、**Then** 足りない設定（secret・ラベル・権限）が名前で示される
4. **Given** 導入済みのリポ、**When** pecot-workflow の新しい版で雛形が変わる、**Then** 利用者は、置いた雛形が古いことと更新の手順を知る方法を持つ
5. **Given** onboarding の流れ、**When** 利用者が自動処理を使わないと選ぶ、**Then** 何も置かれず、ほかの onboarding の手順は変わらない

---

### Edge Cases

- 利用者がビューで既定の Status の札を隠しているとき — 待ちの値は書かれるが、カードには出ない。導入の手順に、札を出す設定を書く
- 起動ラベルを、Epic・Tracker・closed の Issue・PR に付けたとき — 修正を始めずに終わり、Issue には理由を書く
- 既にブランチか open の PR がある Issue に起動ラベルを付けたとき — 2 本目のブランチ・PR を作らず、既にあるものを示して終わるか、続きから進む
- 人が手で着手した Active の Issue へ起動ラベルを付けたとき — 人の作業を上書きしない
- 進行の欄が Backlog・Pending・Archived の Issue へ起動ラベルを付けたとき — 修正を始めずに終わり、Ready に置く手順を Issue に書く
- ボードに無い Issue へ起動ラベルを付けたとき — Ready でボードに載せてから、Ready の Issue と同じ手順で進める
- 起動ラベルを付け直したとき — 起動し直しとして扱い、前回の計画とコメントを読む
- 自動処理が進行中に、人が起動ラベルを外したとき — 進行中の実行は止めない。止めるには、実行そのものを取り消す
- 複数の Issue へ同時に起動ラベルを付けたとき — Issue ごとに独立して動き、互いのブランチに触れない
- 修正の途中でターン・時間の上限に達したとき — 途中のブランチは残り、PR は作られず、Issue に止まった場所が残る
- 導入先のリポの pre-commit・commit-msg の検証が落ちたとき — 検証を迂回せず、直せなければ Issue に書いて終わる
- 自動処理が作った PR の CI が、直す回数の上限まで落ち続けたとき — PR を残し、落ちているチェックを Issue に書いて終わる
- CI の失敗が変更と関係のないとき（不安定なテスト・外部の障害） — コードを変えて直そうとせず、理由を Issue に書いて終わる
- 自動処理が CI を直している間に、人が同じブランチへ push したとき — 人のコミットを上書きしない
- Issue の本文や、書き込み権限の無い人のコメントに、エージェントへの指示（secret の表示・ほかのリポへの push など）が書かれているとき — 従わない
- トークンの期限切れ・権限の不足で、途中の操作を拒否されたとき — 拒否された操作の名前を Issue に書いて終わる。Issue にも書けないときは、実行の記録に残す
- 変更がほかのリポにまたがるとき — 導入先のリポの外を変更しない。対象外として Issue に書いて終わる
- モデルの利用に要る認証（API キーなど）が無い・無効のとき — 起動の直後に失敗し、実行の記録から原因が分かる
- GitHub Enterprise Server のリポ — 雛形が使える範囲と使えない範囲を、導入手順に書く

## Requirements *(mandatory)*

### Functional Requirements

**手順 — 承認を待たずに Issue から PR まで進める**

| ID | 要件 |
|---|---|
| FR-001 | 導入先のリポで、open の Issue に起動ラベルが付いたとき、自動処理が 1 回始まらなければならない |
| FR-002 | 自動処理は、既にある Issue を起点に、ブランチの作成・計画の投稿・修正・変更箇所に絞ったテスト・コミット・push・PR の作成・CI の失敗の修正までを、人の操作を待たずに進めなければならない |
| FR-003 | 自動処理の手順は、pecot-workflow が配布するスキルとして持たなければならない。スキルは新しく 1 つ足す。手で回すスキル（w-quick・w-active・w-pr）の文と承認の箇所は変えない |
| FR-004 | 自動処理が作る Issue のコメント・ブランチ名・コミット・PR は、手で回したときと同じテンプレートと CLI の検証を通らなければならない。検証を迂回してはならない |
| FR-005 | 自動処理は、修正の前に計画を Issue に投稿しなければならない。計画は人の承認を待たないが、後から人が読める形で残る |
| FR-006 | 自動処理は、変更箇所に絞ったテストと、リポの commit 前の検証を通してから PR を作らなければならない。通らないまま PR を作ってはならない |
| FR-007 | 自動処理は、作った PR の CI が通ったところで終わる。PR のマージ・Issue のクローズ・リリース・レビュー指摘への対応を行ってはならない |
| FR-008 | 自動処理は、終わるときに必ず、結果を Issue のコメントに残さなければならない。結果は、PR の CI が通った・質問で止まった・対象外で止まった・失敗した・上限で止まった、のどれかである |
| FR-035 | 自動処理は、作った PR の CI が落ちたとき、落ちた内容を読んで同じブランチで直し、push し直さなければならない。人の操作を待たない |
| FR-036 | CI の失敗を直す回数は上限を持たなければならない。上限は既定値を持ち、利用者が変えられる。上限に達したら、PR を残したまま、落ちているチェックを Issue に書いて終わる |
| FR-037 | CI の失敗を直す対象は、自動処理が作った PR だけでなければならない。人が作った PR では動かない |
| FR-009 | 自動処理の変更は、導入先のリポの中に限らなければならない |

**判断に迷うとき**

| ID | 要件 |
|---|---|
| FR-010 | 自動処理は、Issue の本文と既にあるコメントから直し方が決まらないとき、推測で修正を進めてはならない。判断に要る質問を Issue に書いて終わる |
| FR-011 | 質問で終わった Issue は、人の答えを待っていることが Issue とボードの上で分かり、人が答えた後に起動し直せなければならない。起動し直す操作は、起動ラベルの付け直しだけとする |
| FR-038 | 自動処理は、どの終わり方でも、終わるときに起動ラベルを外さなければならない |
| FR-012 | 起動し直された自動処理は、前回の計画・質問・人の答え・既にあるブランチを読み、続きから進めなければならない。同じ Issue にブランチと PR を重ねて作ってはならない |
| FR-013 | 自動処理は、対象に合わない Issue では修正を始めず、理由を Issue に書いて終わらなければならない。対象は、進行の欄が Ready の Issue・ボードに無い Issue・自動処理が止めた Issue の起動し直しに限る。ボードに無い Issue は、Ready でボードに載せてから進める。Epic・Tracker・closed の Issue は対象に合わない。進行の欄が Backlog・Pending・Archived の Issue も合わない。複数のリポにまたがる変更と、小さなタスクの範囲を超える変更も合わない |
| FR-014 | 「小さなタスクの範囲」の目安は、スキルに書かれていなければならない。範囲を超えるかは自動処理が計画の時点で判断する |

**起動**

| ID | 要件 |
|---|---|
| FR-015 | pecot-workflow は、ラベルを契機に自動処理を起こす GitHub Actions のワークフローの雛形を配布しなければならない |
| FR-016 | 雛形は、pecot-workflow のプラグインを実行環境に入れ、FR-003 のスキルを起動しなければならない |
| FR-017 | 起動ラベルの名前は既定値を持ち、利用者が変えられなければならない |

**権限**

| ID | 要件 |
|---|---|
| FR-018 | 自動処理は、進行の欄を、手で回したときと同じ規則で動かさなければならない。着手で Active にし、PR の作成で In Review にする |
| FR-039 | 自動処理は、人の対応を待って終わるとき、既定の Status に待ちの値を書かなければならない。対象の終わり方は、質問・失敗・上限である。進行の欄は変えない。PR が無ければ Active のまま、PR があれば In Review のままにする |
| FR-040 | 起動し直された自動処理は、既定の Status が待ちの値なら元の値に戻さなければならない。PR の無い Issue では Todo に、PR のある Issue では In Progress に戻す |
| FR-041 | 自動処理は、FR-039 と FR-040 のほかに、既定の Status を書いてはならない。着手・PR の作成・クローズの時点は、ボードの既定の自動化に任せる |
| FR-042 | pecot は、既定の Status に待ちの値を足せなければならない。新しく作るボードには作成のときに足し、既にあるボードには利用者が 1 つの操作で足せる。足すときに、カードに入っている既存の値を消してはならない |
| FR-043 | 待ちの値は、既定の 3 つの値と違う色を持たなければならない |
| FR-019 | ボードを動かすためのトークンの渡し方は 1 つに決め、導入手順に書かなければならない。要る権限は最小の範囲で列挙する |
| FR-020 | 自動処理に渡すトークンと secret は、Issue・PR・コメント・コミットに出力されてはならない |
| FR-021 | ボードを動かす権限が無いとき、自動処理は修正を始めずに終わり、足りない設定を Issue に書かなければならない |

| FR-023 | fork からの操作と、書き込み権限の無い人の操作は、public リポでも自動処理を起動してはならない |

| FR-025 | 自動処理は、1 回の実行のターンと時間に上限を持たなければならない。上限は既定値を持ち、利用者が変えられる |
| FR-026 | 同じ Issue の自動処理は、同時に 1 つしか動いてはならない |
| FR-027 | FR-022〜FR-026 の安全策は、雛形を導入して何も変えない状態で、すべて有効でなければならない |

| FR-029 | 自動処理は、main などの保護されたブランチへ直接 push してはならない。変更は自動処理のブランチと PR だけで届ける |

| FR-032 | 利用者は、導入の後、自動処理に要る設定がそろっているかを確かめられなければならない。確かめる対象は、secret・ラベル・権限・待ちの値・ボードの既定の自動化が有効かである。足りない設定は名前で示す |

### Key Entities

| 名前 | 内容 |
|---|---|
| 起動ラベル | 付けると自動処理が始まるラベル。名前の既定値を持つ |
| 自動処理の実行 | 1 つの Issue に対する 1 回の実行。起動した人・対象の Issue・結果（PR・質問・対象外・失敗・上限）を持つ |
| 結果のコメント | 自動処理が終わるときに Issue に残すコメント。結果と、実行の記録への行き方を持つ |
| 質問のコメント | 判断に迷ったときに Issue に残すコメント。人の答えと対になり、起動し直しのときに読まれる |
| ワークフローの雛形 | 導入先のリポに置く、自動処理を起こす定義。起動者の制限・許可リスト・上限・同時実行の既定値を含む |
| ボード用のトークン | 進行の欄と既定の Status を動かすために、導入先のリポに登録する認証情報 |
| 待ちの値 | 既定の Status に足す値。人の対応を待って止まった Issue に付き、起動し直すと外れる |

## Success Criteria *(mandatory)*

### Measurable Outcomes

| ID | 成果 |
|---|---|
| SC-001 | 直し方が本文から決まるバグか小さなタスクの Issue で、保守者の操作がラベルを付ける 1 回だけで、CI の通った PR ができる |
| SC-002 | 自動処理が作った PR・コメント・ブランチ名・コミットは、手で回したときに通す検証を 100% 通る |
| SC-003 | 自動処理は、どの終わり方でも、結果のコメントを Issue に残す。結果の残らない実行が 0 件である |
| SC-004 | 書き込み権限の無いアカウントからの操作（起票・コメント・本文の編集・fork からの PR）で、自動処理が修正を始める回数が 0 回である |
| SC-005 | 上限を超えて動き続ける実行が 0 件である。上限に達した実行は、上限で止まったことが Issue から分かる |
| SC-010 | CI を直す回数が上限を超える実行が 0 件である。上限に達した PR は、落ちているチェックが Issue から分かる |
| SC-006 | 自動処理が進めた Issue の進行の欄は、着手・PR 作成のどの時点でも、手で回したときの値と一致する |
| SC-011 | 人の対応を待って止まった Issue は、ボードを開いて列を見るだけで、同じ列のほかのカードと色で区別できる。区別にカードを開く操作が要らない |
| SC-007 | 直し方が本文から決まらない Issue では、PR ではなく質問が付く。人が答えて起動し直すと、同じ質問を繰り返さずに PR ができる |
| SC-008 | pecot を設定済みのリポで、利用者が導入の手順だけを読んで、30 分以内に最初の自動処理を起動できる |
| SC-009 | 1 ファイルの修正で、ラベルを付けてから PR ができるまでに、人が待たされる操作が無い |

## Assumptions

- 無人の実行の置き場は GitHub Actions で、エージェントの実行には claude-code-action を使う。claude.ai/code のクラウドセッションは、pecot CLI が動かないので対象にしない
- 自動処理の起点は、既にある Issue である。Issue の起票そのもの（w-quick の起票の部分）は自動処理に含めない。保守者か報告者が先に起票する
- 起票の時点で Issue の種類（Epic・Task・Bug）を判断してボードに載せる仕組みは、この spec の対象にしない。別の Epic で扱う
- 起動の契機はラベルだけだ。コメントでの呼び出し（メンション）は、この spec の対象にしない
- 自動処理は、作った PR の CI が通るところで終わる。PR のレビュー指摘への対応（w-revise）とマージ（w-merge）は、この spec の対象にしない
- CI の結果を受けて自動処理を続ける仕組み（同じ実行で待つか、CI の結果で起こし直すか）は、plan の research で決める
- 対象は、導入先のリポ 1 つで完結する変更である。複数のリポにまたがる変更と Epic の分解は対象にしない
- モデルの利用に要る認証（API キーなど）は、利用者が用意して導入先のリポの secret に登録する。課金は利用者の契約による
- 待ちの値の名前と色は、仮に `Waiting` と赤とする。plan で確定する
- ボードの既定の自動化（追加で Todo、PR の連携で In Progress、クローズで Done）は、有効なままであることを前提にする。無効のときは、導入の確認が知らせる
- 既定の Status への値の追加と、ビューの表示項目の設定は、GitHub の API でできる。列にするフィールドと既定の自動化の中身は、API で変えられない
- 止まった理由（質問・失敗・上限）は、結果のコメントで示す。理由ごとのラベルは足さない
- ボードを動かすトークンは、利用者が発行して secret に登録する。発行の方式は、fine-grained PAT と GitHub App を plan の research で比べて決める
- ターン・時間・許可リストの既定値の具体的な数と中身は、plan の research で、このリポでの試行をもとに決める
- 「小さなタスクの範囲」の目安は、w-quick が対象とする大きさ（1 ファイルの修正・小さなバグ修正）を引き継ぐ
- 自動処理は、導入先のリポで、テストと commit 前の検証が GitHub Actions のランナーの上で動くことを前提にする。動かす準備（依存の install など）は、雛形に利用者が足す
- 最初に確かめる導入先は、このリポ（pecotcraft/pecot）である。public リポなので、外部から起動されないことをここで確かめる
- GitHub Copilot CLI を無人で動かす形は、この spec の対象にしない。スキルの文は、Claude Code 固有のツール名に依らない書き方を保つ
