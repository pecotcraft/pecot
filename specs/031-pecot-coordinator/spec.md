# Feature Specification: pecot-coordinator プラグインを作り、claude.ai のプロジェクトの coordinator とクラウドのスレッドが pecot の流れで動く

**Feature Branch**: `feat/breakdown-pecot-coordinator/756`

**Created**: 2026-11-26

**Status**: Draft

**Input**: Epic #755 の本文と、分解のスレッドで利用者が決めたこと

## 背景

| 項目 | 今の状態 |
|---|---|
| coordinator の判断と手順 | 利用者が claude.ai のプロジェクトの設定に書いたプロジェクト指示の文にしか無い。版の管理もテストも無い |
| 既存のプラグイン | pecot-workflow・pecot-visual・pecot-tools は、どれも直下に `bin/` を持つ。claude.ai の文書は、直下の `bin/` を持つプラグインを Chat と Cowork が丸ごと拒むと書く |
| クラウドのスレッドの VM | GitHub の GraphQL はプロキシで 403 になる。REST はセッションのリポだけに縛られ、Projects・組織のパス・ブランチの作成と削除は 403 になる。通った REST の本文には「Generated by Claude Code」が足される（2026-11-26） |
| GitHub 公式のリモート MCP | claude.ai のサーバーから GitHub へ直接つなぐので、クラウドのスレッドでも動く。Issue・コメント・sub-issue・ブランチの作成・commit・PR を、本文を変えずに書けた（2026-11-26） |
| GitHub 公式の MCP の手 | ボードの書き込み・Issue・sub-issue・コメント・ブランチの作成・PR の作成と更新の手がある。blocked-by は Insiders の試験中のツールだけにある。Development 欄のつながり・ブランチの削除・リリースの作成・ボードの欄の作成と直し・リポとボードのつなぎ込み・アーカイブした item の戻し・スタック PR の登録・非同期のマージ・Actions の secret と variable の名前の一覧は、手が無い（github/github-mcp-server の 2026-11-25 の commit `7edc2dd`） |
| pecot-workflow の GitHub の読み書き | CLI が GraphQL と REST を直に呼ぶ。MCP サーバは CLI のコマンドをすべてツールとして出すので、GitHub Actions だけで使うコマンド（`auto_gate`・`auto_start`・`auto_finish`・`review_finish`・`board_sync`・`tracker_sync`）もエージェントのツールに並ぶ。Actions はこれらを CLI で呼び、Actions の中では GraphQL が通る |

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| coordinator | claude.ai のプロジェクトのプロジェクトチャットで利用者と話し、スレッドを起動して Issue を割り振る Claude |
| スレッド | coordinator が起動し、Issue 1 件を受け持つ Claude。手元の端末で動く RC のスレッドと、クラウドの VM で動くクラウドのスレッドがある |
| 作業場所 | スレッドが作業する場所。RC の wt（`wt1`〜`wt12`）と、クラウドのスレッド |
| プロジェクト指示 | 利用者が claude.ai のプロジェクトの設定に書く文 |
| GitHub 公式の MCP | GitHub が配る MCP サーバ。claude.ai のコネクタでつなぐリモートのものを、リモート MCP と呼ぶ |
| 既存のプラグイン | pecot-workflow・pecot-visual・pecot-tools の 3 つ |
| Actions だけで動く処理 | GitHub Actions のワークフローが起こし、エージェントのスレッドからは使わない処理。w-review・w-handoff・自動処理・ボードの同期・アラートの同期 |
| 手の無い操作 | pecot-workflow が今行っていて、GitHub 公式の MCP にツールが無い操作 |
| Actions のプロジェクト | pecot の GitHub Actions のテンプレートと、そこで動くスクリプトをまとめる新しいプロジェクト。AI と無関係で、AI エージェントに入れるプラグインではない。pecot-workflow か pecot-coordinator を使うリポには、導入が必須 |
| 配布性 | このリポ以外のプロジェクトにも、固有の値を書き換えずに配れること |

## Clarifications

### Session 2026-11-26

- Q: npm の `@pecot/workflow-mcp@latest` を npx で動かす古い雛形が残る利用者のリポを、どう移すか → A: 破壊的変更の版で一度に切り替える。古い雛形は pecot-workflow の確かめが見つけ、エージェントが `uses:` で呼ぶ新しいワークフローに書き換える（FR-029・FR-030）
- Q: プラグインの MCP をどう起動し、CLI の入口を残すか → A: `bin/` をなくし、npm で公開した版を `npx` で起動する。CLI の入口は持たず、MCP のツールだけで公開する。constitution の原則 II もそれに合わせて直す（FR-007）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロジェクト指示とプラグインの線が引かれる (Priority: P1)

保守者は、今のプロジェクト指示の文の 1 つずつについて、プラグインに移すもの（pecot 共通の判断と手順）と、プロジェクト指示に残すもの（プロジェクト固有の値）のどちらかを、一覧で読める。

**Why this priority**: coordinator のスキルに何を書くかが、この線で決まる。線が無いまま書くと、固有の値がスキルに入り、配布性を失う。

**Independent Test**: 今のプロジェクト指示の全文を一覧に写し、行き先の無い文が無いこと、行き先がプロジェクト指示の文に判断や手順が無いことを確かめる。

**Acceptance Scenarios**:

1. **Given** 今のプロジェクト指示がある、**When** 保守者が一覧を読む、**Then** すべての文に行き先と理由が書いてある
2. **Given** 行き先がプラグインの文がある、**When** 保守者が文を読む、**Then** このリポや利用者に固有の名前が入っていない

---

### User Story 2 - GitHub 公式の MCP の試していない手が、実物で分かる (Priority: P1)

保守者は、スレッドが使う pecot-workflow の読み書きのうち、GitHub 公式の MCP に手があるのに試していないもの（ボードの書き込み・Insiders の blocked-by・担当者など）が、今と同じ形に書けるかを、試した記録で読める。
手の無い操作を行う Actions のワークフローが使う token が、ボード・Development 欄・スタック PR に届くかも読める。

**Why this priority**: 作り替え（US6）の形がこの結果で決まる。書けない手があれば、Actions のワークフローに回す操作が増える。

**Independent Test**: 検証用のリポとボードで、リモート MCP だけで Issue 1 件を起票から閉じるまで動かし、pecot-workflow で同じ操作をした Issue とボードの欄を比べる。

**Acceptance Scenarios**:

1. **Given** 試していない手の一覧がある、**When** 保守者が記録を読む、**Then** 手ごとに「今と同じ形に書ける」「書けない（違い）」が、試した操作と結果で書いてある
2. **Given** Actions のワークフローの token、**When** 保守者が記録を読む、**Then** ボード・Development 欄・スタック PR のそれぞれに書けたかが書いてある

---

### User Story 3 - claude.ai への配り方と、読まれるかが分かる (Priority: P1)

保守者は、プラグインを claude.ai に入れる経路と、入れたプラグインが coordinator とクラウドのスレッドで読まれるかを、試した記録で読める。

**Why this priority**: 文書には、claude.ai のプロジェクトとクラウドのスレッドでプラグインが読まれるかが書いていない。読まれないなら、US4・US7・US8 の形が変わる。

**Independent Test**: スキルを 1 つだけ持つ試しのプラグインを claude.ai に入れ、coordinator とクラウドのスレッドがそのスキルを使うかを見る。

**Acceptance Scenarios**:

1. **Given** 試しのプラグイン、**When** 保守者が claude.ai に入れる、**Then** 経路ごとに入ったか、止まった文が記録してある
2. **Given** 入れたプラグインの版を上げた、**When** 次のスレッドが起動する、**Then** 新しい版が使われるかが記録してある

---

### User Story 4 - 既存のプラグインを claude.ai に入れられる (Priority: P1)

利用者は、既存の 3 つのプラグインを claude.ai に入れられる。3 つは同じ形で、直下に `bin/` を持たない。Claude Code での動きは今と変わらない。GitHub Copilot CLI でも今と変わらないが、pecot-visual の編集の後のフックだけは動かなくなる。

**Why this priority**: pecot-workflow が claude.ai に載らないと、クラウドのスレッドは pecot-workflow のスキルを使えない。

**Independent Test**: 直した 3 つを claude.ai に入れて拒まれないこと、Claude Code に入れて MCP とフックが今どおり動くことを確かめる。

**Acceptance Scenarios**:

1. **Given** 直したプラグイン、**When** 利用者が claude.ai に入れる、**Then** 拒まれない
2. **Given** 直したプラグイン、**When** 利用者が Claude Code に入れる、**Then** MCP とフックが今どおり動き、スキルと文書から PATH のコマンドを呼ぶ箇所が残っていない

---

### User Story 5 - Actions のテンプレートとスクリプトが、AI と無関係なプロジェクトにまとまる (Priority: P2)

pecot のワークフローに要るもののうち、GitHub Actions のテンプレートと、そこで動くスクリプト（自動処理・ボードの同期・アラートの同期・レビューと引き継ぎの後処理、手の無い操作）は、プラグインとは別の新しいプロジェクトにまとまる。このプロジェクトは AI と無関係で、スキルも MCP も持たない。
pecot-workflow か pecot-coordinator を使うリポには、このプロジェクトの導入が必須になる。導入する先は利用者のリポで、AI エージェントではない。
pecot-workflow のプラグインには、エージェントが使うもの（スキルと、スキルが使う MCP のツール）だけが残る。Actions のワークフローは今どおり動く。

**Why this priority**: 今は Actions だけで使うコマンドも pecot-workflow の MCP のツールに並び、エージェントが使う流れとそうでない流れの境目が分からない。境目が無いと作り替えの範囲を誤る。US6 の範囲は、この分け方で決まる。

**Independent Test**: pecot-workflow の MCP のツールの一覧に Actions だけで使うコマンドが無いこと、新しいプロジェクトのテンプレートとスクリプトで Actions のワークフローが今どおり成功することを確かめる。

**Acceptance Scenarios**:

1. **Given** pecot-workflow の MCP サーバ、**When** エージェントがツールの一覧を読む、**Then** `auto_*`・`review_finish`・`board_sync`・`tracker_sync` が無い
2. **Given** Actions だけで動く処理、**When** 新しいプロジェクトのテンプレートとスクリプトでワークフローが起こす、**Then** 今と同じ結果になる
3. **Given** 新しいプロジェクト、**When** 保守者が中身を読む、**Then** スキル・MCP・エージェントに向けた文が無い

---

### User Story 6 - スレッドの GitHub の読み書きが、GitHub 公式の MCP を通る (Priority: P2)

開発者が手元の Claude Code・GitHub Copilot CLI・クラウドのスレッドのどこで pecot の流れを進めても、GitHub の読み書きは GitHub 公式の MCP のツールを通る。
スキルが呼ぶ pecot-workflow のツールは GitHub に触らず、計算だけを行う。
手の無い操作は、スキルが Actions のワークフローを起動して行い、利用者の手作業は増えない。
Issue・PR の本文とボードの欄は今と同じ形で、今ある機能は落ちない。

**Why this priority**: クラウドの VM では、ボードに届くのが GitHub 公式の MCP だけだ。pecot-workflow が GitHub を直に呼ぶ限り、クラウドのスレッドで pecot の流れが回らない。

**Independent Test**: 検証用のリポとボードで、Issue 1 件の流れ（起票から片付けまで）を手元とクラウドのスレッドで流し、本文とボードの欄が今の pecot-workflow で流したものと同じになることを確かめる。

**Acceptance Scenarios**:

1. **Given** クラウドのスレッドで Issue に着手した、**When** スキルに従って起票・コメント・ボードの移動・PR の作成を行う、**Then** pecot-workflow のツールが組み立てた本文と値が GitHub 公式の MCP で書かれ、今と同じ形になる
2. **Given** 手元の RC のスレッド、**When** 同じ操作をする、**Then** クラウドのスレッドと同じツールが使われる
3. **Given** 手の無い操作（Development 欄・スタック PR の登録・ボードの欄の作成など）の場面、**When** スキルが進める、**Then** スキルが Actions のワークフローを起動して結果を読み、利用者に起動を頼まない
4. **Given** 利用者がリリースを頼んだ、**When** エージェントが進める、**Then** エージェントがリリースのワークフローを起動する
5. **Given** PR がマージされた、**When** 片付けに進む、**Then** pecot はリモートのブランチを消さず、リポの自動で消す設定に任せる

---

### User Story 7 - coordinator がプラグインのスキルで割り振る (Priority: P2)

利用者は、claude.ai のプロジェクトに pecot-coordinator を入れ、プロジェクト指示には固有の値だけを書く。coordinator はスキルに従い、Ready で未担当の Issue を空いた作業場所に割り振ってスレッドを起動し、利用者に上げる判断の範囲を守る。

**Why this priority**: Epic の目的そのものだが、US1・US3 の結果で形が決まる。

**Independent Test**: 検証用のプロジェクトにプラグインを入れ、値だけのプロジェクト指示で「次の Issue を始めて」と頼み、割り振りとスレッドの起動を確かめる。

**Acceptance Scenarios**:

1. **Given** Ready で未担当の Issue と空いた作業場所がある、**When** 利用者が次の Issue を頼む、**Then** coordinator は Issue を 1 つの作業場所だけに割り振り、スレッドを起動する
2. **Given** 小さな判断（レビュー指摘の採否・push・再開）、**When** coordinator が判断する、**Then** 利用者に聞かずに進める
3. **Given** 仕様を変える判断・マージ・値の戻らない削除、**When** coordinator が判断に来る、**Then** 利用者に上げる

---

### User Story 8 - クラウドのスレッドが実装まで受け持ち、このリポが移る (Priority: P3)

開発者は、クラウドのスレッドに Issue の着手から実装・PR・マージ待ちまでを任せられる。pecot-workflow 自身を直す Issue の sandbox への確かめも、クラウドの VM の中から流せる。
このリポのプロジェクト指示は、固有の値だけに書き直される。

**Why this priority**: US4〜US7 が揃ってから確かめられる。

**Independent Test**: coordinator が起動したクラウドのスレッドに pecot-workflow を直す Issue を進めさせ、sandbox への確かめを VM の中から最後まで流す。

**Acceptance Scenarios**:

1. **Given** クラウドのスレッドに割り振った Issue、**When** スレッドが進める、**Then** 着手から PR のマージ待ちまで、RC のスレッドと同じ流れで進む
2. **Given** pecot-workflow を直す Issue、**When** sandbox への確かめを流す、**Then** VM の中から最後まで流れる
3. **Given** 書き直したこのリポのプロジェクト指示、**When** coordinator に割り振りを頼む、**Then** 書き直す前と同じ判断になる

---

### Edge Cases

- プラグインのスキルとプロジェクト指示が食い違うとき、coordinator はプロジェクト指示を優先し、食い違いを利用者に伝える
- リモート MCP のつなぎ先が読み取りだけのとき、スレッドは書き込みの前にそれと分かり、何をつなげばよいかを利用者に示す
- RC のスレッドとクラウドのスレッドが同じプロジェクトに混ざるとき、同じ Issue が両方に割り振られない
- Actions のワークフローが失敗するか終わらないとき、スキルは止まり、実行の URL を利用者に示す
- Insiders の blocked-by のツールの名前か形が変わったとき、スキルが止まり、利用者に伝える
- マージせずに閉じた PR のブランチは、自動で消す設定では残る。sandbox の確かめのブランチは名前の形で見分けられ、ほかの確かめを邪魔しない
- GitHub が 5xx を返したとき、書き込みが済んでいることがある。やり直す前に、書いたものがあるかを読んで確かめる
- claude.ai に入れたプラグインの版と、このリポの版がずれたとき、利用者が気づける
- 古い雛形が残ったまま新しい版に上がったリポでは、Actions のワークフローが失敗する。pecot-workflow の確かめが古い雛形を見つけ、書き換えを案内する前に、失敗した実行の URL から原因が古い雛形だと分かる

## Requirements *(mandatory)*

### Functional Requirements

#### 検証

- **FR-001**: 保守者は、今のプロジェクト指示のすべての文について、行き先（プラグインかプロジェクト指示か）と理由の一覧を持たなければならない
- **FR-002**: 保守者は、スレッドが使う読み書きのうち GitHub 公式の MCP に手があるものについて、今と同じ形に書けるかの試した記録を持たなければならない
- **FR-003**: 保守者は、手の無い操作を行う Actions のワークフローの token が、ボード・Development 欄・スタック PR に届くかの記録を持たなければならない
- **FR-004**: 保守者は、claude.ai へプラグインを入れる経路ごとの結果と、入れたプラグインが coordinator とクラウドのスレッドで読まれるかの記録を持たなければならない
- **FR-005**: 検証の書き込みは、検証用のリポとボードだけに行い、このリポとボードには書き込んではならない
- **FR-006**: 検証の記録には、読んだ文書と版・日付、試した操作と結果を添えなければならない

#### 既存のプラグイン

- **FR-007**: 既存の 3 つのプラグインは、同じ形で、直下に `bin/` を持ってはならない。MCP のサーバは npm で公開した版を起動し、同じ機能の CLI の入口を持ってはならない
- **FR-008**: 既存の 3 つのプラグインは、Claude Code と GitHub Copilot CLI で、MCP とフックが今どおり動かなければならない。
  ただし、pecot-visual の PostToolUse のフック（MCP のツールを呼ぶフック）は Claude Code だけで動き、Copilot CLI では動かなくてよい（2026-11-26 に利用者が許した）
- **FR-009**: 既存の 3 つのプラグインのスキルと文書は、PATH に載ったコマンドを前提にしてはならない

#### pecot-workflow

- **FR-010**: Actions のテンプレートと、Actions だけで動くスクリプトは、Actions のプロジェクトに置かなければならない。Actions のプロジェクトは、スキル・MCP・エージェントに向けたものを持ってはならず、AI エージェントに入れるプラグインとして配ってはならない。
  pecot-workflow と pecot-coordinator は、Actions のプロジェクトが利用者のリポに導入されていることを前提にし、導入されていなければ、それと分かる案内を出さなければならない
  Actions のプロジェクトは、このリポのルート直下の `actions/` に置く。利用者のリポへは GitHub Actions の action として配り、利用者のリポは `uses:` で版のタグ（`pecot-actions/v<版>`）を指して呼ぶ短いワークフローだけを持つ。スクリプトは action に同梱し、npm を通して配らない
- **FR-011**: pecot-workflow の MCP サーバは、エージェントが使うコマンドだけをツールとして出さなければならない。スキルが呼ぶチェックのツール（FR-014）は、pecot-workflow の MCP のツールとして残す
- **FR-012**: Actions だけで動く処理は、Actions のプロジェクトへ移した後も、移す前と同じ結果にならなければならない。Actions の中では GraphQL・REST を今どおり使ってよい
- **FR-013**: スレッド（手元の Claude Code・GitHub Copilot CLI・クラウド）の GitHub の読み書きは、GitHub 公式の MCP のツールで行わなければならない。クラウドの VM のプロキシを通る REST と GraphQL を使ってはならない
- **FR-014**: スキルが呼ぶ pecot-workflow のツールは、GitHub に読み書きしてはならない。1 つの操作でまとめて書くものごとに、1 つのチェックのツールを置く。書く手は GitHub 公式の MCP のツールか、`pecot-github-ops.yml` の operation である。
  チェックのツールは、書く手に渡すのと同じ値と、公式の MCP で読んだ結果を受け取り、pecot の決まり（テンプレート・題の番号・前提・ボードの欄）に合うかだけを返さなければならない。
  値は組み立てず、テンプレートの frontmatter を、書く公式のツールの引数の名前にそろえる
- **FR-015**: スキルは、pecot-workflow のツールで計算した結果を、GitHub 公式の MCP のどのツールで何のために書くかを示さなければならない。ツールの基本的な使い方は書いてはならない
- **FR-016**: 手の無い操作は、Actions のプロジェクトのワークフローの中で行わなければならない。スキルは、そのワークフローを GitHub 公式の MCP で起動して結果を読み、利用者に起動を頼んではならない
- **FR-017**: リリースは、利用者に頼まれたらエージェントがリリースのワークフローを起動して作らなければならない
- **FR-018**: pecot はリモートのブランチを消してはならない。マージした PR のブランチは、リポの「head ブランチを自動で消す」設定に任せる。オンボーディングと試験環境の手順は、この設定が有効かを確かめなければならない
- **FR-019**: blocked-by の読み書きは、GitHub 公式の MCP の `issue_dependency_read`・`issue_dependency_write` で行わなければならない。features の `issue_dependencies` で有効にし、結果が CSV になる Insiders は使わない
- **FR-020**: 作り替えた後も、Issue・PR・コメントの本文とボードの pecot の欄は、今と同じ形でなければならない
- **FR-021**: 作り替えで、今ある機能を落としてはならない。FR-018 のブランチの削除だけを除く
- **FR-022**: 試験環境を揃える・片付ける手順は、クラウドのスレッドから行えなければならない

#### pecot-coordinator

- **FR-023**: pecot-coordinator の部品は、スキルとマニフェストだけでなければならない。MCP のサーバ・フック・`bin/` を持ってはならない。nx project のファイルとテストは置いてよい
- **FR-024**: pecot-coordinator のスキルは、coordinator の判断と手順（割り振り・スレッドの起動・利用者に上げる判断の範囲）を持たなければならない
- **FR-025**: pecot-coordinator のスキルは、プロジェクト固有の値を持ってはならない。固有の値は、プロジェクト指示から読まなければならない
- **FR-026**: pecot-coordinator は、プロジェクト指示に書く値の一覧と例を利用者に示さなければならない
- **FR-027**: coordinator は、RC の wt とクラウドのスレッドを作業場所として扱い、同じ Issue を 2 つの作業場所に割り振ってはならない
- **FR-028**: クラウドのスレッドは、pecot-coordinator に別のスキルを持たせず、pecot-workflow のスキルで流れを進めなければならない

#### 移行

- **FR-029**: Actions のスクリプトを `actions/` へ移す版は、破壊的変更の版として一度で切り替えなければならない。npm の package から、Actions だけで使う処理を消す
- **FR-030**: pecot-workflow の確かめ（オンボーディング・診断）は、npm の package を npx で呼ぶ古い雛形が利用者のリポにあることを見つけなければならない。見つけたら、エージェントが `uses:` で `actions/` を呼ぶワークフローに書き換え、利用者に手作業を頼んではならない

## Assumptions

- 検証（US1〜US3）は実装の前のフェーズに置き、結果で後続のフェーズの形を見直す
- 検証用のリポは pecotcraft/pecot-sandbox、ボードは「pecot sandbox」を使い、CONTRIBUTING の試験環境の手順に従う
- このリポは public なので、組織の sync は使えない。個人の Add marketplace の経路を第一に試す
- リリースの判断は、今どおり利用者が行う。この Epic で変えるのは、エージェントがワークフローを起動する点だけ

- プラグインと Actions のプロジェクトは、このリポの monorepo の nx project として置く。ルート直下に `actions/` を足すことは、2026-11-26 に利用者が許した（`.claude/rules/repo-root-layout.md` の一覧と hook を同じ変更で直す）
- 利用者のリポの `uses:` のタグの更新は、GitHub の Dependabot（github-actions）に任せる。タグは `pecot-actions/v<版>` の形にする。Dependabot は `<名前>/v<版>` の形のタグを版として読むが、`<名前>-v<版>` の形は読まない（plan の research）
