# Feature Specification: pecot-coordinator プラグインを作り、claude.ai のプロジェクトの coordinator とクラウドのスレッドが pecot の流れで動く

**Feature Branch**: `feat/breakdown-pecot-coordinator/756`

**Created**: 2026-11-25

**Status**: Draft

**Input**: Epic pecotcraft/pecot#755。分解のタスクは #756。

## 背景

| 場面 | 今の姿 |
|---|---|
| coordinator の判断と手順 | Issue 1 件の流れ・空き wt への割り振り・利用者に上げる判断の範囲は、利用者が claude.ai のプロジェクトの設定に書いたプロジェクト指示にだけある。配布物ではないので、版の管理とテストが無い |
| pecot のプラグインを claude.ai に載せる | pecot-workflow・pecot-visual・pecot-tools のどれも、claude.ai の制約に引っかかって載らない（利用者が確かめた）。3 つとも、プラグインの直下に `bin/` を持つ |
| claude.ai の決まり（公式の文書） | 直下に `bin/` を持つプラグインは、claude.ai の Chat と Cowork が「Can't be installed」として、プラグインごと拒む。Claude Code は読み込む。文書は、実行ファイルを `scripts/` などへ移し、`${CLAUDE_PLUGIN_ROOT}/scripts/<name>` で参照するよう案内している。組織の sync では、拒まれたプラグインだけが外れ、marketplace のほかのプラグインは同期される |
| claude.ai で読まれる部品（公式の文書） | Chat で読まれるのはスキル（コマンドはスキルとして）と、固定の URL のリモート MCP（コネクタとして）。エージェント・フック・手元で起動する MCP は無視される |
| 文書に無いこと | Claude Code on the web（クラウドのスレッド）と、claude.ai のプロジェクトでプラグインが読まれるかは、どの文書にも書いていない |
| 配る経路（公式の文書） | 個人は Customize > Plugins の Add marketplace（公開の GitHub リポも可）か Upload plugin で足せる。組織の sync は、github.com の marketplace のリポが private か internal であることを求める。このリポは public |
| クラウドのスレッドで pecot-workflow の MCP を使う | 読み取りでも失敗する。スレッドの VM では GitHub の GraphQL がプロキシで 403 になり、この MCP は手元で GraphQL を呼ぶ（2026-11-25 に確かめた） |
| GitHub 公式のリモート MCP | 動く。claude.ai のサーバーから GitHub へ直接つなぐ。coordinator は、`https://api.githubcopilot.com/mcp/` と `/mcp/x/projects/readonly` で、ボード・Issue・PR を読めている |
| ボードへの書き込み | coordinator がつないでいるボードの MCP は読み取り専用。リモート MCP だけで、ボードの pecot の欄（進行の欄など）を pecot-workflow と同じ形に揃えられるかは確かめていない |

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| coordinator | claude.ai のプロジェクトのプロジェクトチャットで利用者と話し、ボードを読み、スレッドを起動して作業を割り振る Claude |
| スレッド | coordinator が起動する、Issue 1 件の作業を担う Claude のセッション。クラウドの VM で動くもの（クラウドのスレッド）と、利用者の端末の worktree で Remote Control で動くもの（RC のスレッド）がある |
| プロジェクト指示 | 利用者が claude.ai のプロジェクトの設定に書く文。coordinator とスレッドが読む |
| リモート MCP | GitHub 公式の、GitHub が提供する MCP サーバ。claude.ai のコネクタとしてつなぐ |
| pecot の欄 | pecot がボードに持ち、自分の処理で読み書きするフィールド（進行の欄など）と、pecot が Issue に付ける形（親子・blocked-by・ラベル・題の形） |
| pecot の流れ | pecot-workflow のスキルと CLI が定める、Issue の確認・着手・計画・PR・マージ・片付けの順序と、その間のボードの動き |
| 既存のプラグイン | このリポが配る pecot-workflow・pecot-visual・pecot-tools。どれも bin を持つ |
| 配布性 | プラグインを、このリポ以外のプロジェクトと利用者が、スキルを書き換えずにそのまま使えること |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 判断と手順をプラグインに寄せ、プロジェクト指示に残すものを最小限に決める (Priority: P1)

保守者は、今のプロジェクト指示の文を 1 つずつ振り分けた一覧を読める。既定の行き先はプラグインで、プロジェクト指示に残すのは、プラグインでは決められないプロジェクト固有の値（作業場所の名前と数・リポ・ボード・端末の事情）だけだ。固有の値に依る文は、値をプロジェクト指示から受け取る形に書き換えてプラグインに移す。一覧には振り分けの基準と、どちらにも置かないもの（不要になったもの）が書いてある。

**Why this priority**: プラグインのスキルに何を書くかは、この線で決まる。プラグインは他のプロジェクトにも配るので、判断と手順をプロジェクト指示に残すと、利用者ごとに同じ文を書き直すことになる。逆に固有の値がスキルに混ざると、他のプロジェクトで使えない。

**Independent Test**: 今のプロジェクト指示の文がすべて、一覧のどれかの行に入っていることを確かめる。プロジェクト指示に残す側の行に、判断や手順（いつ何をするか）が入っていないことを確かめる。振り分けの基準を別のプロジェクト（pecot-sandbox を想定した架空のプロジェクト）に当て、プラグインに移す側に固有の名前（wt の番号・リポの名前・ボードの名前）が残らないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 今のプロジェクト指示がある、**When** 保守者が振り分けの一覧を読む、**Then** すべての文が「プラグインに移す」「プロジェクト指示に残す」「置かない」のどれかに入り、それぞれに理由がある
2. **Given** 固有の値と判断が混ざった文（例: 「wt1〜wt12 の空きに割り振る」）がある、**When** 振り分ける、**Then** 判断（空きの作業場所に割り振る）はプラグインに、値（wt1〜wt12）はプロジェクト指示に分かれる
3. **Given** 振り分けの基準がある、**When** 新しい決まりを足すとき、**Then** 保守者は基準だけでどちらに書くかを決められる

---

### User Story 2 - リモート MCP だけで、ボードの pecot の欄まで揃えられるかが分かる (Priority: P1)

保守者は、pecot-workflow が行う書き込み（起票・親子・blocked-by・進行の欄の移動・コメント・PR の作成）の 1 つずつについて、リモート MCP だけで同じ形にできるか、できないなら何が足りないかを、試した記録で読める。

**Why this priority**: クラウドのスレッドと coordinator は pecot-workflow の MCP を使えない。リモート MCP で揃えられない書き込みがあれば、スキルの書き方か、流れそのものを変える必要がある。後続のフェーズの形がこの結果で決まる。

**Independent Test**: 検証用のリポ（pecot-sandbox）とボード（pecot sandbox）で、リモート MCP だけを使って Issue 1 件を起票から Done まで動かし、pecot-workflow で同じ操作をした Issue とボードの欄が一致するかを比べる。

**Acceptance Scenarios**:

1. **Given** pecot-workflow の書き込みの一覧がある、**When** 保守者が検証の記録を読む、**Then** 書き込みごとに「同じ形にできる」「できない（足りないもの）」が、試した操作と結果で書いてある
2. **Given** リモート MCP でできない書き込みがある、**When** 保守者が記録を読む、**Then** 代わりの手（別のツール・流れの変更・残す）の案と、それぞれの影響が書いてある
3. **Given** 検証が終わった、**When** 保守者が検証用のボードを見る、**Then** 検証で作ったものは、pecot-sandbox の運用の手順どおりに片付いている

---

### User Story 3 - claude.ai のプロジェクトとクラウドのスレッドへプラグインを配る方法が分かる (Priority: P1)

保守者は、スキルだけのプラグインを claude.ai にインストールし、claude.ai のプロジェクトとクラウドのスレッドで使う手順と、載ったことの確かめ方を読める。手順は試した結果に基づき、載らない経路があればその理由も書いてある。

あわせて、既存のプラグインが今 claude.ai の制約に引っかかる原因と、それらが pecot-coordinator の追加を止めるかが分かる。止めるなら、pecot-coordinator を載せるための置き方（marketplace を分ける・marketplace の載せ方を変えるなど）の案と、それぞれの影響が書いてある。

検証は、公式の文書（claude.ai のプラグインの概要・部品ごとの対応・組織の sync・アップロードの要件）を読んでから行い、読んだ文書と日付を記録に添える。文書に書いていないこと（クラウドのスレッドと claude.ai のプロジェクトで読まれるか）は、試した結果で埋める。

**Why this priority**: claude.ai にインストールできることは、この Epic の目標の 1 つ。配る方法が無ければ、スキルを書いても coordinator に届かない。配る経路によって、プラグインの置き場所（このリポの marketplace か別の場所か）と版の上げ方が変わる。

**Independent Test**: スキルを 1 つだけ持つ試しのプラグインを、既存のプラグインと同じ marketplace に置いた場合と、置かない場合の両方で claude.ai に載せてみて、載るかどうかと止まった理由を記録する。載った経路で、coordinator とクラウドのスレッドの両方でそのスキルが読まれることを確かめる。

**Acceptance Scenarios**:

1. **Given** スキルだけのプラグインがある、**When** 保守者が手順どおりに配る、**Then** claude.ai にインストールでき、coordinator とクラウドのスレッドで、そのスキルが使える
2. **Given** 今の marketplace がある、**When** 保守者が記録を読む、**Then** 既存のプラグインが claude.ai の制約に引っかかる原因（bin かどうか）と、それらが pecot-coordinator の追加を止めるかが、試した結果で書いてある
3. **Given** 既存のプラグインが pecot-coordinator の追加を止める、**When** 保守者が記録を読む、**Then** pecot-coordinator を載せるための置き方の案と、それぞれの影響（Claude Code での入れ方・版の上げ方が変わるか）が書いてある
4. **Given** プラグインの版を上げた、**When** 保守者が手順どおりに更新する、**Then** 新しい版のスキルが、次に起動したスレッドから使われる
5. **Given** 試した経路のうち載らないものがある、**When** 保守者が記録を読む、**Then** 載らない理由が書いてある

### User Story 4 - coordinator が配布したスキルに従って Issue を割り振り、スレッドを起動する (Priority: P2)

利用者がプロジェクトチャットで頼むと、coordinator はプラグインのスキルに従って、ボードを読み、Ready で未担当の Issue を空きの作業場所に割り振り、スレッドを起動する。利用者に上げる判断（計画の承認・マージ・仕様や挙動を変える判断・戻せない削除・端末でしか答えられない権限の確認）と、自分で決める判断（レビュー指摘の採否・push・再開・割り振り）の範囲も、スキルに従う。プロジェクト指示には、プロジェクト固有の事情だけが残る。

**Why this priority**: Epic の目的そのもの。ただし、US1〜US3 の結果でスキルの中身と載せ方が決まるので、その後に置く。

**Independent Test**: プロジェクト指示からプラグインに移した文を消したプロジェクトで、coordinator に「次の Issue を始めて」と頼み、Ready で未担当の Issue が空きの作業場所に割り振られ、スレッドが起動することを確かめる。同じ Issue が 2 つの作業場所に割り振られないことを確かめる。

**Acceptance Scenarios**:

1. **Given** Ready で未担当の Issue と空きの作業場所がある、**When** 利用者が coordinator に作業を頼む、**Then** coordinator は Issue を 1 つの作業場所に割り振り、スレッドを起動する
2. **Given** Issue の無い作業を頼まれた、**When** coordinator が割り振る、**Then** 先に起票させてから割り振る
3. **Given** スレッドが小さな判断（レビュー指摘の採否・push・再開）で止まった、**When** coordinator が気づく、**Then** 利用者に聞かずに推奨どおりに進める
4. **Given** スレッドが計画の承認・マージを待っている、**When** coordinator が利用者に伝える、**Then** 利用者が判断するための検証済みの手順とリンクだけを渡す

---

### User Story 5 - クラウドのスレッドが、pecot-workflow を使わずに pecot の流れで書き込む (Priority: P2)

クラウドのスレッドは、Issue の確認・ボードの進行の欄の移動・Issue へのコメント・PR の作成を、リモート MCP だけで、pecot-workflow と同じ形で行う。ボードと Issue を後から見ても、RC のスレッドが pecot-workflow で進めたものと見分けがつかない。

**Why this priority**: クラウドのスレッドは pecot-workflow の MCP を使えない。US2 の結果に従い、揃えられる範囲で揃える。

**Independent Test**: 検証用のリポとボードで、クラウドのスレッドに Issue 1 件を着手から PR まで進めさせ、ボードの欄・Issue のコメント・PR の本文が、pecot-workflow で進めた Issue と同じ形であることを確かめる。

**Acceptance Scenarios**:

1. **Given** クラウドのスレッドが Ready の Issue を受け持った、**When** 着手する、**Then** ボードの進行の欄が pecot-workflow と同じ値に移る
2. **Given** クラウドのスレッドが PR を作る、**When** PR ができる、**Then** PR の本文と Issue とのつながりが pecot-workflow で作った PR と同じ形になる
3. **Given** US2 で揃えられないと分かった書き込みがある、**When** スレッドがその場面に来る、**Then** スキルが定めた代わりの手で進めるか、止めて利用者に伝える

---

### User Story 6 - 利用者がプロジェクト指示を、プロジェクト固有の事情だけに書き直せる (Priority: P3)

利用者は、案内に沿って今のプロジェクト指示から、プラグインに移った文を消せる。消した後も coordinator の動きは変わらない。

**Why this priority**: 移した後に同じ文が二重に残ると、どちらが正か分からなくなる。ただし、プラグインが動いてからの片付けなので最後に置く。

**Independent Test**: 案内に沿って書き直したプロジェクト指示で、US4 の確かめをもう一度通す。

**Acceptance Scenarios**:

1. **Given** プラグインが載った、**When** 利用者が案内を読む、**Then** プロジェクト指示から消す文と残す文が分かる
2. **Given** 書き直したプロジェクト指示とプラグインがある、**When** coordinator が US4 の場面を進める、**Then** 書き直す前と同じ判断をする

---

### User Story 7 - 既存のプラグインも claude.ai にインストールできる (Priority: P2)

US3 の検証で、既存のプラグインが載らない原因がその構成（直下の `bin/` など）と確かめられたとき、利用者は構成を直した既存のプラグインを claude.ai にインストールできる。Claude Code での使い方（CLI・MCP・フック）は変わらない。

**Why this priority**: claude.ai にインストールできることは目標の 1 つで、原因が既存のプラグインの側にあるなら、そちらを直すのが筋。ただし、原因の特定（US3）が先に要る。

**Independent Test**: 構成を直した既存のプラグインを claude.ai に Add marketplace で足し、拒まれずにインストールできることを確かめる。同じ版を Claude Code に入れ、CLI・MCP・フックが今どおり動くことを確かめる。

**Acceptance Scenarios**:

1. **Given** 構成を直した既存のプラグインがある、**When** 利用者が claude.ai に足す、**Then** 拒まれずにインストールできる
2. **Given** 構成を直した既存のプラグインがある、**When** 利用者が Claude Code に入れる、**Then** CLI・MCP・フックが今どおり動く
3. **Given** 直したプラグインを claude.ai に入れた、**When** 利用者が Chat で使う、**Then** Chat で読まれない部品（手元の MCP・フックなど）に依るスキルがどう振る舞うかが、文書に書いてある

---

### Edge Cases

- プラグインのスキルとプロジェクト指示が食い違うとき、coordinator はどちらに従うか。プロジェクト指示（プロジェクト固有の事情）を優先し、食い違いを利用者に伝える
- リモート MCP のつなぎ先の権限が読み取りだけのとき、スレッドは書き込みの前にそれと分かり、何をつなげばよいかを利用者に示す
- クラウドのスレッドと RC のスレッドが同じプロジェクトに混ざるとき、同じ Issue が両方に割り振られない
- 検証で、リモート MCP がボードの single select の値を ID でしか受け取らないなど、pecot-workflow と入力の形が違うとき、スキルにどこまで書くかは「スキルに MCP の基本を書かない」決まりに従う
- claude.ai に載せたプラグインの版と、このリポの main の版がずれたとき、利用者が気づける

## Requirements *(mandatory)*

### Functional Requirements

**検証（後続のフェーズの前に行う）**

- **FR-001**: 保守者は、今のプロジェクト指示の文を「プラグインに移す」「プロジェクト指示に残す」「置かない」に振り分けた一覧と、振り分けの基準を持たなければならない
- **FR-002**: 振り分けの既定の行き先はプラグインでなければならない。プロジェクト指示に残すのは、プラグインでは決められないプロジェクト固有の値（作業場所の名前と数・リポ・ボード・端末の事情）だけとし、判断と手順を残してはならない。固有の値をプラグイン側に入れてはならない
- **FR-003**: 保守者は、pecot-workflow の書き込みの一覧と、そのそれぞれをリモート MCP だけで同じ形にできるかの検証の記録を持たなければならない
- **FR-004**: FR-003 の検証は、検証用のリポとボードで行い、このリポとボードには書き込まない
- **FR-005**: FR-003 でできないと分かった書き込みには、代わりの手の案と影響を記録しなければならない
- **FR-006**: 保守者は、スキルだけのプラグインを claude.ai にインストールし、claude.ai のプロジェクトとクラウドのスレッドで使う手順・更新の手順・載ったことの確かめ方を、試した結果とともに持たなければならない
- **FR-006a**: 保守者は、既存のプラグインが claude.ai の制約に引っかかる原因と、同じ marketplace のそれらが pecot-coordinator の追加を止めるかを、試した結果とともに持たなければならない。止めるときは、pecot-coordinator を載せるための置き方の案と影響を記録しなければならない
- **FR-007**: 検証の結果が Epic の前提（スキルだけで bin を含めない・GitHub の読み書きはリモート MCP）を崩すときは、後続のフェーズに進む前に利用者に伝え、判断を仰がなければならない

**プラグイン**

- **FR-008**: pecot-coordinator プラグインは、スキルだけを持ち、実行ファイル・MCP サーバ・フックを含めてはならない
- **FR-009**: プラグインは、このリポの他のプラグインと同じく、版の管理・リリース・テストの対象にならなければならない
