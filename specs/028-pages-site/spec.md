# Feature Specification: pecot の文書サイトを GitHub Pages で公開し、インタフェース定義書と合否をそこで読める

**Feature Branch**: `028-pages-site`

**Created**: 2026-11-17

**Status**: Draft

**Input**: Epic pecotcraft/pecot#576。pecot の文書サイト（インタフェース定義書と、振る舞いごとのテストの合否を含む）を GitHub Pages で公開する。この spec の主題は、公開までの流れと、テストの結果の出し方だ。利用者向けの紹介の文章は書かない。

## Clarifications

### Session 2026-11-17

- Q: 公開サイトに、どの版を並べるか（過去の版を残すか、開発中も出すか） → A: 最新のリリースの版と、main の最新の版の 2 つを並べる。リリースのたびにリリース版を、main への push のたびに開発版を、それぞれ上書きする。過去のリリースは残さない（FR-001、FR-002、FR-020、FR-021）
- Q: 機能（feature ブランチ・PR）ごとの定義書と合否を、どう確かめるか → A: PR が開いている間だけ、公開サイトの中に PR ごとの版を置き、URL で見られるようにする。PR に URL を載せ、マージかクローズで消す。fork の PR は対象外（FR-022〜FR-025、User Story 3）

## 背景

定義書と合否は手元でしか読めない。CI の結果のままでは、公開に足る合否がそろわない。

| 場面 | 今の姿 |
|---|---|
| 文書の骨組み | `libs/interface-spec/docs` に、トップ・はじめに・インストール・ガイド・リファレンス・トラブルシューティング・開発のページがある。紹介のページは「準備中」の注記だけ |
| 定義書と合否 | 手元で `interface-spec:docs` を動かして作り、ローカルのサーバで開くしかない。CI でも affected でも動かない |
| 合否の材料 | 定義書の項目につながるのは、3 つのプラグインの `test-cli` と、pecot-workflow の `test-hooks` が出すテストの結果だけ |
| 合否のそろい方 | PR の CI は affected のレーンを job に分けるので、1 つの job に合否の材料がそろわない。そろわない材料で作ると、動かなかったレーンの項目が「未実行」と出る |
| 合否の出し方 | 項目ごとに、つながるテストと「通った・落ちた・未実行」を出す。どの版・いつの実行の結果かは出ない |
| 公開 | リポは public だが、GitHub Pages は有効でなく、公開の workflow も無い |

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| 公開サイト | GitHub Pages で公開する pecot の文書サイト。`libs/interface-spec/docs` から作る |
| 合否のレーン | 定義書の項目につながるテストの結果を出すレーン。今は 3 つのプラグインの `test-cli` と、pecot-workflow の `test-hooks` |
| そろった合否 | 合否のレーンをすべて、同じコミットのソースで動かした結果の一式 |
| リリース版 | 公開サイトのうち、最新のリリースのコミットから作った部分。利用者が入れる版を表す |
| 開発版 | 公開サイトのうち、main の最新のコミットから作った部分。保守者が開発中の状態を確かめる |
| PR 版 | 公開サイトのうち、開いている PR の head のコミットから作った部分。PR ごとに 1 つあり、PR が閉じると消える |
| 側 | リリース版・開発版・PR 版のどれか 1 つ。公開サイトは複数の側からなる |
| 公開の版 | 各側を作ったソースのコミットと、各プラグインの版 |
| 公開の流れ | ソースの取り出しから、合否のレーンの実行・サイトの作成・GitHub Pages への公開までの一連の処理 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - リリースと main への push のたびに、その版の定義書と合否が公開サイトに出る (Priority: P1)

保守者が PR をマージすると、公開の流れが main の最新のコミットで合否のレーンをすべて動かし、開発版を作り直す。リリースすると、そのリリースのコミットで同じことをして、リリース版を作り直す。保守者は手でサイトを作らない。

**Why this priority**: 公開までの流れが無ければ、どの中身も読む人に届かない。この spec の主題だ。

**Independent Test**: main への push（またはリリース）の後、公開サイトの URL を開き、開発版（またはリリース版）の公開の版がそのコミットになっていることを確かめる。

**Acceptance Scenarios**:

1. **Given** 公開の流れが入っている、**When** PR がマージされて main に push される、**Then** そのコミットで合否のレーンが動き、開発版が作り直されて公開される。リリース版は変わらない
2. **Given** 公開の流れが入っている、**When** 保守者が本番のリリースを済ませる、**Then** そのリリースのコミットで合否のレーンが動き、リリース版が作り直されて公開される。開発版は変わらない
3. **Given** 公開の流れが入っている、**When** 保守者が、リリース版か開発版かとコミットを指定して公開を手で起動する、**Then** 指定した側がそのコミットのソースで作り直されて公開される
4. **Given** 公開の流れが動いた、**When** 合否のレーンのうち 1 つが結果を残さずに止まった、**Then** 公開はせず、前に公開したサイトが残る。止まったレーンが workflow の実行から分かる
5. **Given** 公開の流れが動いた、**When** 合否のレーンのテストが落ちた（結果は残った）、**Then** 公開を続け、落ちた項目を落ちたと出す
6. **Given** 同じ側（リリース版か開発版）の公開の流れが 2 回続けて起動された、**When** 両方が終わる、**Then** 後に起動した方の版がその側に残る
7. **Given** fork からの PR、**When** 公開の流れを動かそうとする、**Then** 公開サイトは書き換わらない

---

### User Story 2 - 読む人が、合否がどの版・いつの結果で、項目ごとに何が起きたかを正しく読める (Priority: P2)

公開サイトで定義書のページを開いた人が、その合否がどのコミット・どのリリースの、いつの実行の結果かを知る。項目ごとに、通った・落ちた・飛ばした・つながるテストが無いを見分け、落ちたテストは理由まで読める。

**Why this priority**: 公開した合否を読み違えると、公開しない方がましになる。公開の流れ（P1）ができた後で、出し方を正す。

**Independent Test**: 公開サイトのプラグインの一覧表と、1 つのコマンドのページを開く。版・実行日時・結果の出どころへのリンクと、状態ごとの数と表示の違いを確かめる。

**Acceptance Scenarios**:

1. **Given** 公開サイトが公開済み、**When** どのページを開いても、**Then** 公開の版（コミットの短い ID とリリースの版）と、合否を作った実行の日時が見える
2. **Given** 公開サイトが公開済み、**When** 合否の出どころを確かめたい、**Then** 合否を作った workflow の実行へのリンクをたどれる
3. **Given** プラグインの一覧表を開いた、**When** コマンド・ツールの行を見る、**Then** 振る舞いの項目の数が、通った・落ちた・飛ばした・テストが無いの状態ごとに出ている
4. **Given** コマンドのページを開いた、**When** 振る舞いの項目を見る、**Then** 項目ごとに状態とつながるテストが出ており、状態は色だけでなく文字でも見分けられる
5. **Given** テストが落ちた項目がある、**When** その項目を見る、**Then** 落ちたテストの名前と、失敗の要旨（テストの結果が残したメッセージ）が読める
6. **Given** つながるテストが無い項目がある、**When** その項目を見る、**Then** 「テストが無い」と出て、「未実行」とは区別される
7. **Given** 公開サイトのトップを開いた、**When** 全体の合否を知りたい、**Then** プラグインごとに状態ごとの項目の数が 1 か所にまとまって見える

---

### User Story 3 - PR が開いている間、その PR の定義書と合否を URL で確かめる (Priority: P3)

保守者が PR を開くと、その PR の head のコミットで合否のレーンがすべて動き、PR 版が公開サイトに載る。PR から URL をたどれば、マージする前に、変わった定義書と合否をブラウザで読める。PR を閉じると PR 版は消える。

**Why this priority**: 開発中の機能の定義書と合否を、マージ前に確かめたい。ただし、リリース版・開発版の公開（P1）と出し方（P2）ができてから載せる。

**Independent Test**: 同じリポのブランチから PR を開き、PR に載った URL を開いて PR 版の公開の版が head のコミットであることを確かめる。push の後に作り直されること、PR を閉じた後に消えることも確かめる。

**Acceptance Scenarios**:

1. **Given** 同じリポのブランチから PR を開いた、**When** PR 版の公開の流れが終わる、**Then** PR から 1 回のクリックで PR 版を開け、ページに PR の番号と head のコミットが出ている
2. **Given** PR 版がある、**When** PR の head に push する、**Then** PR 版が新しい head のコミットで作り直され、URL は変わらない
3. **Given** PR 版がある、**When** PR をマージかクローズする、**Then** PR 版は公開サイトから消え、リリース版と開発版は変わらない
4. **Given** fork から PR を開いた、**When** PR の CI が動く、**Then** PR 版は作られず、公開サイトは変わらない
5. **Given** PR 版がある、**When** 開発版やほかの PR 版が作り直される、**Then** その PR 版は消えずに残る

---

### User Story 4 - 保守者が、手元で公開と同じ出し方を確かめられる (Priority: P4)

保守者が、表示の変更を PR に出す前に、手元で公開と同じ形のサイトを作って見る。版と日時の表示は、手元の値で埋まる。

**Why this priority**: 出し方を直すたびに本番へ公開して確かめるのは重い。ただし公開の流れと出し方ができてからでよい。

**Independent Test**: 手元で、合否のレーンを動かしてからサイトを作り、開いた結果に版・日時・状態ごとの数が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 手元で合否のレーンを動かした、**When** 文書サイトを作る、**Then** 公開と同じ形で、手元のコミットと作った日時が出る
2. **Given** 手元で合否のレーンを一部しか動かしていない、**When** 文書サイトを作る、**Then** 作れるが、動かしていないレーンの項目は「未実行」と出る（公開の流れとは違い、止めない）

---

### Edge Cases

- 定義書から消えた項目: 次の公開で、その項目のページが消える
- テストの結果に、定義書に無い項目の ID がある: 公開サイトには出さない（今の決まりのまま）
- 同じテストが複数の結果のファイルに出る: 1 件として数える
- 合否のレーンが増えた（新しいプラグインやレーン）: 公開の流れが動かすレーンと、サイトが読む結果のファイルの一覧が、1 か所の定めからずれない
- 紹介のページは「準備中」のまま公開される: この spec では中身を書かない
- GitHub Pages がまだ有効でない: 初回の公開の前に有効にする手順が、保守者の文書にある
- リリースのタグが無いコミットで手で起動した: 各プラグインの版は、そのコミットの `package.json` の版をそのまま出す。タグの有無で出し方を変えない
- PR 版の作り直しの途中で PR が閉じられた: 作り直しを公開せず、PR 版を消す
- 開いている PR が多い: PR 版の数に上限は置かないが、公開サイトの容量の上限に近づいたら公開の流れが知らせる

## Requirements *(mandatory)*

### Functional Requirements

#### 公開の流れ

- **FR-001**: 公開の流れは、main への push のたびに、そのコミットで開発版を作り直さなければならない。本番のリリースが済むたびに、そのリリースのコミットでリリース版を作り直さなければならない
- **FR-002**: 保守者は、リリース版か開発版かとコミットを指定して、公開の流れを手で起動できなければならない
- **FR-003**: 公開の流れは、合否のレーンをすべて、公開するコミットのソースで動かさなければならない。PR の CI の結果を流用してはならない
- **FR-004**: 合否のレーンのうち 1 つでも結果を残さなかったときは、公開してはならない。前に公開したサイトを残す
- **FR-005**: テストが落ちても結果が残ったときは、公開しなければならない
- **FR-006**: 公開の流れは、GitHub Pages を GitHub Actions から公開する公式の形に従わなければならない
- **FR-007**: リリース版と開発版を書き換える起動は、既定のブランチからに限らなければならない。fork の PR の実行で公開サイトを書き換えてはならない
- **FR-008**: 同じ側の公開の流れが重なったときは、後に起動した版を残さなければならない
- **FR-009**: 公開の流れが動かす合否のレーンと、サイトが読む結果のファイルは、1 か所の定めから決まらなければならない
- **FR-010**: GitHub Pages を有効にする手順と、公開の流れの起動・やり直しの方法を、保守者の文書に書かなければならない
- **FR-011**: README に、公開サイトへのリンクを置かなければならない
- **FR-020**: ある側を作り直しても、ほかの側の中身を消したり古い版に戻したりしてはならない
- **FR-021**: 公開サイトは、リリース版と開発版を行き来でき、今どの側を読んでいるかが分からなければならない。トップから最初に出すのはリリース版とする

#### PR 版

- **FR-022**: 同じリポのブランチから開いた PR は、開いたときと head に push されたときに、その head のコミットで PR 版を作り直さなければならない。fork の PR では作らない
- **FR-023**: PR 版の URL を、PR から 1 回のクリックでたどれる場所に載せなければならない。作り直しても URL は変わらない
- **FR-024**: PR がマージかクローズされたら、その PR 版を公開サイトから消さなければならない
- **FR-025**: PR 版のページには、PR の番号と、PR へのリンクを出さなければならない。PR 版は、リリース版と開発版の行き来の中には並べない

#### テストの結果の出し方

- **FR-012**: 公開サイトのすべてのページに、どの側か、公開の版（コミットの短い ID と、各プラグインの版）と、合否を作った実行の日時を出さなければならない
- **FR-013**: 公開サイトに、合否を作った workflow の実行へのリンクを出さなければならない
- **FR-014**: 振る舞いの項目の状態は、通った・落ちた・飛ばした・テストが無い・未実行の 5 つを区別しなければならない。公開の流れで作ったサイトに「未実行」は現れない
- **FR-015**: 状態は、色だけに頼らず、文字か記号でも見分けられなければならない
- **FR-016**: 落ちたテストには、テストの名前と、テストの結果が残した失敗の要旨を出さなければならない
- **FR-017**: プラグインの一覧表は、コマンド・ツールごとに、状態ごとの項目の数を出さなければならない
- **FR-018**: 公開サイトに、プラグインごとの状態ごとの項目の数を 1 か所にまとめた全体の合否を出さなければならない
- **FR-019**: 手元で作るサイトも、公開と同じ出し方で作れなければならない。手元では、合否のレーンが欠けても止めない

### Key Entities

- **公開サイト**: リリース版・開発版と、開いている PR の数だけの PR 版からなる静的なサイト。各側は定義書のページと合否、紹介のページ（今の骨組み）を持つ
- **公開の版**: 各側を作ったソースのコミット・各プラグインの版・合否を作った実行の日時と、その実行への参照
- **そろった合否**: 合否のレーンすべての結果のファイル。公開の版と同じコミットで作る
- **振る舞いの項目の状態**: 通った・落ちた・飛ばした・テストが無い・未実行のどれか。落ちたときは失敗の要旨を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: main への push とリリースの後、人が手を加えずに、30 分以内に開発版とリリース版がそれぞれのコミットの中身に変わる
- **SC-002**: 公開の流れで作った公開サイトで、「未実行」と出る振る舞いの項目が 0 件である
- **SC-003**: 合否のレーンが 1 つ結果を残さずに止まった実行で、公開サイトが書き換わった件数が 0 件である
- **SC-004**: 公開サイトのどのページからも、1 回のクリック以内で、公開の版と合否を作った実行にたどれる
- **SC-005**: 落ちた項目を見た人が、公開サイトだけで、どのテストがなぜ落ちたかの要旨を言える
- **SC-006**: 公開サイトのリンク切れが 0 件である
- **SC-007**: 同じリポのブランチの PR で、開くか push してから 30 分以内に PR 版がその head の中身になる。閉じてから 30 分以内に PR 版が消える

## Assumptions

- 公開サイトは、`libs/interface-spec/docs` の既存の Sphinx の project から作る。別のサイトの仕組みは立てない
- 利用者向けの紹介の文章（はじめに・インストール・ガイド・トラブルシューティング）は、この spec では書かない。「準備中」の骨組みのまま公開する
- リポは public のまま運用し、独自ドメインは使わない
- 公開するのは、最新のリリース版と main の最新の開発版と、開いている PR の PR 版だけ。過去のリリースは残さない（タグから作り直せる）
- 合否のレーンは今の `iface_junit` の定め（3 つのプラグインの `test-cli` と、pecot-workflow の `test-hooks`）から始める
- 合否のレーンのテストは、外部の資格情報なしで動く（PR の CI と同じ前提）
- 公開サイトは日本語だけで書く
