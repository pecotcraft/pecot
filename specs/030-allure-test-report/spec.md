# Feature Specification: 公開サイトのテストレポートを Allure Report に替え、テストの題・失敗の理由・履歴を読める

**Feature Branch**: `feat/breakdown-allure-report/670`

**Created**: 2026-11-18

**Status**: Draft

**Input**: Epic pecotcraft/pecot#645。公開サイト（specs/028-pages-site で作ったもの）のテスト結果を、自前の作り（sphinx-test-reports）でなく Allure Report で読めるようにする。テストの題・失敗の理由とスタック・前回との違いを、ほかのプロジェクトでも見る普通の形で読める。自前のテストレポートのページは片付ける。

## Clarifications

- Q: テストレポートに入れるテストの範囲 → A: vitest と pytest で動く全レーン。libs と `.githooks` のレーンも含む（FR-002）（2026-11-26 に改めた。下の節）
- Q: 定義書のページに、項目ごとの合否を出すか → A: 出さない。テストレポートへのリンクだけを出し、合否は Allure で読む。合否を描く自前の作りは全部消す（FR-017、FR-022）

### Session 2026-11-23

- Q: 開発版のテストレポートに入れる全レーンのテストの結果は、どの実行から取るか → A: main への push のたびに、テストレポート用の run が全レーンを動かす。そのコミットだけの結果でレポートを作る（FR-009a、FR-012）（2026-11-26 に改めた。下の節）
- Q: リリース版のテストレポートに入れるテストの結果は、どの実行から取るか → A: 本番のリリースが済むたびに、テストレポート用の run が、各プラグインの最新のタグのコミットでそのプラグインのレーンを動かす。libs と `.githooks` のレーンは、最も新しいタグのコミットで動かす（FR-009b）
- Q: この機能が入る前のタグのコミットは Allure が読む結果を出せない。次のリリースまで、リリース版のテストレポートをどう扱うか → A: 結果を出せるタグを持つプラグインだけでレポートを作る。まだ出せないプラグインは、レポートに入っていないことを、公開サイトのリンクのそばに書く。1 つも出せない間は、リリース版にレポートとリンクを置かない（FR-009d、FR-012）
- Q: この機能の中で、今あるテストに添付（スクリーンショットなど）を足すか → A: 足す。画面や画像を扱うテストは、成功したときも毎回スクリーンショットを添付する。成功が嘘の可能性もあるので、成功したテストが何を見て成功としたかを、人が目で確かめられるようにする（FR-007a、FR-007b、SC-011）

### Session 2026-11-23（plan と analyze で改めた点）

- リリース版で結果を出せるプラグインが 1 つも無い間と、テストレポートがまだ保管されていない側には、リンクを出さず、その位置に案内のページを置く。上の「レポートとリンクを置かない」は、この形に改めた（FR-009d、FR-010、research R10）
- PDF・PPTX のように画像でない成果物は、画像にせず、ファイルそのものを添付する（FR-007a、research R11）
- 不安定の印は、最新の実行で成功したテストにも付ける。成功が嘘の可能性を、履歴からも見つけるため（User Story 3、research R5）
- 開発版のテストレポートを作る run は、動いている途中で取り消さない。後から来た push は、動いている run の終わりを待つ（research R9）

### Session 2026-11-26

マージキューは、マージした後の状態をもう試している。main で同じものを流し直しても得るものが無い（#492 で ci の main での実行を消したのと同じ理由）。開発版のレポートは PR の CI と見るものがほぼ同じなので、履歴の価値は、リリースをまたいだ推移と不安定なテストにある。

- Q: 開発版のテストレポートに入れる結果は、どの実行から取るか → A: main では流し直さない。マージキューで流したレーンの結果を、レーンごとに最新の 1 回分だけ持ち、寄せ集めて作る。結果がまだ無いレーンだけ main で流す（FR-009a）
- Q: マージキューが流さなかったレーンは、どの結果で埋めるか → A: このマージの変更が届かないレーンは、そのレーンの前の結果を使う。入力が変わっていないので、前の結果が今のコミットの結果でもある。
  キューは、PR の CI で試し済みのレーンも省く（`list-test-lanes.sh` の積のモード）。変更が届いたのに省いたレーンは、前の結果のままにせず、その変更を試した run の結果に替える。取り方は #821 で決める（FR-012。PR #825 のレビューで補った）
- Q: 開発版のテストレポートに履歴を持つか → A: 持たない。最新の結果だけを出す（FR-018、User Story 3）
- Q: リリース版の履歴は、何回分をどこに置くか → A: 10 回分を S3 に置く。10 回の履歴は約 225 MB で、git の 1 ファイルの上限 100 MB を超え、`pages-store` に置けない（FR-019、FR-020、research R5）
- Q: レポートのレーンの範囲 → A: nx の `test-*` のレーンすべてにする。`node --test` の 2 本は vitest に移し、`allure-vitest` で結果を残す（#809）。bash の `*.test.sh` の 9 本は #810 で入れる（FR-001、FR-002）
- Q: 容量を減らすために、Allure のアダプタが付ける自動のラベル（`host`・`thread` など）を落とすか → A: 落とさない。タイムラインがこの 2 つを使う。容量は、履歴を S3 に置くことで収める（FR-020a、research R5）
- PR 版には、これまでどおりテストレポートを作らない（FR-009）

## 背景

公開サイトは、#648 でテストを待たずに作る形になり、今は定義書だけを載せている。テストの結果を読む場所は、手元で作ったサイトにしか無い。その作りも、読む人の役に立つ情報を出せていない。

| 場面 | 今の姿 |
|---|---|
| テストの並び | テストレポートのページに、sphinx-test-reports の番号（`TF_PECOT_VISUAL_1_…`）が並ぶ。何を確かめるテストかが分からない |
| 見えるテスト | 要件の ID につながるテストだけが、定義書のページに出る。`evidence_create` のテスト約 180 件のうち、つながるのは 5 件で、残りはどこにも出ない |
| 失敗の追い方 | 失敗の要旨は出る。前回の実行との違い・不安定なテスト・添付（スクリーンショット）は無い |
| 見た目と言葉 | 表の列・状態の名前・崩れの直しを、自前で作り続けている（#590 だけで何度も直した） |
| 結果の形 | テストは JUnit XML だけを残す。Allure が読む結果は出していない |
| 要件の ID | `verifies` は、JUnit の属性にだけ ID を残す |
| 公開の流れ | 公開の流れはテストを動かさず、テストの結果を集めない。履歴の置き場所も無い |

この spec で使う言葉（028 の言葉はそのまま使う）:

| 言葉 | 意味 |
|---|---|
| テストレポート | 公開サイトの中の Allure Report。開発版とリリース版に 1 つずつある。PR 版には無い |
| テストの結果 | テストの実行が残す、Allure が読む形の記録。テストの題・状態・失敗の理由とスタック・要件の ID・添付を持つ |
| レポートのレーン | テストレポートに結果を入れるテストのレーン。nx の `test-*` のレーンすべて（プラグイン・libs・`.githooks`・`nx-release`） |
| レーンの最新の結果 | 開発版のテストレポートの材料。レーンごとに、main に入ったコミットで流した最新の 1 回分の結果 |
| 履歴 | リリース版の、前の 10 回までのテストの結果の要約。前回との違いと、不安定なテストを出すために使う。開発版は持たない |
| 要件の ID | 定義書の振る舞いの項目の ID。テストは `verifies` で書く |
| 自前のテストレポート | sphinx-test-reports で作る `development/` の下のページと、定義書のページに合否を描く作り |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 保守者が、公開サイトのテストレポートで、テストの題と失敗の理由を読める (Priority: P1)

保守者が公開サイトからテストレポートを開くと、すべてのレーンのテストが 1 つのレポートにまとまっている。テストは、書いた題のまま並ぶ。落ちたテストを開くと、失敗の理由とスタックが読める。要件の ID につながらないテストも、同じ一覧に出る。

**Why this priority**: テストの結果を読む場所が、公開サイトに無い。これが無ければ、ほかのストーリーはどれも成り立たない。

**Independent Test**: main へのマージの後、公開サイトの開発版からテストレポートを開く。すべてのレーンのテスト（vitest・pytest と、#809・#810 で入れる仕組みのテスト）が同じレポートにあり、題がテストに書いた文のままであることを確かめる。
手元で落ちたテストを 1 つ用意してレポートを作り、理由とスタックが出ることを確かめる。開発版の結果はマージキューを通った run のもので、落ちたテストはほとんど出ないため。

**Acceptance Scenarios**:

1. **Given** 開発版（またはリリース版）のテストレポートがある、**When** 保守者が公開サイトのその側を開く、**Then** 1 回のクリックでテストレポートへ移れる
2. **Given** テストレポートを開いた、**When** テストの一覧を見る、**Then** テストは、テストに書いた題で並び、中の番号（`TF_…`）は出ない
3. **Given** レポートのレーンが、複数のテストの仕組み（vitest・pytest など）で動く、**When** テストレポートを開く、**Then** どの仕組みのテストも 1 つのレポートにあり、プラグインとレーンごとに分かれて並ぶ
4. **Given** 落ちたテストがある、**When** そのテストを開く、**Then** 失敗の理由とスタックが読める
5. **Given** 要件の ID を持たないテストがある、**When** テストの一覧を見る、**Then** そのテストも出ている
6. **Given** 画面や画像を扱うテストが成功した、**When** テストレポートでそのテストを開く、**Then** テストが見た画面の画像か、作った成果物が添付されており、成功が本当かを目で確かめられる。失敗したテストにも同じ添付がある
7. **Given** PR 版を開いた、**When** ページを見る、**Then** テストレポートへのリンクは無く、リンク切れも無い

---

### User Story 2 - 読む人が、定義書の振る舞いの項目から、それを確かめるテストへ飛べる (Priority: P2)

定義書のページで振る舞いの項目を読んだ人が、その項目を確かめるテストをテストレポートで開く。テストレポートの側でも、テストから要件の ID をたどって定義書の項目へ戻れる。

**Why this priority**: 定義書とテストのつながりは、このリポの定義書の中心だ。テストレポートが読める（P1）ようになってから、つなぐ。

**Independent Test**: 定義書の 1 つのコマンドのページを開き、振る舞いの項目からテストレポートへ移る。その項目の ID を持つテストだけが出ることを確かめる。テストの側から、定義書の項目へ戻れることも確かめる。

**Acceptance Scenarios**:

1. **Given** 要件の ID を `verifies` で書いたテストがある、**When** テストレポートでそのテストを開く、**Then** 要件の ID が出ており、定義書のその項目へのリンクになっている
2. **Given** 定義書のページの振る舞いの項目、**When** その項目のテストへのリンクをたどる、**Then** テストレポートで、その項目の ID を持つテストが出る
3. **Given** 定義書のページの振る舞いの項目、**When** その項目を見る、**Then** 合否は出ておらず、テストレポートへのリンクだけがある
4. **Given** PR 版の定義書のページ、**When** 振る舞いの項目を見る、**Then** テストへのリンクは出ない（PR 版にはテストレポートが無い）
5. **Given** つながるテストが無い項目、**When** その項目を見る、**Then** テストへのリンクは出ない（`interface-spec:lint-defs` が、テストに ID が出てこない項目を止めるので、通常は起きない）

---

### User Story 3 - 保守者が、リリース版で、前回の実行との違いと、不安定なテストを読める (Priority: P3)

保守者がリリース版のテストレポートを開くと、前の実行から状態が変わったテスト（新しく落ちた・直った）が分かる。成功と失敗を行き来するテストも、不安定なテストとして分かる。開発版のテストレポートは履歴を持たず、最新の結果だけを出す。

**Why this priority**: 失敗を追う手段になる。ただし、レポートが出て（P1）、定義書とつながって（P2）からでよい。

**Independent Test**: リリース版のテストレポートを、`side=release` の手での起動で 2 回続けて作る。2 回目の履歴のタブに前の回が並び、推移のグラフに 2 回分の値が出ることを確かめる。
状態が変わったテストの印は、前の回の履歴を `generate.py` に渡し、1 つのテストを落としてレポートを作って確かめる。

**Acceptance Scenarios**:

1. **Given** リリース版のテストレポートが前に作られている、**When** 次のリリース版のテストレポートが作られる、**Then** テストごとに過去の実行の状態が並び、前回から状態が変わったテストが分かる
2. **Given** 過去の実行で成功と失敗を行き来したテスト、**When** そのテストを見る、**Then** 不安定なテストとして印が付く。最新の実行で成功していても付く
3. **Given** リリース版のテストレポートが初めて作られる、**When** テストレポートを開く、**Then** 履歴は空で、レポートは作れている
4. **Given** 開発版のテストレポート、**When** 開く、**Then** 履歴は空で、最新の結果だけが出る。開発版のテストレポートを作り直しても、リリース版の履歴は変わらない
5. **Given** リリース版の履歴が 10 回分ある、**When** 次のリリース版のテストレポートが作られる、**Then** 最も古い回が消え、履歴は 10 回分のままである

---

### User Story 4 - 保守者が、自前のテストレポートを保守しなくて済む (Priority: P4)

自前のテストレポートのページと、それを確かめるテストが無くなる。保守者は、表の列や状態の名前を自分で直さない。手元でも、公開と同じテストレポートを作って見られる。

**Why this priority**: 片付けは、替わりのテストレポートが読めるようになってから行う。先に消すと、手元でテストの結果を読む場所が無くなる。

**Independent Test**: 手元でサイトを作り、`development/` の下のテストレポートのページが無いことを確かめる。手元でテストを動かしてテストレポートを作り、開けることを確かめる。

**Acceptance Scenarios**:

1. **Given** この機能が入った、**When** どの条件でサイトを作っても、**Then** 自前のテストレポートのページ（`development/` の下）は作られない
2. **Given** この機能が入った、**When** リポの依存を見る、**Then** sphinx-test-reports は入っていない
3. **Given** 手元でレポートのレーンを動かした、**When** 文書に書いた手順でテストレポートを作る、**Then** 公開と同じ形のテストレポートを手元で開ける
4. **Given** 手元でレポートのレーンを一部しか動かしていない、**When** テストレポートを作る、**Then** 作れて、動かしたレーンのテストだけが出る

---

### Edge Cases

- レポートのレーンのテストが落ちた（結果は残った）: テストレポートを作って公開し、落ちたテストを落ちたと出す
- 開発版で落ちたテスト: 開発版の結果は、マージキューを通った run のものなので、落ちたテストが出るのは、main で流した、結果の無いレーンだけになる。失敗の読み方は、リリース版か手元のテストレポートで確かめる
- レポートのレーンが結果を残さずに止まった: その実行のテストレポートは公開せず、前のテストレポートが残る。止まったレーンが workflow の実行から分かる
- テストの結果に、定義書に無い要件の ID がある: テストレポートには ID をそのまま出す。`interface-spec:lint-defs` が、定義書に無い ID を止める
- 同じ題のテストが複数のレーンにある: レーンとプラグインで見分けられる
- 添付でテストレポートが大きくなる: 添付は今の実行の分だけをレポートに持ち、履歴には持ち越さない。容量が GitHub Pages の上限に近づいたら、公開の流れが知らせる
- 履歴が増え続ける: リリース版の履歴は 10 回を上限とする。上限を超えた古い回は消す。開発版は履歴を持たない
- テストレポートを含めた公開サイトの容量が、GitHub Pages の上限に近づく: 公開の流れが知らせる（028 の決まりのまま）
- 公開サイトを作る run が、テストの結果より先に終わる: 定義書は先に公開する。テストレポートは、結果がそろってから載る
- PR（fork を含む）: テストレポートを作らず、公開サイトに載せない。PR のテストの失敗は CI のログで読む
- 一部のプラグインだけがリリースされた: リリース版のテストレポートのうち、そのプラグインのテストだけが新しいタグの時点に変わる。プラグインに属さないレーン（libs・`.githooks`）は、最も新しいタグのコミットのものを出す（028 の骨組みの文書と同じ決まり）
- この機能が入った直後で、どのプラグインの最新のタグも結果を出せない: リリース版にテストレポートへのリンクは無く、その位置には案内のページがある。プラグインがリリースされるたびに、そのプラグインのテストがレポートに入る
- マージキューが、一部のレーンしか流さなかった: マージの変更が届いたレーンだけが、新しい結果に変わる。届かないレーンは前の結果のままで、開発版のテストレポートには全レーンのテストが出る
- マージキューが、PR の CI で試し済みのレーンを省いた（積のモード）: そのレーンには変更が届いているので、前の結果のままにしない。その変更を試した run（PR の CI など）の結果に替える
- マージキューを通らずに main に入るコミット（リリースの land のバンプやマージのコミット）: そのコミットで入力が変わったレーンを main で流す
- まだ結果の無いレーンがある（足したばかりのレーン・保管の初回）: main で、そのレーンだけを流して埋める
- マージキューで流したが、マージされなかった（落ちた・キューから外れた）: その run の結果は使わない
- 各レーンの結果が、別々のコミットのものになる: レポートで、レーンごとにどのコミットの結果かを読める
- レポートのレーンが増えた・減った: レーンの一覧は 1 か所の定めから決まり、テストレポートに入るレーンがずれない

## Requirements *(mandatory)*

### Functional Requirements

#### テストの結果を残す

- **FR-001**: レポートのレーンは、テストを動かすたびに、Allure が読む形のテストの結果を残さなければならない。
  Allure が公式のアダプタを出している仕組み（vitest・pytest）は、JUnit XML に加えて、そのアダプタの形で残す。
  アダプタの無い仕組みのテストは、アダプタのある仕組みに移すか、Allure が読む形で結果を残す。`node --test` の 2 本は vitest に移す（#809）。bash の `*.test.sh` の形は #810 で決める（2026-11-26 に改めた）
- **FR-002**: レポートのレーンは、nx の `test-*` のレーンすべてとする。プラグインのレーンに加え、libs・`.githooks`・`nx-release` のレーンも含む。`node --test` と bash の `*.test.sh` のレーンは、#809・#810 で入れる（2026-11-26 に改めた）。
  レーンの一覧は 1 か所の定めから決まらなければならず、レーンが増えたときに、一覧から漏れたままにできてはならない
- **FR-003**: テストの結果は、テストに書いた題を、そのテストの名前として持たなければならない
- **FR-004**: テストの結果は、どのプラグイン（またはライブラリ）のどのレーンのテストかを持たなければならない
- **FR-005**: `verifies` で要件の ID を書いたテストは、テストの結果にその ID を持たなければならない。ID は、Allure が要件や外部の項目とのつながりのために用意している項目に入れ、独自の項目を作ってはならない
- **FR-006**: `verifies` の書き方は変えてはならない。今あるテストを書き直さずに、FR-005 を満たす
- **FR-007**: テストの結果を残すことで、テストの成否・JUnit XML の中身・カバレッジの閾値の判定を変えてはならない
- **FR-007a**: レポートのレーンのうち、ブラウザで画面を開くテストと、画像・PDF・スライドを作るテスト（interface-spec の `test-site`、pecot-visual の e2e など）は、テストが見た画面の画像か、作った成果物を、テストの結果に添付しなければならない。
  成果物が画像なら画像を、PDF・PPTX のように画像でないものは、そのファイルを添付する（2026-11-23、plan の research R11 で改めた）。成功したときも、失敗したときも、毎回添付する。対象のテストの一覧は plan で決める
- **FR-007b**: 添付は、テストが判定に使った画面・成果物そのものから作らなければならない。判定の後で別に作り直した画像を添付してはならない

#### テストレポートを作って公開する

- **FR-008**: テストレポートは、レポートのレーンすべての結果を 1 つにまとめた Allure Report でなければならない
- **FR-009**: テストレポートは、開発版とリリース版に置かなければならない。PR 版には置かない。置く場所は、公開サイトの中の、側ごとに決まった場所とし、作り直しても URL は変わらない
- **FR-009a**: 開発版のテストレポートは、main でテストを流し直さずに作らなければならない。マージキューで流したレーンの結果を、レーンごとに最新の 1 回分だけ持ち、レポートのレーンすべての分を寄せ集めて作る（2026-11-26 に改めた）。
  使うのは、main に入った変更を試した run の結果だけで、マージされなかった変更の run の結果は使わない。結果がまだ無いレーンだけを、main で流す。
  マージキューを通らずに main に入るコミット（リリースの land など）は、そのコミットで入力が変わったレーンを main で流す。キューを通らないコミットの見分け方は #821 で決める。
  PR ごとのテストの結果は、今までどおり CI のログで読む。レポートを作る run は、定義書を公開する流れと分ける
- **FR-009b**: リリース版のテストレポートは、本番のリリースが済むたびに、各プラグインの最新のタグのコミットで、そのプラグインのレーンを動かした結果から作らなければならない。プラグインに属さないレーン（libs・`.githooks`）は、最も新しいタグのコミットで動かす。前に動かした結果を保管して使い回すことはしない
- **FR-009c**: 保守者は、開発版かリリース版かを指定して、テストレポートの作り直しを手で起動できなければならない。コミットは指定させず、起動できるのは main からだけとする（028 の FR-002 と同じ決まり）
- **FR-009d**: 最新のタグのコミットが、Allure が読む結果を出せないプラグイン（この機能が入る前のタグ）は、リリース版のテストレポートに入れない。入っていないプラグインの名前を、リリース版のテストレポートへのリンクのそばに書かなければならない。タグのソースに今の設定をかぶせて動かしてはならない。
  結果を出せるプラグインが 1 つも無い間は、リリース版のテストレポートを作らず、リンクも出さない。その位置には案内のページを置く（FR-010）。プラグインに属さないレーンも、最も新しいタグのコミットが結果を出せるようになってから入れる
- **FR-010**: 開発版とリリース版のページから、その側のテストレポートへ 1 回のクリックで移れなければならない。PR 版には、リンクを出してはならない。リンクを出すかどうかは、サイトを作るときに、側と定義書だけから決める。テストレポートがまだ保管されていない側には、その位置に案内のページを置き、リンク切れを出さない（2026-11-23、plan の research R10 で改めた）
- **FR-011**: 定義書を載せる公開は、テストの結果を待ってはならない（028 の FR-003 を保つ）。テストレポートは、テストの結果がそろってから、定義書のページを作り直さずに足す
- **FR-012**: テストレポートは、レポートのレーンすべての結果がそろったときだけ公開しなければならない（2026-11-26 に改めた）。
  リリース版は、材料（FR-009b）で決めたコミットの結果だけでそろえ、別のコミットの結果で欠けたレーンを埋めてはならない。FR-009d で入れないと決まったレーンを除いて数える。
  開発版は、このマージの変更が届かないレーンを、そのレーンの前の結果で埋める。入力が変わっていないので、前の結果が今のコミットの結果でもある。
  変更が届いたレーンは、マージキューが積のモードで省いたもの（PR の CI で試し済みのもの）も含め、その変更を試した run の結果に替える。取り方は #821 で決める。各レーンの結果がどのコミットのものかを、レポートで読めなければならない
- **FR-013**: ある側のテストレポートを作り直しても、ほかの側のテストレポート・履歴・定義書のページを消したり古い版に戻したりしてはならない
- **FR-014**: テストレポートの公開は、028 の信頼の境界（FR-007・FR-026〜FR-028）に従わなければならない。PR の実行（fork を含む）で、テストレポートと履歴を書き換えてはならない。
  マージキューの run の結果は、main に入ったコミットの分だけを、この境界に従って保管する。置き場所と書く run は #821 で決める。PR とマージキューの run は、リリース版の履歴を書き換えてはならない
- **FR-015**: レポートのレーンのテストが落ちても、結果が残っていれば、テストレポートを作って公開しなければならない。結果を残さずに止まったレーンがあるときは公開せず、前のテストレポートを残す

#### 定義書とつなぐ

- **FR-016**: テストレポートのテストに出る要件の ID は、同じ側の定義書のその項目へのリンクでなければならない
- **FR-017**: 開発版とリリース版の定義書のページの振る舞いの項目は、同じ側のテストレポートで、その項目の ID を持つテストを開くリンクを持たなければならない。定義書のページには合否を出してはならない。リンクは、テストの結果を読まずに、定義書だけから作れなければならない

#### 履歴

- **FR-018**: リリース版のテストレポートは、前の実行までの履歴を読み、テストごとの過去の状態と、前回からの変化を出さなければならない。開発版のテストレポートは履歴を持たず、最新の結果だけを出す（2026-11-26 に改めた）
- **FR-019**: リリース版の履歴は、公開の流れが次の実行で読める S3 のバケットに保管しなければならない。`pages-store` には置かない。10 回分の履歴は、git の 1 ファイルの上限 100 MB を超えるため（2026-11-26 に改めた。バケットと書く run は #822）
- **FR-020**: リリース版の履歴に残す実行の数は 10 回とし、超えた古い回は消さなければならない（2026-11-26 に改めた）
- **FR-020a**: Allure のアダプタが付ける自動のラベル（`host`・`thread` など）を、容量を減らすために落としてはならない。タイムラインがこの 2 つを使う（2026-11-26）
- **FR-021**: 履歴が無いか読めないときも、テストレポートは作れなければならない

#### 片付けと手元

- **FR-022**: 自前のテストレポート（`development/` の下のページ、定義書のページに合否を描く作り、`PECOT_SITE_RESULTS`・`PECOT_SITE_STRICT` の切り替え）と、それだけを確かめるテストを消さなければならない。sphinx-test-reports への依存も消す
- **FR-023**: 自前のテストレポートのためだけにある仕組み（JUnit を読むレーンの定めなど）は、ほかに使う所が無ければ消さなければならない。CI が使う JUnit XML の出力は残す
- **FR-024**: 保守者は、手元で動かしたテストの結果から、公開と同じ形のテストレポートを作って開けなければならない。手順を保守者の文書に書く
- **FR-025**: 028 の spec のうち、この機能で変わる決まり（自前の合否を手元で出す FR-014〜FR-019 など）は、この機能の中で改めなければならない

### Key Entities

- **テストの結果**: 1 回のテストの実行が残す記録。テストの題・状態・時間・失敗の理由とスタック・プラグインとレーン・要件の ID・添付を持つ
- **テストレポート**: レポートのレーンすべての結果から作った Allure Report。開発版はレーンの最新の結果から、リリース版は材料のコミットの結果と履歴から作る。公開サイトの中の決まった場所にある
- **レーンの最新の結果**: 開発版のための、レーンごとの最新の 1 回分の結果と、それを流したコミット。main に入ったコミットの結果だけを持ち、新しい結果で置き換わる。置き場所は #821 で決める
- **履歴**: リリース版だけが持つ、過去の実行のテストの状態の要約。10 回分を上限とし、S3 に置く
- **レポートのレーン**: テストレポートに結果を入れるテストのレーンの一覧。1 か所の定めから決まる
- **要件の ID**: 定義書の振る舞いの項目の ID。テストの結果と定義書のページを、両方の向きにつなぐ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 公開サイトの開発版とリリース版から、1 回のクリックでテストレポートを開ける
- **SC-002**: レポートのレーンで動いたテストの 100% が、テストレポートに、書いた題で出る。中の番号だけで出るテストは 0 件である
- **SC-003**: `verifies` で要件の ID を書いたテストの 100% が、テストレポートで ID を持ち、定義書の項目へ移れる
- **SC-004**: 定義書の振る舞いの項目のうち、つながるテストがある項目の 100% から、テストレポートのそのテストへ移れる
- **SC-005**: 落ちたテストの 100% で、失敗の理由とスタックをテストレポートで読める
- **SC-006**: リリース版で 2 回目以降に作ったテストレポートで、前回から状態が変わったテストが見分けられる
- **SC-007**: 定義書の公開にかかる時間が、この機能を入れる前より延びない（テストの結果を待たない）
- **SC-008**: main へのマージとリリースの後、テストの結果がそろってから 30 分以内に、人が手を加えずに、テストレポートがその結果に変わる
- **SC-009**: 自前のテストレポートのページと、sphinx-test-reports への依存が 0 件である
- **SC-010**: テストレポートを含めた公開サイトのリンク切れが 0 件である
- **SC-011**: 画面や画像を扱うテスト（FR-007a の対象）の 100% で、成功・失敗のどちらでも、テストレポートに、画面の画像か成果物の添付がある

## Assumptions

- テストレポートは Allure Report で作る。ほかのレポートの道具とは比べない（Epic で決まっている）
- Allure の版・結果を残す道具・履歴の持ち方は、plan の工程で、Allure の公式の文書の現行の版を読んで決める
- 公開サイトの作り・側・保管ブランチ・信頼の境界は、028 のものをそのまま使う
- テストは、PR の CI と同じく、外部の資格情報なしで動く
- テストレポートの画面の言葉は、Allure が持つ日本語の表示を使う。自前で訳したり、状態の名前を付け替えたりしない
- リリース版の履歴の 10 回は、Allure のグラフの既定（`DEFAULT_CHART_HISTORY_LIMIT = 10`）と同じ回数にした
- S3 のバケットは、プロジェクトアカウントの ap-southeast-2 に置く。Actions は OIDC のロールで入る（#822）
- 公開サイトとテストレポートは、だれでも読める。テストの結果と添付に、秘密の値は入らない（今の CI のログと同じ前提）
