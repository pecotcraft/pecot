## 背景

pecot の開発者は、変更をマージの前に、本物に近い形で確かめる場所を持っていない。
確かめは、このリポか、そのつど作った場所で行われている。

| 今の姿 | 起きたこと |
|---|---|
| GitHub に書き込む処理は、このリポで確かめている | #454 では、直した処理をこのリポの merge queue で初めて動かした。誤りは、PR が queue に入った後で見つかった |
| 検証用のリポが使い捨てになっている | #374 で検証用のリポを 2 つ作った。このリポとそろえて保つ決まりが無い |
| 直したプラグインを、マージ前に動かす手順が無い | #454 では、直したスキルを読み込み直したのに、古い版が動いた |
| 利用者へ配る自動化は、このリポの main に入れないと動かない | ボードの同期の workflow の変更は、main に入った後でしか確かめられない |
| 作業の順番が、確かめる場所の欠けで決まっている | 配られたもので確かめる変更は、前の変更のマージを待つと決めている |

この文書では、次の語を使う。

| 語 | 指すもの |
|---|---|
| 本番 | 公開された pecot を使っている利用者の環境。この文書の本文では、この語を使わない |
| このリポ | `pecotcraft/pecot` とボード `pecot-project`。開発の環境。開発中のプラグインを読み込んで、開発の Issue・PR・ボードを動かしている。確かめで乱れると、開発が止まる |
| 検証用 | main に入れる前の変更を動かす場所。リポ `pecotcraft/pecot-sandbox` とボード `pecot sandbox` |
| 配る自動化 | 利用者のリポに置く自動化。今は、ボードの同期の workflow |
| このリポだけの運用 | 利用者へ配らない仕組み。このリポのリリースの workflow、CI、依存の更新と脆弱性の通知、workflow を外から起こす仕組み。利用者へ配るリリースの処理（w-release）は入らない |
| 試験環境 | マージ前の変更を確かめる場所の総称 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - GitHub に書き込む変更を、このリポを触らずに最後まで動かして確かめる (Priority: P1)

pecot の開発者は、GitHub に書き込む処理を直す。Issue と PR の作成、マージ、ボードの移動といった処理だ。
開発者は、直した処理を、マージの前に実物の GitHub で最後まで動かしたい。
今は、動かせる先がこのリポしか決まっていない。失敗すると、このリポの merge queue とボードが乱れる。
失敗する場合（チェックが落ちる、queue から外される）は、このリポでは起こせないので、確かめないまま出している。

例: #454 では、直したマージの手順をこのリポの merge queue で初めて動かし、PR が queue に入った後で誤りが見つかった。

**Why this priority**: このリポへの書き込みは、失敗したときの影響がいちばん大きい。ほかの story も、この検証用を書き込む先に使う。

**Independent Test**: GitHub に書き込む処理を 1 つ選び、検証用で最後まで動かす。このリポとボードに何も増えていないのを見る。

**Acceptance Scenarios**:

1. **Given** GitHub に書き込む処理を直したブランチ, **When** その処理を検証用で動かす, **Then** このリポと同じ決まりのもとで最後まで進む。決まりは、必須のチェック・merge queue・マージ方式・ボードの値を指す
2. **Given** 検証用で処理を動かした, **When** このリポとボードを見る, **Then** Issue・PR・ブランチ・カードは、増えておらず、動いてもいない
3. **Given** 失敗する場合を確かめたい, **When** 検証用でわざと失敗を起こす, **Then** 失敗したときの処理の動きを、このリポを使わずに見られる
4. **Given** このリポの決まりを変えたのに、検証用が追いついていない, **When** 設定を比べる, **Then** ずれた項目と、このリポ・検証用それぞれの値が分かる
5. **Given** 前の確かめが、検証用に Issue・PR・ブランチを残した, **When** 次の確かめを始める, **Then** 残ったものは次の結果を変えない
6. **Given** 2 人が同時に検証用で確かめる, **When** それぞれが処理を動かす, **Then** 互いの結果を変えない

---

### User Story 2 - 直した pecot-workflow を、マージの前に、利用者と同じ形で動かして確かめる (Priority: P1)

pecot の開発者は、pecot-workflow の中身（スキル・フック・MCP ツール・エージェント）を直す。
開発者は、直した中身を、利用者が使うのと同じ形で、マージの前に動かしたい。
今は、その手順が決まっていない。直したつもりで、入れてある古い版を動かしていても気づけない。
利用者は Claude Code と GitHub Copilot CLI のどちらも使うので、両方で動かせる必要がある。

例: #454 では、直したスキルを読み込み直した後に起動したら、古い版の本文で動いた。

**Why this priority**: pecot-workflow は配布物の中心で、変更の大半がここに入る。User Story 1 の確かめも、直した中身で動かせて初めて、マージ前の確かめになる。

**Independent Test**: pecot-workflow の中身を 1 か所直し、手順どおりに動かして、直した後の中身で動くのを見る。ふだんの使い方では、入れてある版のままで動くのを見る。2 つのクライアントのそれぞれで行う。

**Acceptance Scenarios**:

1. **Given** pecot-workflow のスキル・フック・MCP ツール・エージェントのどれかを直したブランチ, **When** 手順どおりに動かす, **Then** 直した後の中身で動く
2. **Given** pecot-workflow の配られた版も入っている, **When** 動かす前に確かめる, **Then** どちらの中身が動くのかが分かる
3. **Given** ブランチの中身で確かめ終わった, **When** ふだんどおりに使う, **Then** 配られた版で動く
4. **Given** GitHub Copilot CLI を使う開発者, **When** 同じ目的の手順を踏む, **Then** 直した後の中身で動く
5. **Given** どちらかのクライアントで動かせないものがある, **When** 手順を読む, **Then** 動かせる範囲と動かせない範囲が書いてある

### User Story 3 - 利用者へ配る自動化の変更を、main に入れる前に実際に起こして確かめる (Priority: P2)

pecot は、プラグインのほかに、利用者のリポに置く自動化を配る。今は、ボードの同期の workflow がこれに当たる。
開発者は、直した自動化を、main へ入れる前に、実際に起こして結果を見たい。
今は、このリポの main に入れないと動かない。誤りがあると、このリポのボードの同期が止まる。同じ誤りが、利用者にも配られる。

このリポだけの運用は、利用者へ配らない。リリース、依存の更新と脆弱性の通知、workflow を外から起こす仕組みがこれに当たる。
これらを確かめる場所は、要るときが来たら作る。この story の完了の条件には入れない。

**Why this priority**: 配る自動化の誤りは、利用者のボードを乱す。ただし、変更の回数はプラグインより少ない。

**Independent Test**: 配る自動化を 1 か所直し、main へ入れる前に検証用で起こして、結果が検証用のボードだけに出るのを見る。このリポのボードが変わっていないのを見る。

**Acceptance Scenarios**:

1. **Given** 利用者へ配る自動化を直したブランチ, **When** main へ入れる前の定義を、検証用で起こす, **Then** 直した後の定義で動き、結果は検証用にだけ出る
2. **Given** 検証用で自動化を動かした, **When** このリポを見る, **Then** 自動化の定義も、ボードも、変わっていない
3. **Given** 確かめ終わった, **When** 時間がたつ, **Then** 検証用の自動化は、定期の起動で検証用を書き換え続けない
4. **Given** このリポだけの運用を直したブランチ, **When** 開発の文書を読む, **Then** 確かめる場所の有無と、無いときの確かめ方が書いてある

### User Story 4 - どこで確かめるかを計画が示し、確かめがこのリポで流れない (Priority: P2)

エージェントは、変更の計画に CUJ（利用者の操作の流れ）を書き、実装の後に流して確かめる。
開発者は、計画を読んだだけで、どの CUJ がどこで流れるのかを知りたい。
今の計画には、流す先を書く場所が無い。外へ書き込む CUJ は、ほかに先が決まっていないのでこのリポで流れる。
試験環境があっても、計画が流す先を示さなければ、確かめはこのリポで流れ続ける。

pecot を自分のリポで使う利用者には、検証用が無い。この決まりで、利用者の作業が止まってはならない。

**Why this priority**: User Story 1〜3 の試験環境を、日々の作業で使わせる仕組みだ。試験環境ができてから意味を持つ。

**Independent Test**: 外へ書き込む CUJ を含む変更で計画を作り、CUJ ごとに流す先が書かれているのを見る。CUJ を流し、書き込みが検証用にだけ届いたのを見る。

**Acceptance Scenarios**:

1. **Given** 外へ書き込む CUJ を含む変更, **When** 計画を作る, **Then** CUJ ごとに、流す先が計画に書かれる
2. **Given** 流す先が検証用の CUJ, **When** CUJ を流す, **Then** 書き込みは検証用にだけ届き、結果に検証用での証拠が残る
3. **Given** 流す先が書かれていない CUJ, **When** 計画をレビューする, **Then** 欠けとして挙がる
4. **Given** pecot の開発の計画で、流す先がこのリポの CUJ, **When** 計画をレビューする, **Then** このリポで流す計画として挙がる
5. **Given** 外へ書き込まない CUJ, **When** 計画を作る, **Then** 計画を読めば、試験環境の要らない CUJ だと分かる
6. **Given** 検証用を持たない利用者のリポ, **When** 同じ手順で計画を作って CUJ を流す, **Then** 止まらずに終わる

### User Story 5 - 人のいないセッションでも、同じ試験環境で確かめる (Priority: P3)

開発者は、Issue をクラウドのセッションに任せて席を離れる。
開発者は、そのセッションにも、手元と同じ試験環境で確かめまで進めてほしい。
今は、人のいないセッションに、検証用へ書き込む権限を渡す手順が無い。確かめは流せないか、このリポで流すことになる。
渡す権限は、検証用に限りたい。人が見ていないセッションに、このリポへ書き込む権限を持たせたくないからだ。

**Why this priority**: クラウドのセッションに任せる作業は、これから増える。ただし、手元で確かめられる試験環境が先に要る。

**Independent Test**: クラウドのセッションで、User Story 1 と同じ確かめを 1 つ流し、人が 1 度も操作せずに終わるのを見る。同じ権限でこのリポへの書き込みを試し、拒まれるのを見る。

**Acceptance Scenarios**:

1. **Given** クラウドのセッションが始まった, **When** 決まった手順で検証用の権限を受け取る, **Then** 人が操作せずに、検証用での確かめが最後まで流れる
2. **Given** 検証用の権限, **When** このリポへ書き込もうとする, **Then** 拒まれる
3. **Given** 手元のセッションとクラウドのセッション, **When** 同じ確かめを流す, **Then** 同じ試験環境で、同じ結果になる
4. **Given** 検証用の権限が無い、または切れている, **When** 確かめを流そうとする, **Then** 訳を知らせて止まり、このリポへ書き込める権限に切り替えない
5. **Given** クラウドのセッションでできないことが分かった, **When** 文書を読む, **Then** できる範囲とできない範囲が書いてある

---

### User Story 6 - 確かめる場所の都合で、作業の順番を待たされない (Priority: P3)

エージェントは、Epic をフェーズに分け、フェーズの前後を決める。
開発者は、前のフェーズのマージを待たずに、次のフェーズをスタックして進めたい。
今の決まりは、「配られたもので確かめる変更は、前のマージを待つ」としている。
これは、マージ前の変更で確かめる場所が無いことから来た決まりだ。試験環境ができれば、待つ訳が無くなる。

例: 「スキルを直す」フェーズの次に「直したスキルを使って確かめる」フェーズがあると、今は、前のマージと配布が終わるまで着手できない。

**Why this priority**: 決まりは、試験環境で確かめられると分かるまで直せない。効果は、待ちが減ることに出る。

**Independent Test**: 前のフェーズで直したものを使って確かめるフェーズを含む計画を用意し、前後の種類を決めさせる。「待つ」ではなく「スタックできる」になるのを見る。

**Acceptance Scenarios**:

1. **Given** 次のフェーズの確かめが、前のフェーズで直したもの（プラグイン・自動化）を使う, **When** 前後の種類を決める, **Then** 「スタックできる」になる
2. **Given** 試験環境でも確かめられない依存, **When** 前後の種類を決める, **Then** 「マージを待つ」になり、試験環境で確かめられない訳が理由に書かれる
3. **Given** 直した後の決まり, **When** 「マージを待つ」になる例を読む, **Then** 試験環境で確かめられるもの（pecot-workflow・配る自動化）を訳にする例が無い

---

### Edge Cases

- 確かめが途中で失敗して止まったとき、検証用に残ったものは、次の確かめの前に片付くか
- 片付けが、確かめで作ったもの以外（検証用を成り立たせている設定や定義）を消さないか
- このリポの決まりを変える変更を出すとき、検証用を先に変えるのか、後で追いつかせるのか
- 2 人が同時に、別々のブランチの配る自動化を検証用で起こそうとしたとき、どちらが動くか
- 検証用の権限が、同じ org にあるこのリポのボードに届かないか
- 検証用が障害で使えないとき、確かめをこのリポで流す例外を認めるか

## Requirements *(mandatory)*

### Functional Requirements

**このリポと同じにするもの**

検証用は、次の点でこのリポと同じでなければならない。違うと、検証用で通ったものがこのリポで止まる。

| ID | 同じにするもの | 訳 | 今 |
|---|---|---|---|
| FR-001 | マージの決まり（マージ方式・必須のチェック・merge queue・PR の規則） | PR を作る処理とマージする処理が、この決まりを相手に動く | 同じ |
| FR-002 | ボードの項目と値（列・優先度・大きさ・状態）と、ボードの設定ファイルの名前の形（`<host>_<owner>_<number>.json` か、#701 の前の形か）と、設定ファイルが持つ欄と選択肢のキー | ボードを動かす処理が、値の名前を読む。`project activate` の引数と `project` の入力は、設定ファイルの名前で設定を指す。CLI は workflow・status の欄で、選択肢のキーから ID を引く。設定にキーが無いと、その札を動かせない | 同じ |
| FR-003 | 検証用での確かめに要る自動化（必須のチェックを出す CI・配るボードの同期・配る自動レビュー） | 検証用に置かれていないと、検証用で確かめられない | 同じ |

**同じにしなくてよいもの**

次の点は、このリポとそろえない。ずれとして扱わない。

| ID | そろえないもの | 訳 |
|---|---|---|
| FR-004 | コードの脆弱性を調べる規則 | 確かめるのは pecot の動きで、検証用のコードの安全ではない |
| FR-005 | ボードの列の項目の名前 | pecot の仕様で、名前はプロジェクトごとに変わる |
| FR-006 | ボードとリポの公開範囲 | 試し用の Issue を広く見せる訳が無い。ただし、merge queue が使える範囲に置く |
| FR-007 | Issue・PR・コードの中身（ボードの設定ファイルの名前の形と、持つ欄と選択肢のキーは、FR-002 で比べる） | 確かめがそのつど作る |
| FR-008 | このリポだけの運用（リリース・公開サイト・依存の更新・脆弱性の通知・workflow を外から起こす仕組み）。リリースのタグと公開サイトの保管ブランチを守る ruleset も含む | 利用者へ配らない。確かめる場所は、要るときに作る |

**ほかのやり方と同じにするもの**

公式の文書と、実物の GitHub に書き込むプロジェクトのやり方に合わせる。出典は Assumptions の表にある。

| ID | 要件 | 合わせる先 |
|---|---|---|
| FR-009 | 検証用を、使い捨てにせず長く使う。今ある検証用を引き継ぐ | gh CLI、terraform の GitHub provider |
| FR-010 | 確かめが検証用に作ったものを、確かめで作ったと見分けられ、まとめて片付けられる | terraform の GitHub provider |
| FR-011 | 同時に流した確かめが、互いの結果を変えない | gh CLI |
| FR-012 | 検証用での確かめを、PR ごとの CI では流さない。人かエージェントが始める | gh CLI |
| FR-013 | CI のテストは、偽の応答で動く今の形のままにする | probot、octokit |
| FR-014 | 直した pecot-workflow を動かす手順は、各クライアントの公式の読み込み方に従う。独自の読み込み方を作らない | Claude Code と GitHub Copilot CLI の公式の文書 |
| FR-015 | どの中身が動いているかの確認は、各クライアントの公式の手段に従う。独自の表示を作らない | 同上 |

## Assumptions

- 利用者は、pecot を開発する人とエージェントである。試験環境は pecot の開発のためのもので、配布しない
- 配布物に入るのは、計画が流す先を示す決まり、CUJ を流す手順とレビューの手順、フェーズの前後の決まりだけ
- どう作るかは plan で決める。自動化を分けて置く先の形、設定を比べる手段、権限の渡し方、片付けの形がこれに当たる
- 2026-11-16 に比べた時点で、検証用は FR-001〜003 でこのリポと同じだった
- 検証用が障害で使えないときに、確かめをこのリポで流す例外は認めない。認めるときは、ユーザーの明示の承認が要る
- このリポの決まりを変える変更は、検証用の決まりを先に変えて確かめる。main へ入れた後で設定を比べ、ずれが無いことを見る
- 配る自動化の確かめは、1 度に 1 人が行う。検証用の既定のブランチに置ける定義は 1 つだからだ
- 検証用の権限が、同じ org にあるこのリポのボードに届くかは確かめていない。届くと分かったときは、計画に書いてユーザーの承認を得る
- 関連: #454（マージの確かめをこのリポの merge queue で実施）、#374（検証用のリポを作成）、#47（フェーズの前後の決まり）、#49（振る舞いを測る仕組み）
