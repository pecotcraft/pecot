# Feature Specification: CLI と MCP のインタフェース定義書を正として持ち、テストを振る舞いの資料として読める

**Feature Branch**: `022-interface-definitions`

**Created**: 2026-11-10

**Status**: Draft

**Input**: Epic pecotcraft/pecot#199。CLI のコマンドと MCP のツールを構造化した定義書に書き、定義書と実装の食い違いを CI が止める。テストの名前と構成に規約を置き、テストの結果からコマンド・ツールごとの振る舞いの一覧を作る。

## Clarifications

### Session 2026-11-10

- Q: pecot-workflow の振る舞いの項目は、#42 で消える予定の今の pytest につなぐか → A: つなぐ。項目の ID を pytest に足し、名前と中身は直さない。移行のときに、つなぎ先を Node のテストへ移す（FR-019、Assumptions）
- Q: 定義書のうち実装から機械的に取れる部分は、どう保つか → A: 実装から書き出してリポジトリに入れる。実装を変えて書き出し直さないと CI が止まる。人が書くのは、実装から取れない項目だけにする（FR-006、FR-021）
- Q: 人が書く項目とテスト名は何語で書くか → A: 振る舞いの項目の文とテスト名は日本語で書く。読むのは人だ。定義書のそれ以外の欄は英語で書き、人が読むときは訳して読む。欄ごとに言語は 1 つで、同じ文の訳をリポジトリに持たない（FR-022）
- Q: 定義書に何を書けば足りるかを、何に照らして決めるか → A: 確立した枠組みに照らす。1 コマンド・1 ツールに書く節は POSIX のユーティリティ記述の節立てに対応づける。何を書き何を書かないかは Diátaxis のリファレンスに従う。振る舞いの項目の文は EARS の型で書く。テストとのつなぎは、要件とテストの双方向の追跡と網羅の考え方に従う（FR-003、FR-023〜FR-026）

## 背景

「このコマンド・ツールは何をし、何を受け付け、何を処理するか」と問われたとき、今見せられるものはコードか `--help` しか無い。

| | pecot-workflow | pecot-tools | pecot-visual |
|---|---|---|---|
| 公開面 | CLI のサブコマンド 30 余り | MCP ツール約 30 | MCP ツール約 10 |
| 引数・型・既定値・説明のある場所 | typer の定義 | zod の定義 | zod の定義 |
| 処理の内容・副作用・終了コードのある場所 | コードの中だけ | コードの中だけ | コードの中だけ |
| 手書きの資料 | `skills/w-help/references/commands.md`。実装との一致を確かめるものは無い | 無い | 無い |
| テスト名 | pytest の英語の識別子（`test_hash_only_rejected`）。約 2,100 件 | vitest の振る舞いの文。約 380 件 | vitest。約 3,000 件 |

- 設計時の契約は保守されない。`specs/020-workflow-ts-mcp/contracts/mcp-tools.md` などは、その spec の作業が終わると更新されない
- テスト名の書き方は言語ごと・書いた人ごとに違う。`.claude/rules/` にテストの書き方の規則は無い

サブタスク #200（#199-01）で、仕様の項目とテストをつなぐツールを sphinx-needs に決めた。StrictDoc と並べて、このリポの vitest と pytest で試した結果だ。

- テストが、確かめる項目の ID を JUnit の結果に書き出す。ツールが結果を取り込み、項目ごとに結んだテストと合否を HTML に出す
- 結んだテストが 1 件も無い項目は、設定で CI を落とせる
- 項目の書き損じ（閉じ忘れ・存在しない ID・必須の欄の欠け）は、行番号つきで出る

ほかの Epic との関係:

- Epic #42 は、pecot-workflow の CLI を Python から TypeScript と MCP に移す。定義書を移行の前に作ると、移行の前後で公開面が同じことを確かめる契約に使える。そのため pecot-workflow の定義書を最初に作る。今の `pecot` の実体は Python の CLI で、`cli-node/` はコマンドが未登録だ
- Epic #185（CLI の出力を英語の共通の関数にそろえる）— `--help` の文言を英語にする PR #227 がレビュー中だ。定義書の説明文は実装の定義と一致させるので、初版は #227 のマージ後の main から採る

## User Scenarios & Testing *(mandatory)*

### User Story 1 - pecot-workflow の定義書があり、CLI の定義と食い違うと CI が止める (Priority: P1)

pecot-workflow の保守者（人・エージェント）が、あるコマンドの機能・引数・処理・副作用・終了コードを知りたいとき、定義書の 1 か所を読む。定義書のうち、引数・型・既定値・説明は実装から書き出す。
詳しい説明・副作用・終了コード・振る舞いの項目は人が書く。コマンドに引数を足す PR は、定義書を書き出し直さない限り CI が通らない。Epic #42 の移行では、同じ定義書で Node の CLI と MCP ツールを確かめる。

**Why this priority**: Epic #42 の移行の契約になる。移行の前に無いと、移行の前後の一致を確かめる基準が Python の出力の golden だけになる。定義書の形式も、ここで実物に当てて決まる。

**Independent Test**: 実装から書き出したものと定義書を比べる確認を流し、一致することを確かめる。次に、実装の引数を 1 つ足す・既定値を変える・説明を変える、の 3 つをそれぞれ試し、テストが落ちることを確かめる。

**Acceptance Scenarios**:

1. **Given** pecot-workflow の定義書、**When** 任意のサブコマンドの項目を読む、**Then** FR-003 の内容がその項目にそろっている
2. **Given** 定義書と一致している main、**When** CLI のコマンドに引数を 1 つ足し、定義書を書き出し直さずに PR を出す、**Then** 一致の確認が失敗し、食い違ったコマンドと引数の名前を示す
3. **Given** 同じ main、**When** 実装にコマンドを足して書き出し直す、**Then** 形式の検証が失敗し、人が書く項目の空のコマンドを示す
4. **Given** 同じ main、**When** 引数の型・必須か・既定値・許可値・説明のどれかを、実装か定義書の片方だけ変える、**Then** 一致の確認が失敗する
5. **Given** 定義書、**When** 定義書の形式そのものに合わない項目（必須の項目の欠落、知らない項目）を書く、**Then** 形式の検証が失敗する

---

### User Story 2 - pecot-tools と pecot-visual の MCP ツールにも定義書があり、食い違うと CI が止める (Priority: P2)

pecot-tools と pecot-visual の MCP ツールも、同じ形式の定義書を持つ。ツールの入力を変える PR は、定義書を直さないと通らない。

**Why this priority**: 3 プラグインの公開面が同じ形式で読めるようになる。MCP ツールは zod の定義から引数が機械的に取れるので、pecot-workflow で形式を決めた後に合わせる。

**Independent Test**: 2 プラグインの定義書を、MCP サーバが返すツールの一覧と比べるテストを流す。ツールの入力を 1 つ変えて、テストが落ちることを確かめる。

**Acceptance Scenarios**:

1. **Given** pecot-tools・pecot-visual の定義書、**When** MCP サーバが返すツールの一覧と比べる、**Then** ツールの名前・説明・入力の項目が一致する
2. **Given** 一致している main、**When** ツールを 1 つ足す・入力の項目を 1 つ変える、**Then** 一致の確認が失敗する
3. **Given** pecot-tools の定義書、**When** AWS を呼ぶツールの項目を読む、**Then** 実行する AWS の操作と、読み取りだけか書き込みを伴うかが、外部への副作用として書かれている

---

### User Story 3 - 定義書から、人が読む表示と w-help のリファレンスを作る (Priority: P2)

定義書から、人がブラウザで読める表示を生成できる。w-help スキルのコマンド一覧も定義書から作られ、手で書かない。生成物が定義書より古いと CI が止める。

**Why this priority**: 定義書を「見せるもの」にする。w-help の手書きのリファレンスが実装と食い違う問題も、同じ仕組みで無くなる。w-help のコマンド一覧を先に届ける。ブラウザで読む表示は、振る舞いの一覧（User Story 5）と同じ HTML で作るので、同じ時期に届く。

**Independent Test**: 生成のコマンドを動かし、表示と w-help のリファレンスが出ることを確かめる。定義書の説明を 1 つ変えて生成し直さずに生成物の確認を動かし、止まることを確かめる。

**Acceptance Scenarios**:

1. **Given** 3 プラグインの定義書、**When** 表示を生成する、**Then** プラグインごとに、全コマンド・全ツールの項目が 1 つの表示にまとまって出る
2. **Given** pecot-workflow の定義書、**When** w-help のリファレンスを生成する、**Then** コマンド一覧が定義書の内容で書かれ、手書きの部分が残らない
3. **Given** 生成済みの w-help のリファレンス、**When** 定義書だけを変えて PR を出す、**Then** 生成物が古いことを生成物の確認が見つけて失敗する
4. **Given** 配布物としての pecot-workflow、**When** 利用環境のエージェントが w-help を読む、**Then** 生成されたリファレンスだけで、コマンドと引数が分かる。利用環境で生成の処理は動かない

---

### User Story 4 - テストが確かめる項目を名指しし、名前と構成から振る舞いが読める (Priority: P2)

定義書の各コマンド・ツールは、振る舞いの項目（ID と文）を持つ。テストを書く人（人・エージェント）は、テストがどの振る舞いの項目を確かめるかを、テストに書く。規約は、テスト名の文の形・構成の単位（コマンド・ツールごと）・項目へのつなぎ方を決める。規約に外れたテストは lint が止める。

**Why this priority**: テストを振る舞いの資料として読むための前提になる。項目へのつなぎが無いと、テストの結果をコマンド・ツールごとに並べられない。

**Independent Test**: 規約に外れた名前のテストを 1 件足して lint を動かし、止まることを確かめる。存在しない ID につないだテストを 1 件足し、止まることを確かめる。

**Acceptance Scenarios**:

1. **Given** テストの規約、**When** `.claude/rules/` の規則を読む、**Then** FR-012 の 3 つの決めが、vitest と pytest の例つきで書かれている
2. **Given** 規約の対象のテスト、**When** 規約に外れた名前のテストを足す、**Then** lint が失敗し、外れた箇所と規約の場所を示す
3. **Given** 定義書の振る舞いの項目、**When** 存在しない ID につないだテストを足す、**Then** CI が失敗し、そのテストの場所を示す
4. **Given** パラメータ化したテスト、**When** 入力の行ごとに違う項目を確かめる、**Then** 行ごとに別の項目へつなげる
5. **Given** 規約の適用の前からあるテスト、**When** lint を動かす、**Then** 規約の対象に入れた範囲では、外れたテストが残っていない

---

### User Story 5 - テストの結果から、項目ごとの振る舞いと合否の一覧を作り、テストの無い項目を CI が止める (Priority: P3)

テストの実行結果から、コマンド・ツールごとに、振る舞いの項目・結んだテスト・合否を並べた一覧を生成できる。定義書の表示から、そのコマンド・ツールの一覧をたどれる。結んだテストが 1 件も無い振る舞いの項目があると、CI が止める。

**Why this priority**: 定義書（何を受け付けるか）と対になる、振る舞いの資料になる。定義書（User Story 1・2）と、項目へのつなぎ（User Story 4）がそろってから作れる。

**Independent Test**: テストを流して一覧を生成し、任意のコマンド 1 つについて、振る舞いの項目ごとに結んだテストと合否が並ぶことを確かめる。テストの無い項目を 1 つ足し、CI が止まることを確かめる。

**Acceptance Scenarios**:

1. **Given** 項目につないだテストの実行結果、**When** 一覧を生成する、**Then** コマンド・ツールごとに、振る舞いの項目・結んだテスト・合否が並ぶ
2. **Given** 定義書の振る舞いの項目、**When** 結んだテストが 1 件も無い項目を足す、**Then** CI が失敗し、その項目の ID を示す
3. **Given** 生成した表示、**When** あるコマンド・ツールの項目を開く、**Then** その振る舞いの一覧を同じ表示の中でたどれる
4. **Given** vitest のテストと pytest のテスト、**When** 一覧を生成する、**Then** どちらの結果も同じ一覧に入る

---

### Edge Cases

- 利用者に見せない内部用のコマンド（`--help` に出さないもの）も、定義書に載せる。見せないことは項目の属性で表す
- 既定値が実行時の環境で決まる引数（現在のリポ、設定ファイルの値など）は、定義書に固定の値を書けない。決まり方を書く形を持つ
- 引数どうしの排他と依存、詳しい説明、副作用、終了の状態は、実装の定義から機械的に取れない。一致の確認の対象は機械的に取れる項目に限り、書き起こした項目は形式の検証（必須の項目があること）だけで守る
- 1 つの操作が CLI のコマンドと MCP ツールの両方で公開される（Epic #42 の移行後の pecot-workflow）ときは、定義書の 1 つの項目が両方を指し、両方と一致を確かめる
- pecot-tools のツールは許可リストから作られる。許可リストにコマンドを足すと、定義書にも項目を足さない限り CI が通らない
- 1 件のテストが複数の振る舞いの項目を確かめるときは、複数の項目へつなげる
- どの項目にも属さないテスト（ドメイン層の単体テストなど）は、項目へつながなくてよい。一覧には出ない
- 定義書の項目と、つなぐツールが読む項目を別々に手で書くと、2 つが食い違う。項目の源は定義書の 1 つにする
- 失敗したテストは、一覧に失敗として出る。CI を落とすのは、今のテストのレーンが担う
- 変更が届いたレーンだけを CI が動かすので、定義書だけを変えた PR でも、一致の確認と生成物の確認が動く
- Epic #185 の PR が説明文を変えると、定義書の説明も同じ PR で直すことになる

## Requirements *(mandatory)*

### Functional Requirements

| ID | 要件 |
|---|---|
| FR-001 | 3 プラグインは、それぞれ自分の公開面の定義書を持つ。公開面は、pecot-workflow の CLI の全サブコマンド、pecot-tools と pecot-visual の全 MCP ツールとする |
| FR-002 | 定義書は、機械が読める構造化した形式で書く。形式は 3 プラグインで同じにし、形式そのものを検証できる定義（schema）を持つ。実装の言語に依らない |
| FR-003 | 定義書の 1 項目は、POSIX のユーティリティ記述の節に対応する欄を持つ。欄は、名前と説明・使い方（引数の並びと排他・依存）・引数（型・必須か・既定値・許可値）・詳しい説明・標準入力・出力の形・診断の出力・環境変数・終了の状態・失敗の後に残る状態・例とする。加えて、外部への副作用・前提・冪等か・非推奨か・振る舞いの項目（ID と文）を持つ |
| FR-023 | 欄と POSIX の節の対応を、形式の定義と同じ場所（`libs/interface-spec`）に表で持ち、表示にも出す。形式の定義の欄がすべて表にあることを、テストが確かめる。POSIX に節の無い欄（副作用・前提・冪等か・振る舞いの項目）は、借りた先（MCP の annotations・設計契約・要件の書き方）を同じ表に書く |
| FR-024 | 使わない欄は省かず、使わないことを決まった値で明示する。書き忘れと区別できる |
| FR-025 | 詳しい説明の欄には、外から観測できる結果だけを書く。内部の手順・使い方の案内・設計の理由は書かない |
| FR-026 | 振る舞いの項目の文は、EARS の 5 つの型（常時・契機・状態・異常・任意の機能）のどれかで書き、どの型かを項目に持つ。1 つの文に、契機と応答を 1 組だけ書く。形式の検証が、型と文の形の食い違いを止める |
| FR-027 | MCP ツールの副作用の種類（読み取り・書き込み・破壊）と冪等かどうかは、ツールが公開する annotations と食い違うと、形式の検証が止める |
| FR-028 | 環境変数の欄は、実装のソースが読む環境変数の名前と比べる。ソースにあって定義書に無い名前があると、CI が止める |
| FR-004 | 外部への副作用は、相手（GitHub・AWS・git・ファイル・起動するプロセス）と、種類（読み取り・書き込み・破壊）を、項目ごとに書く |
| FR-005 | 定義書の形式は、既存の形式（OpenCLI・usage spec）と自前の形式を比べて決め、選んだ理由を残す。実装から取れない欄を載せる決めも、同じ場所に残す |
| FR-006 | 定義書のうち機械的に取れる項目は、実装の定義から書き出す。対象は、コマンド・ツールの名前の集合、説明、引数の名前・型・必須か・既定値・許可値、非推奨かどうかとする。MCP ツールは、出力の形と annotations も対象にする。リポジトリの定義書が、書き出し直したものと食い違うと CI が落ち、食い違った項目を名指しする |
| FR-007 | 定義書の形式に合わない項目（必須の項目の欠落、知らない項目）は、検証が止める |
| FR-008 | 定義書は実装の言語に依らず、Epic #42 の移行後は、同じ定義書で Node の CLI と MCP ツールの定義にも一致の確認ができる。1 つの項目が CLI のコマンドと MCP ツールの両方を指せる |
| FR-009 | 定義書から、人が読む表示を生成できる。表示はプラグインごとに、全項目を載せる |
| FR-010 | w-help のコマンド一覧（`commands.md`）は、定義書から生成する。生成物はリポジトリに入れて配布し、利用環境では生成しない |
| FR-011 | リポジトリに入れた生成物が定義書より古いと、生成物の確認が止める |
| FR-012 | テストの規約を `.claude/rules/` に置く。規約は、テスト名の文の形・構成の単位・振る舞いの項目へのつなぎ方を、vitest と pytest の例つきで決める |
| FR-013 | 規約の対象のテストで規約に外れたものは、lint が止める。定義書に無い ID につないだテストは、CI が止める |
| FR-014 | 規約の適用の前からあるテストのうち、規約の対象に入れた範囲は、規約に沿うように直す |
| FR-015 | テストの実行結果から、コマンド・ツールごとの振る舞いの一覧を生成できる。一覧は、振る舞いの項目・結んだテスト・合否を並べる。vitest と pytest の結果を同じ一覧に入れる |
| FR-019 | 結んだテストが 1 件も無い振る舞いの項目があると、CI が止める |
| FR-021 | 書き出しは、人が書いた項目（Key Entities の「書き起こす項目」）を消さず、書き換えない |
| FR-022 | 定義書の欄ごとに、書く言語は 1 つに決める。振る舞いの項目の文と vitest のテスト名は日本語、それ以外の欄は英語とする。pytest の関数の名前は対象にしない。同じ文を 2 つの言語で持たない。形式の検証と lint が、欄の言語の外れを止める |
| FR-020 | 定義書の項目と、つなぐツールが読む項目の源は 1 つにする。同じ項目を 2 か所に手で書かない |
| FR-016 | 生成した表示の各項目から、そのコマンド・ツールの振る舞いの一覧をたどれる |
| FR-017 | 一致の確認・形式の検証・生成物の確認・テストの規約の lint・テストの無い項目の確認は、nx のレーンに載り、PR ごとの CI で動く。定義書だけを変えた PR でも動く |
| FR-018 | `specs/020-workflow-ts-mcp/contracts/` など、設計時の契約のうち定義書と重なるものは、定義書を正とする旨を残して重なりを無くす |

### Key Entities

| 名前 | 説明 |
|---|---|
| 定義書 | プラグインの公開面を構造化して書いたもの。プラグインごとに 1 つ。REST API の OpenAPI に当たる |
| 項目 | 定義書の中の、コマンドまたはツール 1 つ分。FR-003 の内容を持つ |
| 振る舞いの項目 | コマンド・ツールの「どのとき、どうするか」を 1 文で書いたもの。ID を持ち、テストがその ID を名指しして確かめる |
| 機械的に取れる項目 | 名前・説明・引数の名前・型・必須か・既定値・許可値・非推奨か。MCP ツールは、出力の形（`outputSchema`）と annotations も取れる。実装の定義から書き出す |
| 書き起こす項目 | 排他と依存・詳しい説明・標準入力・CLI の出力の形・診断の出力・環境変数・終了の状態・失敗の後に残る状態・副作用・前提・冪等か・例・振る舞いの項目。人が書き、形式の検証で守る |
| 一致の確認 | リポジトリの定義書と、実装から書き出し直したものを比べること |
| 生成物 | 定義書から作る、人が読む表示と w-help のリファレンス |
| 生成物の確認 | リポジトリに入れた生成物と、定義書から作り直したものを比べること |
| テストの規約 | テスト名の文の形・構成の単位・振る舞いの項目へのつなぎ方の決め |
| 振る舞いの一覧 | テストの実行結果から作る、コマンド・ツールごとの、振る舞いの項目・結んだテスト・合否の並び |

## Assumptions

| 前提 | 内容 |
|---|---|
| 定義書と実装の向き | 機械的に取れる項目は実装から定義書へ書き出す。定義書から実装の定義を生成する形にはしない。公開面を読む人とツールは、実装ではなく定義書を読む |
| pecot-workflow の比べる相手 | 今の `pecot` の実体の Python の CLI と比べる。`cli-node/` はコマンドが未登録なので、今は比べる相手にしない |
| 言語を分ける理由 | 実装から書き出す説明は Epic #185 の決めで英語になる。詳しい説明・副作用などの欄は、主にエージェントが読むので同じ英語にする。振る舞いの項目の文とテスト名は、一覧と CI の結果で人が読むので日本語にする。pecot-tools のテスト名は今も日本語だ |
| エージェントが読む文書の言語 | w-help のリファレンスに載せるのはコマンドと説明で、振る舞いの項目は載せない。利用環境のエージェントが読む文書に、日本語の欄は入らない |
| 初版を採る時点 | pecot-workflow の初版は、PR #227（`--help` を英語にする）のマージ後の main から採る |
| 表示の置き場 | 人が読む表示は、リポジトリの中で生成して開く。Web への公開はこの spec の範囲に入れない |
| つなぐツール | 項目とテストをつなぎ、一覧と表示を作るツールは、#200 で決めた sphinx-needs を使う。開発の環境でだけ動かし、配布物には入れない。利用者の前提に Python を足さない。表示を CI で作るかは、実装の中で決める |
| ツールに合わせたテストの直し | vitest の `it.each` は項目へつなげないので、つなぐテストは `it.for` に書き換える。pytest の結果は、クラスの名前が入らない形で出る（#200 の結果） |
| 規約の対象のテスト | コマンド・ツールの公開面を確かめるテストを対象にする。ドメイン層の単体テストは、名前の文の形だけを規約に合わせ、項目へのつなぎは求めない |
| pecot-workflow の pytest | Epic #42 で Python のテストは消える。既存の pytest の約 2,100 件は名前を直さず、規約の lint の対象から外す。項目へのつなぎは pytest でも書けるので、pecot-workflow の振る舞いの項目は、今の pytest につなぐ。移行のときに、つなぎ先を Node のテストへ移す |
| テストの構成の決め | 「いちばん外の題をコマンド・ツールの名前にする」決めは、新しく作る公開面のテストのファイルから当てる。今の公開面のテストは、観点ごとのファイルで全ツールを回す作りなので、作り替えない。コマンド・ツールごとの一覧は、項目へのつなぎから作れる |
| CLI の JSON の出力の形 | CLI の出力の形は人が書き、実装の出力と比べる確認は置かない。Epic #42 の移行の後は、MCP ツールの出力の形として実装から書き出す |
| コマンド一覧の補足 | w-help のコマンド一覧は、書き出した名前と説明だけから作る。今の表にある補足は、実装の help の文に移す |
| 項目を消してよい条件 | テストの無い振る舞いの項目を消してよいのは、今の実装にその振る舞いが無いと確かめたときだけにする。実装にある振る舞いは、テストを足す |
| hooks と状態ファイル | hooks は CLI・MCP の公開面ではないので、定義書の対象に入れない。w-help の `flags.md` は `.pecot/state/` の状態ファイルの一覧で、hooks も書き手なので、手書きのまま残す |
| スキルと agents | スキルの指示文と agents の定義は、定義書の対象に入れない |
| 終了コードと出力 | 既存のコマンド・ツールの振る舞いは変えない。定義書は今の振る舞いを書き起こす |
| 枠組みへの従い方 | POSIX の節立ては CLI が前提だ。MCP ツールでは、終了の状態を失敗の種別に、標準出力を結果の構造に読み替える。この読み替えは、このリポの決めである |
| 枠組みの名乗り方 | ISO/IEC/IEEE 29148・29119 と Automotive SPICE は本文を読めていない。準拠は名乗らず、追跡と網羅の考え方に従うとだけ書く |
| 採らない節 | POSIX の ASYNCHRONOUS EVENTS は全項目が既定の扱いなので、欄にしない。CHANGE HISTORY は各プラグインの CHANGELOG が担う |
| EARS の日本語の型 | 標準の日本語の文型は見つからなかった。型ごとの日本語の形は、このリポの規約として決める。主語（コマンド・ツールの名前）は省き、項目の ID で補う |
