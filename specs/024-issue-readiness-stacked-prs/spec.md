# Feature Specification: Issue の着手の可否を依存関係から判定し、前提が PR 中なら stacked PRs として積んで進める

**Feature Branch**: `024-issue-readiness-stacked-prs`

**Created**: 2026-11-12

**Status**: Draft

**Input**: Epic pecotcraft/pecot#47（親）と pecotcraft/pecot#50。フェーズの Issue の前後関係を GitHub の blocked by で表し、着手の可否を CLI が判定する。前提が PR 中のときは、その PR の上に積んで着手し、GitHub の stacked PRs として運用する。

## Clarifications

### Session 2026-11-12

- Q: 積んだ PR の最下段の base を、Epic ごとの統合ブランチと main のどちらにするか → A: main に直接積む。統合ブランチは作らない（FR-044）
- Q: サブタスクの親にする Epic を、#47 と #50 のどちらにするか → A: #47 を親にする。#50 の内容は User Story 1 に含める
- Q: w-issueize の段階で、積んで進めることをどこまで扱うか → A: フェーズごとの進め方と積める並びを、表と完了報告に出す（FR-046〜FR-051）
- Q: 上に載せれば足りる前提と、main に入るまで待つ前提を区別するか → A: 区別する。tasks.md の前提の表に種類と理由を書き、マージを待つ前提だけを理由つきで Issue の本文に残す。積める前提は書かない（FR-052〜FR-062）
- Q: 前提の関係を tasks.md のどこから読むか → A: w-breakdown が tasks の工程で、決まった形の前提の表を書かせる。表が無い tasks.md は、これまでどおり文章から読む（FR-052〜FR-054）
- Q: 前提の Issue がどの状態になったら、その上に積んで着手できることにするか → A: 前提の Issue の PR が開いたとき。ドラフトの PR も含む。ブランチがあるだけの段階と、push があるだけの段階では積まない（FR-012）
- Q: 「ブロック中」と判定された Issue に、待たずに着手する手段を用意するか → A: 用意しない。待たずに進めたいときは、前提を外すか種類を変えてから着手する（FR-021）
- Q: 前提の Issue がマージされないまま閉じられたとき、それを待っていた Issue をどう扱うか → A: 「ブロック中」のままにし、理由にその旨を出す。進めるには前提を外す（FR-011、FR-063）
- Q: 着手の可否を、ボードでどう見せるか → A: 進行の欄の列で見せる。`Blocked` の列を足し、前提を待つ Issue を置く。`Ready` の列は、着手できる Issue だけにする。積めば着手できる Issue も `Ready` に置く。既定の Status は進み具合の軸なので、着手の可否には使わない（FR-064〜FR-072）
- Q: 前提がマージされないまま閉じられた Issue を、ボードでどう見せるか → A: 列は `Blocked` のままにする。既定の Status には、人の判断を待つ値 `Needs Attention` を重ねる。人がセッションを始めて前提を見直す（FR-066）
- Q: 人の判断を待つ値と、spec 023（Epic #315）の待ちの値の関係をどうするか → A: 同じ 1 つの値にする（FR-071）
- Q: `Blocked` の列と、既にある `Pending` の列をどう分けるか → A: 置く理由と動かす者で分ける。`Pending` は、人が今はやらないと決めて置く列で、人だけが出し入れする。`Blocked` は、前提を待つ Issue を pecot が置く列で、pecot だけが出し入れする（FR-073〜FR-075）
- Q: 積めること・積んでいることを、ボードでどう見せるか → A: 見せない。人は `Ready` の列にあれば着手できると読むだけでよい。main から切るか積むかは、着手の操作のときに CLI が決め、エージェントはその出力に従う。積む先を示すフィールドやラベルは足さない（FR-076）
- Q: ボードの列を、いつ何が動かすか → A: 2 つの段で動かす。pecot の操作がその場で動かす。pecot の操作が拾えなかったずれは、GitHub Actions のワークフローが直す（FR-068、FR-069、FR-078〜FR-083）
  - 契機は `pull_request: closed`・`issues: closed/reopened`・`schedule` である。一覧を出す操作は、列を直さず判定を表示するだけだ
  - Projects の組み込みの Workflows は使えない。ほかの Issue の状態と blocked by を条件にできず、進行の欄も動かせないからだ
- Q: 人がボードのカードを誤って動かしたとき、どう扱うか → A: 未着手の Issue が判定と違う列にあれば、Actions のワークフローが判定に合った列へ動かす。一覧を出す操作は動かさない。対象の列は `Blocked`・`Ready`・`Active`・`In Review` である。動かした内容は出力に出す。人が動かす列（`Backlog`・`Pending`・`Archived`）への移動は、意図と区別できないので直さない（FR-079〜FR-081）
- Q: タイトルの先頭の番号を、この機能の後も付け続けるか → A: Epic の中の通し番号だけにする（`#42-20`、`#42-21`）。段を表す番号と枝の文字（`22a`・`22b`）はやめる。順番と並行は、blocked by とボードの列で読む（FR-043）
- Q: 人の判断を待つ値の名前を何にするか → A: `Needs Attention`。spec 023 の `Waiting` を置き換える（FR-071）
- Q: 着手済みの Issue が後からブロック中になったとき、列と札を動かすか → A: 動かさない。ブランチか PR がある Issue は、進めているセッションのものだ。別のセッションの操作とワークフローは、その列と札を変えない。食い違いは警告で知らせる（FR-084）

## 背景

Issue を進めてよいかどうかを、ボードと CLI のどちらでも読めない。

| 場面 | 今の姿 |
|---|---|
| Ready の意味 | w-issueize は tasks.md の全フェーズを Ready に置く。前提が済んでいないフェーズも Ready に並ぶので、Ready は「着手できる」を意味しない。文書の定義も「未着手または中断中」である |
| 前後関係の表し方 | タイトルの段の番号（`#42-20` など）だけ。段が同じなら並行できると分かるが、どの Issue がどの Issue を待つかは、本文と tasks.md を読まないと分からない |
| 前提が PR 中のとき | 前提の Issue が In Review の間、次の Issue を待つか、前提の PR の上に積んで始めるかを、人がその都度判断する。積んで始める動線はスキルにも CLI にも無い |
| PR の出し方 | すべての PR を main へ単独で出す。前提の PR がマージされるまで、次の Issue のブランチは切れない |

GitHub の側には、使える機能がそろっている。

| 機能 | 確かめたこと |
|---|---|
| Issue の依存関係（blocked by / blocking） | 2025-08-21 から一般提供。別のリポの Issue も指せる。付ける操作は通った。外す操作は、Epic #50 では GraphQL が GitHub の側のエラーで失敗したが、#374 の確かめでは GraphQL も REST も通った |
| stacked PRs | 2026-10-06 に github.com の全プランで一般提供。下の PR をマージすると、上の PR は自動で積み直され、base が main に変わる。マージは下からだけできる。squash と merge queue に対応する。スタックの中のすべての PR に、最下段の base の ruleset と必須チェックがかかる。fork をまたぐスタックは作れない |
| このリポの設定 | マージは squash だけを許す。main に ruleset と merge queue がかかる。PR の CI は base のブランチで絞っていないので、積んだ PR でも動く |

前提の出どころは spec-kit の tasks.md だ。spec-kit は最新版（v1.4.0）でも、依存を文章でしか持たない。

| 知りたいこと | 今の tasks.md で分かる程度 |
|---|---|
| どのフェーズがどのフェーズを待つか | ほぼ分かる。ただし書式が決まっておらず、表のものと文のものがある。文のものはエージェントの読解に頼る |
| 並行できる範囲 | 分かる。箇条書きで書かれている |
| 上に載せれば足りるか、main に入るまで待つか | 表の外の文にしか無い。例は `specs/023-label-triggered-autofix/tasks.md` で、確認のタスクは前のフェーズのスキルが main に入ってから動かす |
| ブランチと PR の単位、着手できるかの判定 | 無い。spec-kit は 1 本の feature ブランチで全タスクを進める前提である |

spec-kit の Issue 化のコマンドは、blocked by と sub-issue のどちらも付けない。前提の種類を区別して Issue に残し、積む判断に使う仕組みは、spec-kit と pecot のどちらにも前例が無い。

この spec で使う言葉:

| 言葉 | 意味 |
|---|---|
| 前提 | ある Issue の着手を止める別の Issue。GitHub の blocked by で表す |
| 前提の種類 | 前提ごとに決める待ち方。「積める」と「マージを待つ」の 2 つ。何も書かなければ「積める」 |
| 積める前提 | 前提の変更がブランチの下にあれば進められる前提。前提が PR 中なら、その上に積んで着手できる |
| マージを待つ前提 | 前提の変更が main に入るまで着手できない前提。理由を必ず添える |
| 前提の表 | tasks.md の中の、フェーズ・前提・種類・理由を 1 行に 1 組ずつ並べた表 |
| 済んだ前提 | 前提の Issue が閉じていて、Issue の PR がマージ済みである状態。マージされずに閉じられた Issue は、済んだ前提に数えない |
| 着手の判定 | 前提の状態から計算する、Issue を今進めてよいかの区分。「着手できる」「積めば着手できる」「ブロック中」の 3 つ |
| 進行の欄 | pecot がボードに足す独自のフィールド。ボードの列になっている。値は Backlog・Pending・Ready・Active・In Review・Archived。この機能で `Blocked` を足す |
| 既定の Status | GitHub のボードに初めからあるフィールド。値は `Todo`・`In Progress`・`Done`。進み具合を示し、GitHub の既定の自動化が動かす。カードの上に色付きの札で出る |
| 人の判断を待つ値 | 既定の Status に足す `Needs Attention`。spec 023（Epic #315）が「待ちの値」と呼ぶものと同じ値で、Issue が人の対応か判断を待っていることを示す。列は動かさず、札だけが変わる |
| Issue の PR | Issue にリンクしたブランチを head に持つ PR と、閉じる参照でその Issue を指す PR。pecot は着手のたびにリンクしたブランチを作るので、pecot で進めた Issue は前者で見つかる |
| PR 中 | Issue が開いていて、Issue の PR がちょうど 1 本開いている状態。ドラフトの PR も含む。ブランチがあるだけで PR が無い Issue は、着手済みでも PR 中に数えない |
| 列 | 前提の関係で 1 本につながった、PR 中の Issue の並び。下が main に近い |
| 積む | main ではなく、前提の Issue のブランチを base にしてブランチを切り、PR を出すこと |
| スタック | GitHub が 1 つのまとまりとして扱う、積んだ PR の並び |
| 進め方 | 前提の形と種類から決まる、フェーズの進め方の見込み。「単独」「積める」「合流」「マージ待ち」の 4 つ。Issue の状態は見ない |
| 積める並び | 前提を 1 本ずつたどってつながる、フェーズまたは Issue の並び。前提のマージを待たずに続けて進められる範囲を示す |
| 積み直し | 下の段のブランチが変わった後に、上の段のブランチをその上に載せ直すこと |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - w-issueize で作ったフェーズの Issue に、前提が blocked by として付いている (Priority: P1)

Epic を分解した人が w-issueize でフェーズを一括で Issue にする。投稿の前に、フェーズごとの進め方と積める並びが表で示され、どこまでを前提のマージを待たずに続けて進められるかが分かる。投稿が終わると、前提のあるフェーズの Issue には、前提のフェーズの Issue が blocked by として付いている。前後関係は GitHub の Issue の画面とボードで見える。

**Why this priority**: 着手の判定も、積む判断も、この情報を元にする。これが無いと後の話が成り立たない。これだけでも、GitHub の画面で前後関係が読めるようになる（Epic #50 の内容）。

**Independent Test**: 前提のあるフェーズと並行できるフェーズを含む tasks.md を w-issueize にかける。作られた Issue を GitHub の画面で開き、前提のあるフェーズにだけ blocked by が付き、指す先が前提のフェーズの Issue であることを確かめる。投稿の前の表で、列に並ぶフェーズが「積める」、2 本の列を受けるフェーズが「合流」と出ることも確かめる。

**Acceptance Scenarios**:

1. **Given** フェーズ B の前提がフェーズ A である tasks.md、**When** 一括投稿する、**Then** B の Issue に A の Issue が blocked by として付く
2. **Given** 互いに依存しない 2 つのフェーズ、**When** 一括投稿する、**Then** どちらの Issue にも、相手を指す blocked by が付かない
3. **Given** 前提が 2 つあるフェーズ、**When** 一括投稿する、**Then** 両方の前提が blocked by として付く
4. **Given** 前提が、以前の実行で Issue 化済みのフェーズである、**When** 一括投稿する、**Then** 既存の Issue を blocked by に指す
5. **Given** 一括投稿で作られた Issue、**When** 本文を読む、**Then** 前後関係を説明する文が本文に無い
6. **Given** blocked by を付ける操作が途中で失敗した一括投稿、**When** 投稿が終わる、**Then** 作られた Issue と付けられなかった前提の組が出力に並ぶ
7. **Given** 前提が無いフェーズ、**When** w-issueize が投稿の前の表を示す、**Then** 進め方が「単独」と出る
8. **Given** 前提が 1 本の列に並ぶフェーズ、**When** 表を示す、**Then** 進め方が「積める」と出て、積む先のフェーズが読める
9. **Given** 互いに依存しない 2 つのフェーズを前提にするフェーズ、**When** 表を示す、**Then** 進め方が「合流」と出て、マージを待つフェーズが読める
10. **Given** 進め方の表、**When** 表の下を読む、**Then** 積める並びが、下の段から順に 1 本ずつ並んでいる
11. **Given** 一括投稿が終わった、**When** 完了報告を読む、**Then** 積める並びが Issue の番号で並び、最初に着手できる Issue が分かる
12. **Given** マージを待つ前提を持つフェーズ、**When** 表を示す、**Then** 進め方が「マージ待ち」と出て、待つフェーズと理由が読める
13. **Given** マージを待つ前提を持つフェーズ、**When** 一括投稿する、**Then** その Issue の本文に、マージを待つ前提の Issue 番号と理由が載る
14. **Given** 積める前提だけを持つフェーズ、**When** 一括投稿する、**Then** その Issue の本文に、前提についての記述が無い
15. **Given** 進め方の表と積める並び、**When** 同じ Issue ファイルでもう一度出す、**Then** 同じ結果になる。エージェントが手で計算した値ではない

### User Story 2 - Issue を今進めてよいかが、一覧と Issue の表示から分かる (Priority: P1)

次のタスクを選ぶ人またはエージェントが、ボードの一覧を出す。Ready の各 Issue に、着手できるか・どの Issue の上に積めば着手できるか・どの Issue を待つのかが並んでいる。本文も tasks.md も読まずに、次に手を付ける Issue を選べる。

**Why this priority**: 進めてよいかどうかが分からないことが、今の非効率の中心だ。ブランチや PR の動線を変えなくても、これだけで選ぶ手間が消える。

**Independent Test**: 前提の状態が「済んだ」「PR 中」「未着手」の Issue を 1 件ずつ用意する。一覧と個別の表示を出す。3 件の判定は順に「着手できる」「積めば着手できる」「ブロック中」になる。理由の Issue 番号も正しいことを確かめる。

**Acceptance Scenarios**:

1. **Given** 前提が無い、または前提がすべて済んだ Issue、**When** 一覧を出す、**Then** 「着手できる」と出る
2. **Given** 開いている前提が 1 件で、その前提が PR 中の Issue、**When** 一覧を出す、**Then** 「積めば着手できる」と、積む先の Issue 番号が出る
3. **Given** 開いている複数の前提がすべて PR 中で 1 本の列に並ぶ Issue、**When** 一覧を出す、**Then** 「積めば着手できる」と列の最上段の Issue 番号が出る
4. **Given** 未着手の前提がある Issue、**When** 一覧を出す、**Then** 「ブロック中」と、待っている Issue 番号が出る
5. **Given** 開いている前提がすべて PR 中だが、2 本以上の列に分かれている Issue、**When** 一覧を出す、**Then** 「ブロック中」と、列が分かれている旨と前提の Issue 番号が出る
6. **Given** 着手の判定が出ている Issue、**When** 前提の Issue の PR がマージされる、**Then** 次に一覧を出したとき、人が何も書き換えなくても判定が変わっている
7. **Given** 任意の Issue、**When** その Issue を個別に表示する、**Then** 前提の一覧（番号・タイトル・状態・種類）と着手の判定が出る
8. **Given** マージを待つ前提が PR 中の Issue、**When** 一覧を出す、**Then** 「ブロック中」と出て、マージを待つ Issue 番号と理由が読める
9. **Given** マージを待つ前提が済み、積める前提が PR 中の Issue、**When** 一覧を出す、**Then** 「積めば着手できる」と出る
10. **Given** 前提がマージされないまま閉じられた Issue、**When** 一覧を出す、**Then** 「ブロック中」と出て、前提がマージされずに閉じられた旨と、前提を外す操作が読める
11. **Given** 「着手できる」Issue、**When** ボードを見る、**Then** `Ready` の列にある
12. **Given** 「積めば着手できる」Issue、**When** ボードを見る、**Then** `Ready` の列にある
13. **Given** 「ブロック中」の Issue、**When** ボードを見る、**Then** `Blocked` の列にある
14. **Given** 前提がマージされないまま閉じられた Issue、**When** ボードを見る、**Then** `Blocked` の列にあり、既定の Status の札が `Needs Attention` である
15. **Given** `Blocked` の列の Issue、**When** 前提の Issue の PR ができて積めるようになる、**Then** `Ready` の列に移る
16. **Given** `Blocked` の列の Issue、**When** 前提の PR がマージされて片付けが済む、**Then** `Ready` の列に移る
17. **Given** 札が `Needs Attention` の `Blocked` の Issue、**When** 人が前提を外すか付け替える、**Then** 札が `Todo` に戻り、Issue は判定に合った列へ移る
18. **Given** w-issueize の一括投稿、**When** 投稿が終わる、**Then** 前提を待つフェーズの Issue は `Blocked` の列にある。待たないフェーズの Issue は `Ready` の列にある
19. **Given** 人が `Pending` の列に置いた Issue、**When** その前提が済む、または前提が増える、**Then** `Pending` の列から動かない
20. **Given** `Pending` の列の Issue、**When** 人が `Ready` か `Blocked` の列へ戻す、**Then** 次に pecot が動いたときに、判定に合った列へ直る
21. **Given** `Ready` の列の Issue、**When** 着手する前に前提が足される、**Then** `Blocked` の列に移る
22. **Given** 進行の欄に `Blocked` の値が無いボード、**When** 一覧を出す、**Then** 一覧の判定と理由は出て、足りない値と足し方が案内される

### User Story 3 - 着手すると、判定に合った base でブランチが切られ、ブロック中なら止まる (Priority: P1)

エージェントが w-active で Issue に着手する。前提がすべて済んでいれば main から、前提が PR 中なら前提のブランチから、ブランチが切られる。ブロック中の Issue は、理由を示して止まる。人が base を選ぶことは無い。

**Why this priority**: 判定を見せるだけでは、積むかどうかの判断と操作が人に残る。着手の操作が判定に従うことで、「スタックとしてなら進められる」場面を取りこぼさなくなる。

**Independent Test**: User Story 2 と同じ 3 件の Issue で着手の操作を打つ。1 件目は main から、2 件目は前提のブランチからブランチができ、3 件目はブランチができずに理由が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 「着手できる」Issue、**When** 着手する、**Then** main を base にブランチができる。動きはこれまでと変わらない
2. **Given** 「積めば着手できる」Issue、**When** 着手する、**Then** 積む先の Issue のブランチを base にブランチができ、出力から base と積んだ理由が読める
3. **Given** 「ブロック中」の Issue、**When** 着手する、**Then** ブランチを作らずに止まり、待っている Issue 番号と状態が出る
4. **Given** 「ブロック中」で止まった着手、**When** 出力を読む、**Then** 待たずに進めたいときの直し方（前提を外す・種類を変える）が案内されている
5. **Given** 「積めば着手できる」Issue、**When** 人が積まずに待つと決める、**Then** 着手の操作を打たないだけで済み、ボードの状態は変わらない
6. **Given** 積んで着手したブランチ、**When** w-active の続きの手順（調査・計画・レビュー・投稿）を進める、**Then** 手順は単独のブランチのときと同じに進む

### User Story 4 - 積んで着手した Issue の PR が、スタックとして出る (Priority: P2)

積んで着手した Issue の実装を終えた人が w-pr で PR を作る。PR の base は下の段のブランチになり、GitHub の上でスタックとして登録される。レビューする人は、その段の差分だけを見る。

**Why this priority**: User Story 3 で積んだブランチを、レビューへ出せる形にする。User Story 1〜3 が無いと積んだブランチが生まれないので、その後に置く。

**Independent Test**: 前提の PR が開いている状態で、積んで着手した Issue の PR を作る。GitHub の画面で、PR の base が前提のブランチであること、2 つの PR がスタックとして並ぶこと、差分にその段の変更だけが出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 積んで着手したブランチ、**When** PR を作る、**Then** PR の base が下の段のブランチになる。人は base を指定しない
2. **Given** 下の段の PR が開いている、**When** 上の段の PR を作る、**Then** 2 つの PR が GitHub のスタックとして登録される
3. **Given** 積んで着手した後に下の段の PR がマージされずに閉じられたブランチ、**When** PR を作ろうとする、**Then** 止まり、base にしたブランチの PR が無い旨と直し方を示す
4. **Given** 積んで着手した後に下の段の PR がマージされたブランチ、**When** PR を作る、**Then** PR の base が main になり、差分はその段の変更だけになる
5. **Given** main から切った単独のブランチ、**When** PR を作る、**Then** これまでどおり main へ単独の PR が出る。スタックには登録されない
6. **Given** gh stack 拡張が入っていない環境、**When** 積んだブランチの PR を作る、**Then** 拡張を求めずに、PR がスタックとして登録される

### User Story 5 - スタックを下からマージし、次に着手できる Issue が分かる (Priority: P2)

レビューの済んだ PR を w-merge でマージする。スタックの最下段だけがマージの対象になる。マージの後、上の段は main 向きに変わり、着手できるようになった Issue が知らされる。

**Why this priority**: 積んだ PR を main に届ける最後の工程だ。順番を誤ると上の段の変更が巻き込まれるので、CLI が順番を守らせる。

**Independent Test**: 2 段のスタックで、上の段の PR のマージを試みて止まることを確かめる。次に下の段をマージする。上の段の PR の base が main に変わり、下の段の Issue が閉じることを確かめる。マージした Issue を待っていた別の Issue について、「着手できる」に変わったと知らされることも確かめる。

**Acceptance Scenarios**:

1. **Given** 2 段のスタック、**When** 下の段の PR をマージする、**Then** 下の段の Issue が閉じ、上の段の PR は開いたまま base が main になる
2. **Given** 下の段が未マージのスタック、**When** 上の段の PR をマージしようとする、**Then** マージせずに止まり、先にマージする PR が出る
3. **Given** マージが終わった、**When** マージの後の片付けが済む、**Then** この Issue を前提にしていた Issue のうち判定の変わったものを、新しい判定とともに知らせる
4. **Given** 下の段がマージされた、**When** 上の段の作業ディレクトリに戻る、**Then** 上の段のブランチを main の上に載せ直す手順が案内され、その後は単独のブランチと同じに扱える
5. **Given** 単独の PR、**When** マージする、**Then** これまでどおりにマージと片付けが進む

### User Story 6 - 下の段を直した後に、上の段を積み直せる (Priority: P3)

レビューの指摘で下の段の PR を直した。上の段のブランチは、古い下の段の上へ載ったままだ。上の段を積み直す手順がある。積み直しの要るブランチは CLI が知らせる。

**Why this priority**: 積んでいる間に下の段が変わるのは、積んだ運用では普通に起きる。ただし User Story 4・5 までで、下の段を直さずに通るスタックは運用できる。

**Independent Test**: 2 段のスタックで下の段にコミットを足して push する。上の段で状態を確かめる操作を打ち、積み直しが要ると出ることを確かめる。積み直しの手順を実行し、上の段の PR の差分がその段の変更だけに戻ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 下の段が push された後のスタック、**When** 上の段で状態を確かめる、**Then** 積み直しが要ると出る
2. **Given** 積み直しが要る上の段、**When** 積み直しの手順を実行する、**Then** 上の段のブランチが新しい下の段の上に載り、PR の差分がその段の変更だけになる
3. **Given** 積み直しの途中で衝突が起きた、**When** 手順が止まる、**Then** 衝突したファイルと、続ける操作・取りやめる操作が案内される
4. **Given** 下の段と上の段が別々の作業ディレクトリにある、**When** 下の段を直す、**Then** 上の段の作業ディレクトリの未コミットの変更は書き換えられない
5. **Given** w-revise で下の段の PR の指摘を直した、**When** w-revise が終わる、**Then** 上に積んだ段があれば、積み直しの要る旨を報告に出す

### User Story 7 - 既存の Issue にも、前提を付け外しできる (Priority: P3)

w-issueize を通らずに作った Issue や、この機能より前に作ったフェーズの Issue にも、前提を付けたい。CLI から 1 件ずつ付け外しでき、付けた直後から着手の判定に反映される。

**Why this priority**: 計画は途中で変わる。前提を足す・外す手段が無いと、判定が実態からずれたまま直せない。新しく作る Issue は User Story 1 で足りるので、後に置く。

**Independent Test**: 前提の無い 2 件の Issue で、一方をもう一方の前提として付ける。一覧の判定が「ブロック中」に変わることを確かめる。外すと「着手できる」に戻ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 2 件の Issue、**When** 一方をもう一方の前提として付ける、**Then** GitHub の画面に blocked by が出て、着手の判定に反映される
2. **Given** 前提の付いた Issue、**When** その前提を外す、**Then** GitHub の画面から blocked by が消え、判定が変わる
3. **Given** 別のリポの Issue、**When** 前提として付ける、**Then** 付き、判定に反映される
4. **Given** 付けると前提が輪になる組、**When** 付けようとする、**Then** 付けずに止まり、輪になる Issue の並びが出る
5. **Given** すでに付いている前提、**When** 同じ前提をもう一度付ける、**Then** エラーにならず、付いている状態のまま終わる

### User Story 8 - w-breakdown が、前提を決まった形の表で tasks.md に書かせる (Priority: P2)

Epic を分解する人が w-breakdown で tasks の工程を回す。できた tasks.md には、フェーズ・前提・種類・理由を並べた前提の表がある。マージを待つ前提には理由が書かれている。w-issueize は、その表を読解せずにそのまま使う。

**Why this priority**: 前提の読み違いは、blocked by と積む判断の両方を誤らせる。今は書式が tasks.md ごとに違い、種類は表の外の文にしか無い。ただし表が無くても User Story 1 は文章から読んで動くので、P1 の後に置く。

**Independent Test**: main に入らないと確かめられないフェーズを含む Epic を w-breakdown にかける。できた tasks.md の前提の表に、そのフェーズの前提が「マージを待つ」と理由つきで載ることを確かめる。その tasks.md を w-issueize にかけ、表の行と付いた blocked by が 1 対 1 で合うことを確かめる。

**Acceptance Scenarios**:

1. **Given** w-breakdown の tasks の工程、**When** tasks.md ができる、**Then** 前提の表があり、前提を持つフェーズごとに、前提・種類・理由が 1 行に 1 組ずつ並ぶ
2. **Given** 前提の変更が main に入らないと確かめられないフェーズ、**When** tasks.md ができる、**Then** その前提の種類が「マージを待つ」になり、理由が書かれている
3. **Given** 前提の表のある tasks.md、**When** w-issueize にかける、**Then** 表の行と、付く blocked by が 1 対 1 で合う
4. **Given** 存在しないフェーズ・輪になる前提・理由の無い「マージを待つ」のどれかを含む前提の表、**When** w-issueize にかける、**Then** 投稿の前に止まり、直す行を示す
5. **Given** 前提の表の無い tasks.md（spec-kit をそのまま使ったもの）、**When** w-issueize にかける、**Then** 文章から前提を読み、種類を「積める」として表を示す。表が無かった旨を利用者に伝える
6. **Given** w-issueize が示した表、**When** 利用者が、ある前提の種類を変えるよう指示する、**Then** その指示が進め方と投稿の内容に反映される

### User Story 9 - 計画が変わったら、前提の種類を後から変えられる (Priority: P3)

積めると決めた前提が、進めてみると main に入るまで待つ必要があると分かった。逆もある。利用者は、Issue ごとに前提の種類と理由を変えられ、変えた直後から着手の判定に反映される。

**Why this priority**: 種類を Issue に残すので、直す手段が無いと実態からずれる。新しく作る Issue は User Story 1 と 8 で足りるので、後に置く。

**Independent Test**: 積める前提が PR 中の Issue で、その前提を「マージを待つ」に変える。判定が「ブロック中」に変わり、Issue の本文に理由が載ることを確かめる。元に戻すと「積めば着手できる」に戻り、本文の記述が消えることを確かめる。

**Acceptance Scenarios**:

1. **Given** 積める前提を持つ Issue、**When** その前提を理由つきで「マージを待つ」に変える、**Then** Issue の本文に前提の Issue 番号と理由が載り、判定に反映される
2. **Given** マージを待つ前提を持つ Issue、**When** その前提を「積める」に変える、**Then** 本文からその記述が消え、判定に反映される
3. **Given** 「マージを待つ」への変更、**When** 理由を付けずに変えようとする、**Then** 変えずに止まり、理由が要る旨を示す
4. **Given** すでに積んで着手した Issue、**When** 下の段の前提を「マージを待つ」に変える、**Then** 変更は通り、着手済みのブランチは変わらない。状態を確かめる操作に、判定と着手の食い違いが出る
5. **Given** 前提を付ける操作、**When** 種類と理由を一緒に指定する、**Then** 1 回の操作で blocked by と本文の記述がそろう

### Edge Cases

- 前提の Issue が、マージされずに閉じられた（やらない・重複・手で閉じた）とき: 「ブロック中」のままにし、理由にその旨を出す。計画を見直し、要らない前提は外す
- 前提の Issue が読めない（権限が無い・削除された）とき: 判定を「ブロック中」にし、読めなかった Issue を理由に出す
- 前提の Issue が別のリポにあり、PR 中のとき: 別のリポのブランチには積めないので「ブロック中」にし、その旨を理由に出す
- 前提の Issue に開いている PR が 2 本以上あるとき: 積む先を決められないので「ブロック中」にし、PR の番号を理由に出す
- 前提の Issue の PR が、リンクしたブランチと閉じる参照のどちらも持たないとき: Issue の PR として見つからない。対象は、`Closes` が無い PR と、base が既定のブランチでない PR である。前提は PR 中にならず、待つ側は「ブロック中」になる。理由に、前提に PR が見つからない旨を出す
- 前提の Issue の PR が fork から出ているとき: 積めないので「ブロック中」にする
- 前提の Issue が着手済みで PR が無いとき: 「ブロック中」にし、理由に、着手済みで PR を待っている旨を出す
- 前提が輪になっているとき（GitHub の画面で付けられた場合）: 輪の中の Issue はすべて「ブロック中」にし、輪になっている旨を出す
- 積んで着手した後に、下の段の Issue が PR を閉じて作り直しになったとき: 状態を確かめる操作で、base のブランチが無くなった旨を出す
- 積んだ段の数が多いとき: 段の数に上限は置かない。一覧の表示には、main からの段の数が読める
- 本文にマージを待つ前提の記述があるのに、その Issue が blocked by に無いとき（GitHub の画面で外された場合）: blocked by を正とし、その記述は判定に使わない。個別の表示に、食い違いがある旨を出す
- 本文のマージを待つ前提の記述が、人の編集で読めない形になったとき: 読めなかった前提を「マージを待つ」として扱い、「ブロック中」にする。積める側には倒さない
- マージを待つ前提と積める前提の両方が開いているとき: 「ブロック中」にし、理由にはマージを待つ前提を先に出す
- 一部のタスクだけが main を待つとき（フェーズ全体は進められる）: 前提にも「マージを待つ」にもしない。これまでどおり、タスクの行の注記として Issue の Tasks に写る
- 前提の Issue が `Needs Attention`（人の対応を待って止まっている）になっているとき: 判定の規則は変えない。PR が開いていれば積める前提として扱い、PR が無ければ「ブロック中」にする。理由に、前提が人の対応を待っている旨を添える
- 自動処理（spec 023）が `Needs Attention` を書いた Issue に、前提の見直しも重なったとき: 値は 1 つなので `Needs Attention` のままにする。どちらの理由かは、Issue の個別の表示で読める。両方が解消するまで、ほかの値に変えない
- pecot を通さない操作（GitHub の画面でのマージ・PR のクローズ・前提の変更）で列が古くなったとき: 着手の操作は列を読まずに判定を計算し直す。Actions のワークフローが、ずれを直す
- 人が GitHub の画面で、`Blocked` の Issue を `Ready` へ手で動かしたとき: Actions のワークフローが `Blocked` へ戻す。待たずに進めたいときは、前提を外すか種類を変える
- 人が `Blocked` か `Ready` の Issue を `Pending`・`Backlog`・`Archived` へ動かしたとき: 意図した移動か誤操作かを区別できないので、pecot は動かさない。その Issue を前提にしている Issue の理由に、前提がその列にある旨が出る
- 人が未着手の Issue を誤って `Active` か `In Review` へ動かしたとき: 着手の跡（Issue のブランチ・PR）が無いので、判定に合った列（`Ready` か `Blocked`）へ戻す
- ワークフローが列を直している最中に、別のセッションが同じ Issue の列を動かしたとき: 後から書いたほうが残る。次のワークフローの実行で、判定に合わせて直る
- `Pending` の Issue を前提にしている Issue: 判定は「ブロック中」のままで、列は `Blocked` にある。理由に、前提が保留中である旨を添える
- 着手した後でブロック中になった Issue: 列と札は動かさない。前提の追加・下の段の PR のクローズ・種類の変更・前提の開き直しで起きる。その作業ディレクトリの状態の表示に、食い違いを警告で出す。続けるか待つかは、進めている人が決める
- Backlog・Archived の Issue: この機能は列を動かさない
- 中断して `Ready` に戻した Issue: 着手の跡があるので、列は動かさない。再開のときに前提が済んでいなければ、着手の操作が止まり、理由を出す
- Epic や Tracker のように、着手の対象でない Issue: 着手の判定を出さない
- 判定のための問い合わせが失敗したとき（通信・レート制限）: 一覧そのものは出し、判定の欄に取得できなかった旨を出す。「着手できる」とは出さない
- 一括投稿の途中で Issue の作成そのものが失敗したとき: すでに作った Issue の blocked by は、作られた Issue どうしの分だけ付ける
- スタックの機能が無いリポ（GitHub Enterprise Server など）で、積んだブランチの PR を作るとき: PR は下の段を base にして作る。スタックとして登録できなかった旨を出す

## Requirements *(mandatory)*

### Functional Requirements

#### 前提の登録

| 番号 | 要件 |
|---|---|
| FR-001 | w-issueize の一括投稿は、フェーズの前提を、作った Issue どうしの blocked by として付けなければならない |
| FR-002 | 一括投稿は、前提が以前に Issue 化済みのフェーズであるとき、既存の Issue を blocked by に指さなければならない |
| FR-003 | 前提として付けるのは、フェーズ全体の着手を止める依存だけとする。一部のタスクだけが待つ依存は付けない |
| FR-004 | w-issueize が利用者に示すフェーズの表は、各フェーズの前提を、付ける blocked by の形で示さなければならない |
| FR-005 | Issue の本文のテンプレートと w-issueize の手順は、GitHub の画面が示す前後関係を本文に書かせてはならない。書かせるのは、マージを待つ前提とその理由だけとする |
| FR-006 | 一括投稿は、blocked by を付けられなかった組を、Issue の番号とともに出力しなければならない。Issue の作成の結果は、その失敗で取り消さない |
| FR-007 | 利用者は、既存の Issue に前提を 1 件ずつ付け外しできなければならない。同じリポの Issue も、別のリポの Issue も指せる |
| FR-008 | 前提を付ける操作は、付けると輪になる組を拒まなければならない |
| FR-009 | 前提を付け外しする操作は、同じ操作を繰り返しても結果が変わらないものでなければならない |

#### Issue 化の時点での進め方

| 番号 | 要件 |
|---|---|
| FR-046 | w-issueize は、投稿の前に示すフェーズの表に、フェーズごとの進め方を出さなければならない。進め方は次の順で決める。前提が無ければ「単独」。マージを待つ前提があれば「マージ待ち」。積める前提が 1 本の列に並べば「積める」。2 本以上の列に分かれれば「合流」 |
| FR-047 | 進め方が「積める」のフェーズには積む先のフェーズを添えなければならない。「合流」と「マージ待ち」のフェーズには、マージを待つフェーズを添える。「マージ待ち」には理由も添える |
| FR-048 | w-issueize は、フェーズの表の下と完了報告に、積める並びを下の段から順に出さなければならない。完了報告では Issue の番号で出す |
| FR-049 | 進め方と積める並びは、前提の形と種類からその都度計算しなければならない。計算の結果を Issue の本文・ラベル・ボードのフィールドに残してはならない |
| FR-050 | 進め方と積める並びを決める規則は、着手の判定の規則（FR-011〜FR-013）と同じ列の定義と種類の扱いを使わなければならない。Issue 化の時点で「積める」と出たフェーズは、前提が PR 中になった時点で「積めば着手できる」と判定される |
| FR-051 | ボードの一覧は、同じ Epic の Issue について、積める並びを読める形で出さなければならない |

#### 前提の種類

| 番号 | 要件 |
|---|---|
| FR-052 | w-breakdown は、tasks の工程で、tasks.md に前提の表を書かせなければならない。表は、前提を持つフェーズごとに、前提のフェーズ・種類・理由を 1 行に 1 組ずつ持つ |

## Assumptions

- スタックは main に直接積む。Epic ごとの統合ブランチは作らない（2026-11-12 にユーザーが決定）
- この spec の「main」は、リポの開発ブランチ（設定の `develop_branch`）を指す。このリポでは main である
- 親 Epic は #47 とし、#50 の内容は User Story 1 として含める（2026-11-12 にユーザーが決定）。#47 の TO-BE にあった「w-pr・w-merge など他のスキルの stacked PRs 対応はやらない」は取り下げる
- 前提の種類は 2 つだけにする。「一部のタスクだけが main を待つ」は種類にせず、これまでどおりタスクの行の注記で表す
- マージを待つ前提と理由は、Issue の本文に置く。GitHub の blocked by は種類を持てず、待つ理由は読者の判断に使う情報だからだ。置く形（節の名前と書式）は plan の工程で決める
- 前提の表の形（列の名前と値の書き方）は plan の工程で決める。spec-kit のテンプレートは利用者の環境のものなので変えず、w-breakdown から tasks の工程に渡す指示で書かせる
- 本文の Issue のキーのプレースホルダの展開は、今のまま残す。マージを待つ前提の節は CLI が足すので、この機能はプレースホルダを使わない
- 判断は CLI に寄せ、スキルは CLI の出力に従う。利用環境のエージェントの挙動は、配布物（SKILL.md・テンプレート・CLI の検証）で決まるからだ
- CLI の変更は Node の CLI にだけ入れる。Python の CLI は Epic #42 で消す予定（#350・#351）で、この機能の実装はその後に置く
- 「PR 中」は、前提の Issue を閉じる PR が開いていることで判定する（2026-11-12 にユーザーが決定）。リンクしたブランチは着手の直後にリモートへできるが、中身が無いので積む先にしない
- 「ブロック中」を無視して着手する指定は作らない（2026-11-12 にユーザーが決定）。判定が実態と違うときは、前提か種類を直す。直した結果が Issue に残り、後で見る人とエージェントが同じ判断をできる
- 着手の可否は、進行の欄の列で示す（2026-11-12 にユーザーが決定）。既定の Status は進み具合の軸で、`Todo` は残っている作業、`In Progress` は着手済み、`Done` は完了を意味する。着手の可否をここに混ぜない
- 前提の見直しが要る Issue は、人の判断を待つ値 `Needs Attention` を既定の Status に重ねて表す（2026-11-12 にユーザーが決定）。spec 023 の設計と同じく、列は動かさない
- GitHub の Projects には、依存の関係を並べて見せるビューも、blocked by を列に出すフィールドも無い（2026-11-12 に調査）。親子の入れ子（Show hierarchy）はあるが、依存には対応していない
- 値を足す操作は、spec 023（FR-042）と同じ操作にまとめる。どちらの機能が先に入っても、後から入るほうが足りない値を足す。spec 023 の `Waiting` は未実装なので、名前を `Needs Attention` に変えても、直すのは文書だけで済む
- 積めば着手できる Issue は、専用の列を作らず `Ready` に置く。今手を付けられる点は同じで、積むかどうかは着手の操作が決める
- ボードで増えるのは、進行の欄の `Blocked` と、既定の Status の `Needs Attention` の 2 つだけにする（2026-11-12 にユーザーが決定）。`Pending` の列は隠さず、出したままでよい
- `Blocked` の列は `Ready` のすぐ左に置く。左から、待っている・着手できる・作業中・レビュー中の順に読める
- ボードの列は保存された写しで、古くなることも、人の誤操作でずれることもある。着手の操作は列を読まずに判定を計算するので、列がずれていても、ブロック中の Issue に着手することは無い
- カードを動かした履歴は GitHub から読めないので、誤操作そのものは見つけられない。見つけられるのは、列と実態の食い違いだけである
- 列を直す役は、一覧を出す操作から外し、GitHub Actions のワークフローに移す（2026-11-13 にユーザーが決定）。前提のある Issue が増えると、一覧のたびの読み取りが点数を食うからだ。ワークフローが動くまで、pecot を通らない操作の後は列が古い
- GitHub の標準の Blocked の印は、blocked by が付けば自動で出る。積めば着手できる Issue は、`Ready` の列にあって Blocked の印も出る。前提が開いているが積んで進められる、という意味になる
- マージされずに閉じられた前提は、済んだものと数えない（2026-11-12 にユーザーが決定）。別の PR にまとめて入った・手で直した場合も、前提を外す操作が 1 回要る
- 対象は github.com とする。stacked PRs が届いていない GitHub Enterprise Server では、前提の登録と着手の判定だけが使える
- pecot は、merge queue の無いブランチでは `merge_method: "squash"` を渡し、あるブランチでは渡さない
  - squash を許さないリポでは、GitHub が `failed` を返し、pecot はその文を出して止まる（未確認）

  - 段ごとに別の作業ディレクトリを使うときの、積み直しの手順（R6）
  - 積んだ PR がマージされたときの、Issue の自動クローズの挙動（R7）
